# OPSX 工作流

> 欢迎在 [Discord](https://discord.gg/YctCnvvshC) 上提供反馈。

## 这是什么？

OPSX 现在是 OpenSpec 的标准工作流。

它是一个**流动的、迭代的工作流**，用于 OpenSpec 变更。不再有僵化的阶段——只有您可以随时采取的行动。

## 为什么存在

旧版 OpenSpec 工作流虽然有效，但它是**锁定**的：

- **指令是硬编码的** — 埋在 TypeScript 中，您无法更改
- **全有或全无** — 一个大命令创建所有内容，无法单独测试各个部分
- **固定结构** — 每个人使用相同的工作流，无法自定义
- **黑盒** — 当 AI 输出不好时，您无法调整提示

**OPSX 将其开放。** 现在任何人都可以：

1. **尝试指令** — 编辑模板，看看 AI 是否表现更好
2. **粒度测试** — 独立验证每个产物的指令
3. **自定义工作流** — 定义自己的产物和依赖关系
4. **快速迭代** — 更改模板，立即测试，无需重建

```
旧版工作流：                      OPSX：
┌────────────────────────┐           ┌────────────────────────┐
│  硬编码在包中          │           │  schema.yaml           │◄── 您编辑这个
│  （无法更改）          │           │  templates/*.md        │◄── 或者这个
│        ↓               │           │        ↓               │
│  等待新版本发布        │           │  即时生效               │
│        ↓               │           │        ↓               │
│  希望它更好            │           │  自己测试               │
└────────────────────────┘           └────────────────────────┘
```

**这适用于所有人：**
- **团队** — 创建与您实际工作方式匹配的工作流
- **高级用户** — 调整提示以在您的代码库中获得更好的 AI 输出
- **OpenSpec 贡献者** — 无需发布即可尝试新方法

我们都在学习什么最有效。OPSX 让我们一起学习。

## 用户体验

**线性工作流的问题：**
您处于"规划阶段"，然后"实施阶段"，然后"完成"。但实际工作并非如此。您实施了一些东西，发现设计有误，需要更新 specs，继续实施。线性阶段与实际工作的方式相悖。

**OPSX 方法：**
- **行动，而非阶段** — 创建、实施、更新、归档——随时做其中任何一个
- **依赖关系是使能器** — 它们显示什么是可能的，而不是下一步必须做什么

```
  proposal ──→ specs ──→ design ──→ tasks ──→ implement
```

## 设置

```bash
# 确保您安装了 openspec — skills 会自动生成
openspec init
```

这会在 `.claude/skills/`（或等效目录）中创建 AI 编码助手自动检测的 skills。

默认情况下，OpenSpec 使用 `core` 工作流配置（`propose`、`explore`、`apply`、`sync`、`archive`）。如果您想要扩展工作流命令（`new`、`continue`、`ff`、`verify`、`bulk-archive`、`onboard`），使用 `openspec config profile` 进行配置，并使用 `openspec update` 应用。

在设置过程中，系统会提示您创建**项目配置**（`openspec/config.yaml`）。这是可选的，但推荐。

## 项目配置

项目配置让您设置默认值并将项目特定上下文注入到所有产物中。

### 创建配置

配置在 `openspec init` 期间创建，或手动创建：

```yaml
# openspec/config.yaml
schema: spec-driven

context: |
  技术栈：TypeScript, React, Node.js
  API 约定：RESTful, JSON 响应
  测试：Vitest 用于单元测试，Playwright 用于端到端测试
  风格：ESLint 与 Prettier，严格 TypeScript

rules:
  proposal:
    - 包括回滚计划
    - 标识受影响的团队
  specs:
    - 使用 Given/When/Then 格式编写场景
  design:
    - 对复杂流程包含时序图
```

### 配置字段

| 字段 | 类型 | 描述 |
|-------|------|-------------|
| `schema` | string | 新变更的默认 schema（例如 `spec-driven`） |
| `context` | string | 注入到所有产物指令中的项目上下文 |
| `rules` | object | 按产物规则，以产物 ID 为键 |

### 工作原理

**Schema 优先级**（从高到低）：
1. CLI 标志（`--schema <name>`）
2. 变更元数据（变更目录中的 `.openspec.yaml`）
3. 项目配置（`openspec/config.yaml`）
4. 默认（`spec-driven`）

**上下文注入：**
- 上下文被添加到每个产物的指令之前
- 包裹在 `<context>...</context>` 标签中
- 帮助 AI 理解您项目的约定

**规则注入：**
- 规则仅注入到匹配的产物中
- 包裹在 `<rules>...</rules>` 标签中
- 出现在上下文之后、模板之前

### 按 Schema 的产物 ID

**spec-driven**（默认）：
- `proposal` — 变更提案
- `specs` — 规范
- `design` — 技术设计
- `tasks` — 实施任务

### 配置验证

- `rules` 中未知的产物 ID 会生成警告
- Schema 名称会根据可用 schema 进行验证
- 上下文有 50KB 的大小限制
- 无效的 YAML 会报告行号

### 故障排除

**"规则中的未知产物 ID：X"**
- 检查产物 ID 是否与您的 schema 匹配（参见上面的列表）
- 运行 `openspec schemas --json` 查看每个 schema 的产物 ID

**配置未生效：**
- 确保文件位于 `openspec/config.yaml`（不是 `.yml`）
- 使用验证器检查 YAML 语法
- 配置更改立即生效（无需重启）

**上下文过大：**
- 上下文限制为 50KB
- 请总结或链接到外部文档

## 命令

| 命令 | 作用 |
|---------|--------------|
| `/opsx:propose` | 一步创建变更并生成规划产物（默认快速路径） |
| `/opsx:explore` | 思考想法、调查问题、明确需求 |
| `/opsx:new` | 启动新的变更 scaffold（扩展工作流） |
| `/opsx:continue` | 创建下一个产物（扩展工作流） |
| `/opsx:ff` | 快进规划产物（扩展工作流） |
| `/opsx:apply` | 实施任务，根据需要更新产物 |
| `/opsx:verify` | 验证实施是否匹配产物（扩展工作流） |
| `/opsx:sync` | 同步 delta specs 到主目录（默认工作流，可选） |
| `/opsx:archive` | 完成后归档 |
| `/opsx:bulk-archive` | 归档多个已完成的变更（扩展工作流） |
| `/opsx:onboard` | 端到端变更的引导式演示（扩展工作流） |

## 使用

### 探索想法
```
/opsx:explore
```
思考想法、调查问题、比较选项。无需结构——只是一个思考伙伴。当想法明确时，过渡到 `/opsx:propose`（默认）或 `/opsx:new`/`/opsx:ff`（扩展）。

### 启动新变更
```
/opsx:propose
```
创建变更并生成实施前所需的规划产物。

如果您已启用扩展工作流，您可以改用：

```text
/opsx:new        # 仅 scaffold
/opsx:continue   # 一次创建一个产物
/opsx:ff         # 一次性创建所有规划产物
```

### 创建产物
```
/opsx:continue
```
根据依赖关系显示已就绪的内容，然后创建一个产物。重复使用以逐步构建您的变更。

```
/opsx:ff add-dark-mode
```
一次性创建所有规划产物。当您清楚要构建什么时使用。

### 实施（灵活部分）
```
/opsx:apply
```
逐项完成任务，勾选完成。如果您同时处理多个变更，可以运行 `/opsx:apply <名称>`；否则它会从对话中推断，如果无法确定会提示您选择。

### 收尾
```
/opsx:archive   # 完成后移至归档（如果需要，会提示同步 specs）
```

## 何时更新与重新开始

您始终可以在实施前编辑您的 proposal 或 specs。但什么时候优化变成了"这是不同的工作"？

### Proposal 捕获什么

Proposal 定义三件事：
1. **意图** — 您在解决什么问题？
2. **范围** — 哪些在范围内/外？
3. **方法** — 您将如何解决它？

问题是：哪些发生了变化，变化有多大？

### 更新现有变更时：

**相同意图，执行调整**
- 您发现了之前未考虑到的边界情况
- 方法需要调整但目标不变
- 实施揭示设计略有偏差

**范围缩小**
- 您意识到完整范围太大，想先发布 MVP
- "添加暗色模式" → "添加暗色模式切换（系统偏好在 v2 中）"

**学习驱动的修正**
- 代码库结构与您想的不一样
- 某个依赖不按预期工作
- "使用 CSS 变量" → "改用 Tailwind 的 dark: 前缀"

### 开始新变更时：

**意图发生根本性改变**
- 问题本身已经不同
- "添加暗色模式" → "添加包含自定义颜色、字体、间距的完整主题系统"

**范围扩展**
- 变更增长太多，本质上是不同的工作
- 更新后原始 proposal 将无法识别
- "修复登录 bug" → "重写认证系统"

**原始可完成**
- 原始变更可以标记为"完成"
- 新工作是独立的，而非改进
- 完成"添加暗色模式 MVP" → 归档 → 新变更"增强暗色模式"

### 启发式方法

```
                        ┌─────────────────────────────────────┐
                        │     这是同一项工作吗？              │
                        └──────────────┬──────────────────────┘
                                       │
                    ┌──────────────────┼──────────────────┐
                    │                  │                  │
                    ▼                  ▼                  ▼
            意图相同？       重叠超过 50%？     原始变更能否
            问题相同？       范围相同？        "完成"而无需
                    │                  │          这些改动？
                    │                  │                  │
          ┌────────┴────────┐  ┌──────┴──────┐   ┌───────┴───────┐
          │                 │  │             │   │               │
         是               否  是           否   否              是
          │                 │  │             │   │               │
          ▼                 ▼  ▼             ▼   ▼               ▼
       更新              新变更 更新        新变更 更新         新变更
```

| 测试 | 更新 | 新变更 |
|------|--------|------------|
| **身份** | "同一件事，改进" | "不同的工作" |
| **范围重叠** | 超过 50% 重叠 | 少于 50% 重叠 |
| **完成性** | 没有更改就无法"完成" | 可以完成原始，新工作独立 |
| **连贯性** | 更新链讲述连贯的故事 | 补丁会混淆多于澄清 |

### 原则

> **更新保留上下文。新变更提供清晰性。**
>
> 当您的思考历史有价值时选择更新。
> 当重新开始比打补丁更清晰时选择新变更。

把它想象成 git 分支：
- 在同一个功能上工作时持续提交
- 当它是真正的新工作时开始新分支
- 有时合并部分功能，然后为第二阶段重新开始

## 有哪些不同？

| | 旧版（`/openspec:proposal`） | OPSX（`/opsx:*`） |
|---|---|---|
| **结构** | 一个大提案文档 | 具有依赖关系的离散产物 |
| **工作流** | 线性阶段：规划 → 实施 → 归档 | 灵活行动——随时做任何事情 |
| **迭代** | 笨拙地回退 | 边学习边更新产物 |
| **自定义** | 固定结构 | Schema 驱动（定义自己的产物） |

**关键洞见：** 工作不是线性的。OPSX 不再假装它是线性的。

## 架构深入

本节解释 OPSX 在底层如何工作以及它与旧版工作流的比较。
本节中的示例使用扩展命令集（`new`、`continue` 等）；默认 `core` 用户可以将相同的流程映射到 `propose → apply → sync → archive`。

### 理念：阶段与行动

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         旧版工作流                                          │
│                    （阶段锁定，全有或全无）                                  │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   ┌──────────────┐      ┌──────────────┐      ┌──────────────┐             │
│   │    规划      │ ───► │    实施      │ ───► │    归档      │             │
│   │    阶段      │      │    阶段      │      │    阶段      │             │
│   └──────────────┘      └──────────────┘      └──────────────┘             │
│         │                     │                     │                       │
│         ▼                     ▼                     ▼                       │
│   /openspec:proposal   /openspec:apply      /openspec:archive              │
│                                                                             │
│   • 一次性创建所有产物                                                     │
│   • 实施期间无法回退更新 specs                                              │
│   • 阶段门控强制执行线性推进                                                │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘


┌─────────────────────────────────────────────────────────────────────────────┐
│                            OPSX 工作流                                      │
│                      （灵活行动，迭代）                                     │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│              ┌────────────────────────────────────────────┐                 │
│              │              行动（而非阶段）               │                 │
│              │                                            │                 │
│              │   new ◄──► continue ◄──► apply ◄──► archive │                 │
│              │    │          │           │           │    │                 │
│              │    └──────────┴───────────┴───────────┘    │                 │
│              │              任意顺序                      │                 │
│              └────────────────────────────────────────────┘                 │
│                                                                             │
│   • 一次创建一个产物或快进                                                  │
│   • 在实施期间更新 specs/design/tasks                                       │
│   • 依赖关系促进进展，阶段不存在                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 组件架构

**旧版工作流**使用 TypeScript 中的硬编码模板：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                      旧版工作流组件                                          │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   硬编码模板（TypeScript 字符串）                                           │
│                    │                                                        │
│                    ▼                                                        │
│   工具特定配置器/适配器                                                     │
│                    │                                                        │
│                    ▼                                                        │
│   生成的命令文件（.claude/commands/openspec/*.md）                          │
│                                                                             │
│   • 固定结构，没有产物意识                                                  │
│   • 更改需要修改代码 + 重建                                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

**OPSX** 使用外部 schema 和依赖关系图引擎：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                         OPSX 组件                                           │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│   Schema 定义（YAML）                                                       │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  name: spec-driven                                                  │   │
│   │  artifacts:                                                         │   │
│   │    - id: proposal                                                   │   │
│   │      generates: proposal.md                                         │   │
│   │      requires: []              ◄── 依赖关系                          │   │
│   │    - id: specs                                                      │   │
│   │      generates: specs/**/*.md  ◄── Glob 模式                        │   │
│   │      requires: [proposal]      ◄── 在 proposal 后启用               │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   产物图引擎                                                                │
│   ┌─────────────────────────────────────────────────────────────────────┐   │
│   │  • 拓扑排序（依赖排序）                                             │   │
│   │  • 状态检测（文件系统存在性）                                       │   │
│   │  • 丰富指令生成（模板 + 上下文）                                    │   │
│   └─────────────────────────────────────────────────────────────────────┘   │
│                    │                                                        │
│                    ▼                                                        │
│   Skill 文件（.claude/skills/openspec-*/SKILL.md）                          │
│                                                                             │
│   • 跨编辑器兼容（Claude Code、Cursor、Windsurf）                            │
│   • Skills 查询 CLI 获取结构化数据                                          │
│   • 通过 schema 文件完全可自定义                                            │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 依赖关系图模型

产物形成一个有向无环图（DAG）。依赖关系是**使能器**，而非门控：

```
                              proposal
                             (根节点)
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                    ▼                           ▼
                 specs                       design
              (需要：                      (需要：
               proposal)                   proposal)
                    │                           │
                    └─────────────┬─────────────┘
                                  │
                                  ▼
                               tasks
                           (需要：
                           specs, design)
                                  │
                                  ▼
                          ┌──────────────┐
                          │ APPLY 阶段   │
                          │ (需要：       │
                          │  tasks)      │
                          └──────────────┘
```

**状态转换：**

```
   被阻塞 ────────────────► 就绪 ────────────────► 完成
      │                        │                       │
   缺少依赖                 所有依赖                文件存在
                           已完成                  于文件系统
```

### 信息流

**旧版工作流** — agent 接收静态指令：

```
  用户："/openspec:proposal"
           │
           ▼
  ┌─────────────────────────────────────────┐
  │  静态指令：                              │
  │  • 创建 proposal.md                      │
  │  • 创建 tasks.md                         │
  │  • 创建 design.md                        │
  │  • 创建 specs/<能力>/spec.md             │
  │                                         │
  │  不知道什么已经存在或                    │
  │  产物之间的依赖关系                      │
  └─────────────────────────────────────────┘
           │
           ▼
  Agent 一次性创建所有产物
```

**OPSX** — agent 查询丰富上下文：

```
  用户："/opsx:continue"
           │
           ▼
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  步骤 1：查询当前状态                                                     │
  │  ┌────────────────────────────────────────────────────────────────────┐  │
  │  │  $ openspec status --change "add-auth" --json                      │  │
  │  │                                                                    │  │
  │  │  {                                                                 │  │
  │  │    "artifacts": [                                                  │  │
  │  │      {"id": "proposal", "status": "done"},                         │  │
  │  │      {"id": "specs", "status": "ready"},      ◄── 第一个就绪的     │  │
  │  │      {"id": "design", "status": "ready"},                          │  │
  │  │      {"id": "tasks", "status": "blocked", "missingDeps": ["specs"]}│  │
  │  │    ]                                                               │  │
  │  │  }                                                                 │  │
  │  └────────────────────────────────────────────────────────────────────┘  │
  │                                                                          │
  │  步骤 2：获取就绪产物的丰富指令                                           │
  │  ┌────────────────────────────────────────────────────────────────────┐  │
  │  │  $ openspec instructions specs --change "add-auth" --json          │  │
  │  │                                                                    │  │
  │  │  {                                                                 │  │

  │  │  }                                                                 │  │
  │  └────────────────────────────────────────────────────────────────────┘  │
  │                                                                          │
  │  步骤 3：读取依赖 → 创建一个产物 → 显示解锁的内容                       │
  └──────────────────────────────────────────────────────────────────────────┘
```

### 迭代模型

**旧版工作流** — 迭代笨拙：

```
  ┌─────────┐     ┌─────────┐     ┌─────────┐
  │/proposal│ ──► │ /apply  │ ──► │/archive │
  └─────────┘     └─────────┘     └─────────┘
       │               │
       │               ├── "等等，设计有误"
       │               │
       │               ├── 选项：
       │               │   • 手动编辑文件（打破上下文）
       │               │   • 放弃并重新开始
       │               │   • 强行通过，稍后修复
       │               │
       │               └── 没有正式的"回退"机制
       │
       └── 一次性创建所有产物
```

**OPSX** — 自然迭代：

```
  /opsx:new ───► /opsx:continue ───► /opsx:apply ───► /opsx:archive
      │                │                  │
      │                │                  ├── "设计有误"
      │                │                  │
      │                │                  ▼
      │                │            只需编辑 design.md
      │                │            然后继续！
      │                │                  │
      │                │                  ▼
      │                │         /opsx:apply 从您
      │                │         上次中断处继续
      │                │
      │                └── 创建一个产物，显示解锁内容
      │
      └── 创建变更 scaffold，等待指示
```

### 自定义 Schema

使用 schema 管理命令创建自定义工作流：

```bash
# 从零创建新 schema（交互式）
openspec schema init my-workflow

# 或 fork 现有 schema 作为起点
openspec schema fork spec-driven my-workflow

# 验证您的 schema 结构
openspec schema validate my-workflow

# 查看 schema 从何处解析（用于调试）
openspec schema which my-workflow
```

Schemas 存储在 `openspec/schemas/`（项目本地，受版本控制）或 `~/.local/share/openspec/schemas/`（用户全局）。

**Schema 结构：**
```
openspec/schemas/research-first/
├── schema.yaml
└── templates/
    ├── research.md
    ├── proposal.md
    └── tasks.md
```

**schema.yaml 示例：**
```yaml
name: research-first
artifacts:
  - id: research        # 在 proposal 之前添加
    generates: research.md
    requires: []

  - id: proposal
    generates: proposal.md
    requires: [research]  # 现在依赖于 research

  - id: tasks
    generates: tasks.md
    requires: [proposal]
```

**依赖关系图：**
```
   research ──► proposal ──► tasks
```

### 总结

| 方面 | 旧版 | OPSX |
|--------|----------|------|
| **模板** | 硬编码 TypeScript | 外部 YAML + Markdown |
| **依赖关系** | 无（一次性全部） | 带拓扑排序的 DAG |
| **状态** | 基于阶段的心理模型 | 文件系统存在性 |
| **自定义** | 编辑源码，重建 | 创建 schema.yaml |
| **迭代** | 阶段锁定 | 灵活，编辑任何内容 |
| **编辑器支持** | 工具特定配置器/适配器 | 单一 skills 目录 |

## Schemas

Schemas 定义存在哪些产物及其依赖关系。目前可用：

- **spec-driven**（默认）：proposal → specs → design → tasks

```bash
# 列出可用 schema
openspec schemas

# 查看所有 schema 及其解析来源
openspec schema which --all

# 交互式创建新 schema
openspec schema init my-workflow

# Fork 现有 schema 进行自定义
openspec schema fork spec-driven my-workflow

# 使用前验证 schema 结构
openspec schema validate my-workflow
```

## 提示

- 使用 `/opsx:explore` 在提交变更前思考想法
- 当您清楚想要什么时使用 `/opsx:ff`，探索时使用 `/opsx:continue`
- 在 `/opsx:apply` 期间，如果发现问题——修复产物，然后继续
- 任务通过 `tasks.md` 中的复选框跟踪进度
- 随时检查状态：`openspec status --change "名称"`
