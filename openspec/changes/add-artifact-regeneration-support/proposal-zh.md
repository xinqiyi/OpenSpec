# 添加产物重新生成支持

## 问题

目前，在 OPSX 工作流中**没有办法重新生成产物**：

- `/opsx:apply` 仅读取磁盘上的现有内容
- `/opsx:continue` 仅创建下一个产物 - 不会触及现有的产物

如果你在 `tasks.md` 存在后编辑了 `design.md`，你唯一的选择是：
1. 手动删除 tasks.md，然后运行 `/opsx:continue`
2. 手动编辑 tasks.md

文档声称你可以"在过程中更新产物并继续"，但实际上没有支持这一点的机制。

## 提议的解决方案

两个部分：

### 第 1 部分：陈旧性检测
在 `/opsx:apply` 中添加产物陈旧性检测：

1. **跟踪修改时间**：生成产物时，记录其依赖项的修改时间
2. **检测陈旧性**：当 `/opsx:apply` 运行时，检查上游产物（design.md、规范）自 tasks.md 生成以来是否已被修改
3. **提示用户**：如果发现陈旧，询问："设计在任务生成后已被修改。是否想用 `/opsx:continue` 重新生成任务？"

## 用户体验

### 愿景：无缝中途修正

这是我们希望实现的工作流（目前有文档但没有支持）：

```
你：/opsx:apply

AI：正在处理任务...
    ✓ 任务 1.1：创建了缓存层
    ✓ 任务 1.2：添加了缓存失效

    正在处理 1.3：实现 TTL...
    我注意到设计假设使用 Redis，但你的项目使用
    内存缓存。我应该更新设计吗？

你：是的，更新为使用现有缓存模块。

AI：已将 design.md 更新为使用 src/cache/ 中的 CacheManager
    已将 tasks.md 更新为修订后的实施步骤
    继续实施...
    ✓ 任务 1.3：使用 CacheManager 实现了 TTL
    ...
```

**无需重新启动。** 只需更新产物并继续。

### 陈旧性警告用户体验

当用户手动编辑上游产物时：

```
$ /opsx:apply

⚠️  检测到上游产物的变更：
    - design.md 在 5 分钟前被修改（在 tasks.md 生成之后）

选项：
1. 重新生成任务（推荐）
2. 使用当前任务继续
3. 取消

>
```

### 第 2 部分：重新生成能力

添加重新生成特定产物的方式：

```bash
# 选项 A：在 continue 上添加标志
/opsx:continue --regenerate tasks

# 选项 B：单独的命令
/opsx:regenerate tasks

# 选项 C：检测到陈旧时的交互式提示
/opsx:apply
# "设计已变更。重新生成任务？[y/N]"
```

## 技术方案

### 选项 A：元数据文件
在变更目录中存储 `.openspec-meta.json`：
```json
{
  "tasks.md": {
    "generated_at": "2025-01-24T10:00:00Z",
    "dependencies": {
      "design.md": "2025-01-24T09:55:00Z",
      "specs/feature/spec.md": "2025-01-24T09:50:00Z"
    }
  }
}
```

### 选项 B：Frontmatter
向生成的产物添加 YAML frontmatter：
```markdown
---
generated_at: 2025-01-24T10:00:00Z
depends_on:
  - design.md@2025-01-24T09:55:00Z
---
# 任务
...
```

### 选项 C：基于 Git
使用 git 检测自下游文件最后修改以来上游文件是否已变更。无需额外元数据，但需要 git。

## 非目标

- 自动重新生成（用户应始终选择）
- 完全阻止 apply（仅警告）
- 跟踪代码文件变更（仅产物依赖）

## 依赖

- 应在 `fix-midflight-update-docs` 之后实现，以便文档先准确
- 如果需要，可与该变更合并

## 成功标准

- 用户在应用陈旧产物时收到警告
- 如有需要，有清晰的重新生成路径
- 无误报（仅在真正陈旧时警告）
- 文档中的声明变为实际可行
