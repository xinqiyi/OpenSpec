## 新增需求

### 需求：堆叠元数据模型
系统应支持活跃变更上的可选元数据，以表达排序和分解关系。

#### 场景：存在可选的堆叠元数据
- **当** 变更包含堆叠元数据字段
- **那么** 系统应解析并暴露 `dependsOn`、`provides`、`requires`、`touches` 和 `parent`
- **并且** 验证应强制规范化的字段形状和值类型（`dependsOn`/`provides`/`requires`/`touches` 为字符串数组，`parent` 在存在时为字符串）

#### 场景：无堆叠元数据的向后兼容性
- **当** 变更不包含堆叠元数据
- **那么** 现有行为应继续运行而无需迁移步骤
- **并且** 验证不应仅因堆叠元数据缺失而失败

### 需求：变更依赖图谱
系统应为活跃变更提供依赖感知的排序。

#### 场景：构建依赖顺序
- **当** 用户请求堆叠规划输出
- **那么** 系统应计算跨活跃变更的依赖图谱
- **并且** 应为未阻塞的变更返回确定性的拓扑顺序

#### 场景：相同依赖深度内的断链
- **当** 多个未阻塞变更共享相同的拓扑依赖深度
- **那么** 排序应按变更 ID 的字典序断链
- **并且** 对相同输入重复运行应返回相同的顺序

#### 场景：依赖循环检测
- **当** 活跃变更包含依赖循环
- **那么** 验证应在归档或排序操作进行之前失败，并显示循环详情
- **并且** 输出应包含打破循环的可操作指导

### 需求：能力标记和重叠语义
系统应将能力标记视为验证契约，将 `touches` 视为建议性的重叠信号。

#### 场景：活跃变更提供所需的能力
- **当** 变更 B 声明 `requires` 标记 `X`
- **并且** 活跃变更 A 声明 `provides` 标记 `X`
- **那么** 验证应要求 B 在 `dependsOn` 中声明对至少一个 `X` 的活跃提供者的显式排序边
- **并且** 如果未声明显式依赖，验证应失败

#### 场景：没有活跃提供者的 Requires 标记
- **当** 变更声明 `requires` 标记
- **并且** 没有活跃变更声明对应的 `provides` 标记
- **那么** 验证不应推断隐式依赖边
- **并且** 排序应继续仅由显式 `dependsOn` 关系决定

#### 场景：归档历史满足 Requires 标记
- **当** 变更声明 `requires` 标记
- **并且** 没有活跃变更提供该标记
- **并且** 历史中至少有一个归档变更提供了该标记
- **那么** 验证不应仅因缺少提供者而发出警告
- **并且** 应继续使用显式 `dependsOn` 进行活跃排序

#### 场景：完整历史中缺失 Requires 标记
- **当** 变更声明 `requires` 标记
- **并且** 历史中没有活跃或归档的变更提供该标记
- **那么** 验证应发出非阻塞警告，指出变更和缺失的标记
- **并且** 不应推断隐式依赖边

#### 场景：共享 touches 的重叠警告
- **当** 多个活跃变更声明重叠的 `touches` 值
- **那么** 验证应发出警告，列出重叠的变更和触及的区域
- **并且** 验证不应仅因重叠而失败
