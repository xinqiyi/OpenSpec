## 上下文

OpenSpec 目前假定大多数生成的构件为项目本地安装，Codex 命令提示是主要的全局例外。这种混合模型可行，但它是隐式的且不可由用户配置。

请求的变更是支持用户可选择的工具 skill/命令安装范围（`global` 或 `project`），新配置默认使用 `global`，同时在显式迁移之前保留旧的项目本地行为。

## 目标 / 非目标

**目标：**

- 提供一个单一的范围偏好，用户可以全局设置并每次运行覆盖
- 新用户默认使用 `global` 范围
- 使安装路径解析跨工具/界面具有确定性和显式性
- 保留尚未定义 `installScope` 的旧配置文件用户的当前行为
- 避免静默的部分安装；在输出中显示有效范围决策

**非目标：**

- 实现全局设置的项目本地配置文件支持
- 为上游位置约定未知的工具定义全局安装路径
- 在此变更中更改 workflow/配置文件语义（`core`、`custom`、`delivery`）

## 决策

### 1. 全局配置中的范围模型

向全局配置添加安装范围偏好：

```ts
type InstallScope = 'global' | 'project';

interface GlobalConfig {
 // 现有字段...
 installScope?: InstallScope;
}
```

默认值：

- 新配置应显式写入 `installScope: global`。
- 没有此字段的现有配置通过架构演进安全加载，并应解析有效默认值为 `project`，直到用户显式设置 `installScope`。

### 2. 显式工具范围支持元数据

扩展 `AI_TOOLS` 元数据，为每个界面添加可选的范围支持声明：

```ts
interface ToolInstallScopeSupport {
 skills?: InstallScope[];
 commands?: InstallScope[];
}
```

解析规则：

1. 如果工具界面缺少范围支持元数据，出于保守的向后兼容性，将其视为仅项目支持。
2. 尝试首选范围。
3. 如果不支持，在支持时使用替代范围。
4. 如果两者都不支持，以可操作的错误失败。

这使得在保持对仅支持项目本地路径的工具安全的同时，实现默认全局行为。

### 3. 能感知范围的安装目标解析器

引入共享的解析器工具，用于计算以下的有效目标路径：

- skill 根目录
- 命令输出文件

解析器输入：

- 工具 ID
- 请求的范围
- 项目根目录
- 环境上下文（`CODEX_HOME` 等）

解析器输出：

- 每个界面的有效范围
- 具体的目标路径
- 面向用户输出的可选回退原因

平台行为：

- 解析器输出具有 OS 感知能力，并为当前平台 spec 化。
- Windows 全局目标必须使用 Windows 路径约定（例如，当 `CODEX_HOME` 未设置时，Codex 的 `%USERPROFILE%\.codex\prompts` 回退），而不是 POSIX 默认值。

### 4. 能感知上下文的命令适配器路径

更新命令生成合约，使适配器接收用于路径解析的安装上下文。这避免了硬编码的绝对/相对假设，并集中了范围决策。

示例方向：

```ts
getFilePath(commandId: string, context: InstallContext): string
```

### 5. CLI 行为和 UX

`init`：

- 默认使用配置的安装范围；如果在旧配置中缺失，使用迁移安全的有效默认值（`project`）。
- 支持显式覆盖标志（`--scope global|project`）。
- 在交互 schema 下，在写入文件之前显示所选范围和任何每个工具的回退决策。

`update`：

- 应用当前范围偏好（或覆盖）；如果在旧配置中缺失，使用迁移安全的有效默认值（`project`）。
- 使用有效的作用域路径和上次应用的范围状态执行漂移检测。
- 在摘要输出中报告有效范围决策。

`config`：

- `openspec config profile` 交互流程包括安装范围选择。
- `openspec config list` 显示 `installScope` 及其来源注释（`explicit`、`new-default` 或 `legacy-default`）。

### 6. 范围更改时的清理安全

当范围更改时：

- 写入发生在新的有效目标中。
- 清理/移除仅限于相关工具/workflow ID 的 OpenSpec 托管文件。
- 输出明确说明哪些范围位置已更新，哪些已清理。

### 7. 范围漂移状态跟踪

在项目托管状态中跟踪每个工具/界面上次成功的有效范围。

规则：

1. 当当前解析的范围与已配置工具/界面的上次成功范围不同时，检测到漂移。
2. 在任何写入开始之前，必须验证所有已配置工具/界面的范围支持。
3. 更新首先写入新解析的目标，验证完整性，然后移除先前目标上的托管文件。
4. 如果新目标写入部分完成或验证失败，命令应中止旧目标清理并报告可操作的失败，附有不完整/新路径和保留/旧路径。
5. 清理失败不回滚新写入；命令返回可操作的失败，附带需要解决的剩余路径。

### 8. 与命令界面能力更改的协调

如果 `add-tool-command-surface-capabilities` 落地，planning 逻辑必须一起评估范围解析和交付/能力行为（范围 x 交付 x 命令界面）。

## 风险 / 权衡

**风险：跨项目共享全局状态**
全局安装在项目之间共享。从一个项目更新全局构件会影响使用该工具范围的所有项目。
-> 缓解措施：在输出中明确范围；保持配置文件/交付是全局的和确定性的。

**风险：工具特定的未知全局约定**
并非所有工具都记录了稳定的全局安装位置。
-> 缓解措施：使用显式的范围支持元数据；回退或失败而不是猜测。

**风险：适配器 API 变动**
更改适配器路径合约会影响许多文件/测试。
-> 缓解措施：在一次通过中迁移，并附有适配器合约测试和现有的端到端生成测试。

## 推出计划

1. 添加安装范围的配置架构 + 默认值。
2. 添加工具范围能力元数据和解析器工具。
3. 升级命令适配器合约和生成器路径管道。
4. 将能感知范围的行为集成到 init/update 中。
5. 添加文档和测试覆盖。
