# OpenSpec 约定规范

## 目的

OpenSpec 约定应定义系统能力如何文档化、变更如何提议和跟踪，以及规范如何随时间演进。此元规范作为 OpenSpec 自身约定的真实来源。

## 核心原则

系统应遵循以下原则：
- 规范反映当前已构建和部署的内容
- 变更包含应修改内容的建议
- AI 驱动文档流程
- 规范是与已部署代码保持同步的活文档

## 目录结构

当 OpenSpec 项目被初始化
则它应具有以下结构：
```
openspec/
├── project.md              # 项目特定上下文
├── README.md               # AI 助手指令
├── specs/                  # 当前已部署的能力
│   └── [capability]/       # 单一、专注的能力
│       ├── spec.md         # 是什么和为什么
│       └── design.md       # 怎么做（可选，用于已建立的模式）
└── changes/                # 提议的变更
    ├── [change-name]/      # 描述性变更标识符
    │   ├── proposal.md     # 原因、内容和影响
    │   ├── tasks.md        # 实现清单
    │   ├── design.md       # 技术决策（可选）
    │   └── specs/          # 完整的未来状态
    │       └── [capability]/
    │           └── spec.md # 纯 Markdown（无差异语法）
    └── archive/            # 已完成的变更
        └── YYYY-MM-DD-[name]/
```

## 变更存储约定

### 未来状态存储

当创建变更提案时
则存储受影响规范的完整未来状态
并且使用纯 Markdown，无需差异语法

`changes/[name]/specs/` 目录应包含：
- 变更后规范将存在的完整规范文件
- 不带 `+` 或 `-` 前缀的纯 Markdown
- 最终预期状态的所有格式和结构

### 提案格式

当文档化变更内容时
则提案应显式描述每个变更：

```markdown
**[章节或行为名称]**
- 从： [当前状态/需求]
- 到： [未来状态/需求]
- 原因： [为何需要此变更]
- 影响： [破坏性/非破坏性，谁受影响]
```

这种显式格式弥补了没有内联差异的不足，确保审查者准确理解将变更的内容。

## 变更生命周期

变更流程应遵循以下状态：

1. **提议**：AI 使用未来状态规范和显式提案创建变更
2. **审查**：人类审查提案和未来状态
3. **批准**：变更被批准实施
4. **实现**：遵循 tasks.md 清单（可跨多个 PR）
5. **部署**：变更部署到生产环境
6. **更新**：`specs/` 中的规范更新以匹配已部署的现实
7. **归档**：变更移至 `archive/YYYY-MM-DD-[name]/`

## 查看变更

当审查提议的变更时
审查者可以使用以下方式进行比较：
- 提交变更时的 GitHub PR 差异视图
- 命令行：`diff -u specs/[capability]/spec.md changes/[name]/specs/[capability]/spec.md`
- 任何比较当前状态与未来状态的视觉差异工具

系统依赖工具生成差异而非存储它们。

## 能力命名

能力应使用：
- 动词-名词模式（例如 `user-auth`、`payment-capture`）
- 连字符小写名称
- 单一关注点（每个能力一个职责）
- 无嵌套（`specs/` 下的扁平结构）

## 何时变更需要提案

以下情况应创建提案：
- 新功能或能力
- 对现有行为的破坏性变更
- 架构或模式变更
- 改变行为的性能优化
- 影响访问模式的安全更新

以下情况不需要提案：
- 恢复预期行为的错误修复
- 拼写错误或格式修复
- 非破坏性依赖更新
- 为现有行为添加测试
- 文档澄清

## 为何采用此方法

清晰的未来状态存储提供：
- **可读性**：无差异语法污染
- **AI 兼容性**：AI 工具可理解的标准 Markdown
- **简单性**：无需特殊解析或处理
- **工具无关**：任何差异工具均可显示变更
- **清晰意图**：显式提案记录推理过程
