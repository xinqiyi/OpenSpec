# OpenSpec 使用说明

本文档为 AI 编程助手提供如何使用 OpenSpec spec 进行 spec 驱动开发的说明。在启用 OpenSpec 的项目中工作时，请精确遵循以下规则。

## 核心原则

OpenSpec 是一个面向 AI 原生的变更驱动开发系统，其中：
- **spec**（`specs/`）反映当前已构建和部署的内容
- **变更**（`changes/`）包含关于应该变更的内容的 proposal
- **AI 驱动流程** - 你生成 proposal，人类审查和批准
- **spec 是活文档** - 始终与已部署的代码保持同步

## 从简开始

**默认采用最小实现：**
- 新功能最初应少于 100 行代码
- 使用最简单的可行方案
- 避免过早优化（无缓存、并行化或在未证明需要之前使用复杂 schema）
- 选择成熟技术而非前沿方案

**复杂性触发条件** - 仅在以下情况下增加复杂性：
- **性能数据** 显示当前方案太慢
- **规模要求** 有具体数字（超过 1000 用户、超过 100MB 数据）
- **多个用例** 需要相同的抽象
- **监管合规性** 要求特定 schema
- **安全威胁** 简单方案无法解决

当触发时，在你的变更 proposal 中记录具体的理由。

## 目录结构

```
openspec/
├── project.md # 项目特定上下文（技术栈、约定）
├── README.md # 本文件 - OpenSpec 使用说明
├── specs/ # 当前真实状态 - 已构建的内容
│ ├── [能力]/
│ │ ├── spec.md # 该能力做什么以及为什么
│ │ └── design.md # 如何构建（既定 schema）
│ └── ...
├── changes/ # 提议的变更 - 我们正在变更的内容
│ ├── [变更名称]/
│ │ ├── proposal.md # 为什么、什么、影响（整合）
│ │ ├── tasks.md # 实施检查清单
│ │ ├── design.md # 技术决策（可选，用于复杂变更）
│ │ └── specs/ # 受影响 spec 的未来状态
│ │ └── [能力]/
│ │ └── spec.md # 纯 Markdown（无差异语法）
│ └── archive/ # 已完成的变更（按日期 archive）
```

### 能力组织

**使用能力而非功能** - `specs/` 下的每个目录代表一个单一的、专注的职责：
- **动词-名词命名**：`user-auth`、`payment-capture`、`order-checkout`
- **10 分钟规则**：每个能力应在 10 分钟内能被理解
- **单一目的**：如果需要用"和"来描述，就拆分它

示例：
```
✅ 好的：user-auth、user-sessions、payment-capture、payment-refunds
❌ 差的：users、payments、core、misc
```

## 关键行为规则

### 1. 始终从阅读开始

在任何任务之前：
1. **阅读相关 spec** `specs/[能力]/spec.md` 以了解当前状态
2. **检查待处理的变更** `changes/` 目录中的潜在冲突
3. **阅读 project.md** 了解项目特定约定

### 2. 何时创建变更 proposal

**始终为以下情况创建变更 proposal：**
- 新功能或新特性
- 破坏性变更（API 变更、架构更新）
- 架构变更或新 schema
- 改变行为的性能优化
- 影响认证/访问 schema 的安全更新
- 需要多步骤或影响多个系统的任何变更

**跳过 proposal 的情况：**
- 恢复预期行为的 Bug 修复
- 拼写错误、格式或注释更新
- 依赖更新（除非是破坏性的）
- 配置或环境变量变更
- 为现有行为添加测试
- 文档修复

**复杂性评估：**
- 如果你的方案需要超过 100 行新代码，请说明复杂性理由
- 如果添加依赖、框架或架构 schema，请记录为什么更简单的替代方案不可行
- 默认采用单文件实现，直到证明不够用

### 3. 创建变更 proposal

当用户请求重大变更时：

```bash
# 1. 创建变更目录
openspec/changes/[描述性名称]/

# 2. 生成包含所有上下文的 proposal.md
## 为什么
[1-2 句话说明问题/机会]

## 什么变更 
[变更列表，包括破坏性变更]

## 影响
- 受影响的 spec：[列出将变更的能力]
- 受影响的代码：[列出关键文件/系统]

# 3. 为所有受影响的能力创建未来状态 spec
# - 存储变更后完整的 spec 文件
# - 使用纯 Markdown，无差异语法（+/- 前缀）
# - 包含最终预期状态的所有格式和结构
specs/
└── [能力]/
 └── spec.md

# 4. 创建包含实施步骤的 tasks.md
## 1. [任务组]
- [ ] 1.1 [具体任务]
- [ ] 1.2 [具体任务]

# 5. 对于复杂变更，添加 design.md
[技术决策和权衡]
```

### 4. 变更生命周期

1. **提议** → 创建包含所有文档的变更目录
2. **审查** → 用户审查并批准 proposal
3. **实施** → 按照批准的 tasks.md 执行（可以是多个 PR）
4. **部署** → 用户确认部署
5. **更新 spec** → 将 specs/ 与新现实同步（如果变更影响系统能力）
6. **archive** → 移动到 `changes/archive/YYYY-MM-DD-[名称]/`

### 5. 实施变更

在实施已批准的变更时：
1. 精确遵循 tasks.md 检查清单
2. **在 tasks.md 中标记已完成的任务**（例如 `- [x] 1.1 任务已完成`）
3. 确保代码与提议的行为一致
4. 更新任何受影响的测试
5. **将变更保留在 `changes/` 目录中** - 不要在实施 PR 中 archive

**多个实施 PR：**
- 变更可以通过多个 PR 实施
- 每个 PR 应更新 tasks.md 以标记完成内容
- 不同的开发者可以处理不同的任务组
- 示例：PR #1 完成任务 1.1-1.3，PR #2 完成任务 2.1-2.4

### 6. 部署后更新 spec 和 archive

**在部署后创建单独的 PR**，该 PR：
1. 将变更移动到 `changes/archive/YYYY-MM-DD-[名称]/`
2. 更新 `specs/` 中的相关文件以反映新现实（如果需要）
3. 如果存在 design.md，将已验证的 schema 纳入 `specs/[能力]/design.md`

这确保了变更只有在真正完成并部署后才被 archive。

### 7. 不需要 spec 的类型变更

某些变更只影响开发基础设施，不需要 spec：
- 初始项目设置（package.json、tsconfig.json 等）
- 开发工具变更（linter、格式化工具、构建工具）
- CI/CD 配置
- 开发依赖

对于这些变更：
1. 实施 → 部署 → 标记任务完成 → archive
2. 完全跳过"更新 spec"步骤

### 什么值得有 spec？

问自己：
- 这是用户或其他系统交互的系统能力吗？
- 它有需要文档记录的持续行为吗？
- 新开发者是否需要理解这个才能使用系统？

如果全部为否 → 不需要 spec（可能只是工具/基础设施）

## 理解 spec 与代码

### spec 记录什么和为什么
```markdown
# 认证 spec

用户应使用邮箱和密码进行认证。

当凭据有效时，则签发 JWT 令牌。
当凭据无效时，则返回通用错误。

原因：防止用户枚举攻击。
```

### 代码记录如何做
```javascript
// 实现细节
const user = await db.users.findOne({ email });
const valid = await bcrypt.compare(password, user.hashedPassword);
```

**关键区别**：spec 捕获意图、约束和从代码中不易看出的决策。

## 常见场景

### 新功能请求
```
用户："添加密码重置功能"

你应该：
1. 阅读 specs/user-auth/spec.md
2. 检查 changes/ 中待处理的认证变更
3. 创建 changes/add-password-reset/ 及 proposal
4. 等待批准后再实施
```

### Bug 修复
```
用户："当 bio 为空时出现空指针错误"

你应该：
1. 检查 spec 是否说明 bio 是可选的
2. 如果是 → 直接修复（这是一个 bug）
3. 如果否 → 创建变更 proposal（这是行为变更）
```

### 基础设施设置
```
用户："初始化 TypeScript 项目"

你应该：
1. 为 TypeScript 设置创建变更 proposal
2. 实施配置文件（PR #1）
3. 在 tasks.md 中标记任务完成
4. 部署后，创建单独的 PR 进行 archive
 （无需更新 spec - 这是工具，不是能力）
```

## workflow 总结

1. **接收请求** → 确定是否需要变更 proposal
2. **读取当前状态** → 检查 spec 和待处理变更
3. **创建 proposal** → 生成完整的变更文档
4. **获取批准** → 用户审查 proposal
5. **实施** → 遵循已批准的任务，在 tasks.md 中标记完成项
6. **部署** → 用户部署实施
7. **archive PR** → 创建单独的 PR 以：
 - 将变更移至 archive
 - 根据需要更新 spec
 - 标记变更为完成

## PR workflow 示例

### 单一开发者，简单变更
```
PR #1：实施
- 实施所有任务
- 更新 tasks.md 标记完成项
- 合并并部署

PR #2：archive（部署后）
- 将 changes/feature-x/ 移至 changes/archive/2025-01-15-feature-x/
- 根据需要更新 spec
```

### 多个开发者，复杂变更
```
PR #1：Alice 实施认证组件
- 完成任务 1.1、1.2、1.3
- 更新 tasks.md 标记这些为完成

PR #2：Bob 实施 UI 组件 
- 完成任务 2.1、2.2
- 更新 tasks.md 标记这些为完成

PR #3：Alice 修复集成问题
- 完成剩余任务 1.4
- 更新 tasks.md

[部署所有变更]

PR #4：archive
- 移至 archive 并注明部署日期
- 更新 spec 以反映新的认证流程
```

### 关键规则
- **永远不要在实施 PR 中 archive** - 变更在部署前没有完成
- **始终更新 tasks.md** - 显示准确的进度
- **每个变更一个 archive PR** - 清晰的完成边界
- **archive PR 包含 spec 更新** - 保持 spec 最新

## 能力组织最佳实践

### 命名能力
- 使用 **动词-名词** schema：`user-auth`、`payment-capture`、`order-checkout`
- 要具体：`payment-capture` 而不是仅仅 `payments`
- 保持扁平：避免在能力内部嵌套能力
- 单一焦点：如果需要用"和"来描述，就拆分它

### 何时拆分能力
当你有以下情况时拆分：
- 多个不相关的 API 端点
- 不同的用户角色或参与者
- 独立的部署考虑
- 独立的演进路径

#### 能力边界指南
- 你会单独导入它们吗？→ 分为独立能力
- 不同的部署节奏？→ 分为独立能力
- 不同的团队拥有它们？→ 分为独立能力
- 共享数据模型可以，共享业务逻辑意味着合并

示例：
- user-auth（登录/登出）与 user-sessions（令牌管理）→ 分开
- payment-capture 与 payment-refunds → 分开（不同 workflow）
- user-profile 与 user-settings → 合并（相同数据模型，相同所有者）

### 横切关注点
对于系统级策略（限流、错误处理、安全），在以下位置记录：
- `project.md` 中的项目级约定
- 在适用能力的相关 spec 中
- 或者如果足够复杂，创建专用能力（例如 `api-rate-limiting/`）

### 组织良好的能力示例
```
specs/
├── user-auth/ # 登录、登出、密码重置
├── user-sessions/ # 令牌管理、刷新
├── user-profile/ # 个人资料 CRUD 操作
├── payment-capture/ # 处理支付
├── payment-refunds/ # 处理退款
└── order-checkout/ # 结账 workflow
```

详细指导请参阅[能力组织指南](../docs/capability-organization.md)。

## 常见场景和说明

### 决策模糊性：Bug 与行为变更

当 spec 缺失或模糊时：
- 如果不存在 spec → 将当前代码行为视为隐式 spec，需要 proposal
- 如果 spec 模糊 → 需要 proposal，在修复的同时澄清 spec
- 如果代码和 spec 不一致 → spec 是真理，代码有 Bug（无需 proposal 修复）
- 如果不确定 → 默认创建 proposal（更安全的选择）

示例：
```
用户："API 对缺失用户返回 404，但应该返回 400"
AI：这是 Bug（spec 说 400）还是行为变更（spec 说 404）？
```

### 当你不清楚范围时
可以先探索！告诉用户你需要调查，然后创建有依据的 proposal。

### 探索阶段（需要时）

在创建 proposal 之前，在以下情况下你可能需要探索：
- 用户请求模糊或高层
- 存在多种实施方案
- 不查看代码就无法确定范围

探索检查清单：
1. 告诉用户你需要先探索
2. 使用 Grep/Read 了解当前状态
3. 基于发现创建初步 proposal
4. 根据用户反馈完善

示例：
```
用户："添加缓存以提高性能"
AI："让我探索代码库以了解当前架构并确定缓存机会。"
[探索后]
AI："根据我的分析，我确定了三个缓存会有所帮助的领域。这是我的 proposal..."
```

### 当没有 spec 存在时
将当前代码视为隐式 spec。你的 proposal 应记录当前状态和提议的变更。

### 有疑问时
默认创建 proposal。跳过不必要的 proposal 比修复未记录的变更更容易。

### AI workflow 适配

使用 OpenSpec 进行任务跟踪：
- 将探索任务与实施任务分开记录
- 边进行边记录 proposal 创建步骤
- 在 proposal 批准前保持实施任务独立

鼓励并行操作：
- 同时阅读多个 spec
- 同时检查多个待处理变更
- 批量进行相关搜索以提高效率

进度沟通：
- "正在探索代码库以了解范围..."
- "正在基于发现创建 proposal..."
- "正在实施已批准的变更..."

### 对于 AI 助手
- **倾向于简单** - 提出可行的最小方案
- 在提议前充分利用你的探索工具
- 批量操作以提高效率
- 沟通你的进度
- 根据发现修订 proposal 是可以的
- **质疑复杂性** - 如果你的方案感觉复杂，先简化

## 边缘情况处理

### 多能力变更
创建一个 proposal，该 proposal：
- 列出所有受影响的能力
- 显示每个能力的变更
- 具有统一的任务列表
- 作为一个整体获得批准

### 过时的 spec
如果 spec 明显过时：
1. 创建 proposal 以更新 spec 以匹配现实
2. 在单独的 proposal 中实施新功能
3. 或者在一个 proposal 中结合两者，使用清晰的部分

### 紧急热修复
对于关键生产问题：
1. 宣布："这是一个紧急修复"
2. 立即实施修复
3. 创建追溯性 proposal
4. 部署后更新 spec
5. 在 archive 中标记为 [紧急]

### 纯重构
以下情况不需要 proposal：
- 代码格式化/样式
- 内部重构（相同 API）
- 性能优化（相同行为）
- 为未类型化的代码添加类型

以下情况需要 proposal：
- API 变更（即使是兼容的）
- 数据库架构变更
- 架构变更
- 新依赖

### 可观测性添加
以下情况不需要 proposal：
- 添加日志语句
- 新指标/追踪
- 调试添加
- 错误追踪

以下情况需要 proposal：
- 更改日志格式/结构
- 添加新的监控服务
- 更改记录的内容（隐私）

## 记住

- 你是流程驱动者 - 自动处理文档负担
- spec 必须始终反映部署的现实
- 变更是提议的，不是强加的
- 影响分析防止意外
- **简单即力量** - 只是 Markdown 文件，最小方案
- 从简单开始，只在有理由时增加复杂性

通过遵循这些约定，你能够实现真正的 spec 驱动开发，其中文档保持最新，变更可追溯，演进是有意为之的。
