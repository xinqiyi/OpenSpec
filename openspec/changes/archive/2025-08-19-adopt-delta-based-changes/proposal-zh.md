# 采用基于 Delta 的规范变更

## 原因

当前在变更提案中存储完整未来状态的方法造成了糟糕的审查体验。在 GitHub 上审查变更时，审查者看到整个规范文件（通常超过 100 行）以绿色显示为"新增"，使得无法识别实际变更的内容。随着最近结构化格式的采用，我们现在有了清晰的章节边界，可以支持更好的方法：仅存储新增和修改。

## 变更内容

仅存储实际变更的需求，而不是完整的未来状态：

- **ADDED（新增）需求**：正在引入的新能力
- **MODIFIED（修改）需求**：正在修改的现有需求（必须匹配当前标题）
- **REMOVED（移除）需求**：已弃用的能力
- **RENAMED（重命名）需求**：显式的标题变更（例如，`FROM: 旧名称` → `TO: 新名称`）

归档命令将使用规范化标题匹配（修剪首尾空白）以编程方式应用这些 delta，而不是手动复制整个文件。

## 影响范围

**受影响的规范**：openspec-conventions、cli-archive、cli-diff

**好处**：
- GitHub diff 仅显示实际变更（25 行而不是 150+ 行）
- 审查者立即看到新增、修改或移除了什么
- 当两个变更修改同一需求时，冲突更加明显
- 归档命令可以编程方式应用变更

**格式**：仅 delta 格式 - 所有变更必须使用 ADDED/MODIFIED/REMOVED 部分。

## 示例

不再存储 150 行的完整未来规范，而是仅存储：

```markdown
# 用户认证 - 变更

## ADDED（新增）需求

### Requirement: OAuth 支持
用户应通过 OAuth 提供商（包括 Google 和 GitHub）进行认证。

#### Scenario: OAuth 登录流程
- **当** 用户选择 OAuth 提供商
- **那么** 重定向到提供商授权
- **并且** 交换授权码获取令牌

## MODIFIED（修改）需求

### Requirement: 会话管理
会话应在 30 分钟不活动后过期。

#### Scenario: 不活动会话超时
- **当** 无活动达 30 分钟 ←（原为 60 分钟）
- **那么** 使会话令牌失效
- **并且** 要求重新认证

## RENAMED（重命名）需求
- FROM: `### Requirement: 基础认证`
- TO: `### Requirement: 邮箱认证`
```

这使得审查聚焦，变更显式明确。

## 冲突解决

当两个变更修改同一需求标题时，Git 自然检测冲突。这实际上比完整状态存储更好，因为后者 Git 可能会静默合并不兼容的变更。

## 决策和产品指南

为保持归档流程精简和可预测，适用以下决策：

- **新规范创建**：当目标规范不存在时，自动生成最小骨架并仅插入 ADDED 需求。骨架格式：
  - `# [规范名称] 规范`
  - `## 目的`，包含占位符："TBD — created by archiving change [change-name]. Update Purpose after archive."
  - `## 需求`
  - 如果不存在的规范包含 MODIFIED/REMOVED/RENAMED，则中止并提示先仅通过 ADDED 创建。

- **需求标识**：通过精确的标题 `### Requirement: [Name]` 匹配需求，使用仅修剪的规范化和大小写敏感比较。使用需求块提取器，保留精确标题并捕获完整内容（包括场景），同时适用于主规范和 delta 文件。

- **应用顺序和原子性**：按 RENAMED → REMOVED → MODIFIED → ADDED 顺序应用 delta。首先验证所有操作，在内存中应用，然后每个规范写入一次。任何验证失败时，中止且不写入部分结果。在所有规范上显示汇总总计行：`Totals: + A, ~ M, - R, → N`。

- **验证矩阵**：强制要求 MODIFIED/REMOVED 存在；ADDED 不存在；RENAMED 的 FROM 存在且 TO 不存在；所有操作后无重复；无跨部分冲突（例如，同一项同时出现在 MODIFIED 和 REMOVED 中）。当重命名和修改应用于同一项时，MODIFIED 必须引用新标题。

- **幂等性**：保持 v1 简单。前提条件失败时中止（例如，ADDED 已存在）并给出清晰错误。v1 中不实现无操作检测。

- **输出和用户体验**：对每个规范，使用标准符号 `+ ~ - →` 显示操作计数。可选地在末尾包含一个简短的汇总总计行。保持消息简洁和可操作。

- **错误消息**：标准化消息为 `[spec] [operation] failed for header "### Requirement: X" — reason`。中止时，显式声明：`Aborted. No files were changed.`

- **子章节**：需求下的任何子章节（例如 `#### Scenario: ...`）在解析和应用期间逐字保留。

- **向后兼容**：拒绝现有规范的完整未来状态规范副本，并指导转换为 deltas。允许全新规范通过上述骨架使用仅 ADDED 的 delta 创建。

- **Dry-run**：推迟到 v1 以后，以保持范围最小化。
