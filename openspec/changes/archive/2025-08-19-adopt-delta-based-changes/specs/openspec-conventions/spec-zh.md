# OpenSpec 约定 - 变更

## 已修改的需求

### 需求：基于标题的需求标识

需求标题应当作为唯一标识符，用于当前 spec 与提议变更之间的程序化匹配。

#### 场景：以编程方式匹配需求

- **WHEN** 处理 delta 变更时
- **THEN** 使用 `### 需求：[名称]` 标题作为唯一标识符
- **AND** 使用 spec 化标题进行匹配：`normalize(header) = trim(header)`
- **AND** spec 化后以大小写敏感的方式比较标题

#### 场景：处理需求重命名

- **WHEN** 重命名一个需求时
- **THEN** 使用专门的 `## 已重命名的需求` 章节
- **AND** 明确指定新旧名称：
 ```markdown
 ## 已重命名的需求
 - 从：`### 需求：旧名称`
 - 到：`### 需求：新名称`
 ```
- **AND** 如果内容也发生变化，使用新标题将其包含在已修改部分

#### 场景：验证标题唯一性

- **WHEN** 创建或修改需求时
- **THEN** 确保 spec 内不存在重复标题
- **AND** 验证工具应将重复标题标记为错误

### 需求：变更存储约定

变更 proposal 应仅存储对 spec 的增补、修改和删除，而非完整的未来状态。

#### 场景：创建带有增补的变更 proposal

- **WHEN** 创建添加新需求的变更 proposal 时
- **THEN** 仅将新需求放在 `## 新增的需求` 下
- **AND** 每个需求应包含其完整内容
- **AND** 使用标准的结构化格式编写需求和场景

#### 场景：创建带有修改的变更 proposal

- **WHEN** 创建修改现有需求的变更 proposal 时
- **THEN** 将修改后的需求放在 `## 已修改的需求` 下
- **AND** 使用与当前 spec 相同的标题文本（spec 化后）
- **AND** 包含完整的修改后需求（而非差异对比）
- **AND** 可选择使用内联注释标注更改内容，如 `← (原为 X)`

#### 场景：创建带有删除的变更 proposal

- **WHEN** 创建删除需求的变更 proposal 时
- **THEN** 将其列在 `## 已删除的需求` 下
- **AND** 使用 spec 化标题文本进行标识
- **AND** 说明删除原因
- **AND** 如适用，记录迁移路径


`changes/[name]/specs/` 目录应包含：
- 仅显示变更内容的 delta 文件
- 新增、已修改、已删除和已重命名需求的章节
- 用于需求标识的 spec 化标题匹配
- 使用结构化格式的完整需求
- 每个需求变更类型的明确指示

#### 场景：使用标准输出符号

- **WHEN** 在 CLI 输出中显示 delta 操作时
- **THEN** 使用以下标准符号：
 - `+` 表示新增（绿色）
 - `~` 表示已修改（黄色）
 - `-` 表示已删除（红色）
 - `→` 表示已重命名（青色）

### 需求：archive 流程增强

archive 流程应使用基于标题的匹配，以编程方式将 delta 变更应用到当前 spec。

#### 场景：使用 delta archive 变更

- **WHEN** archive 已完成的变更时
- **THEN** archive 命令应：
 1. 首先解析已重命名章节并应用重命名
 2. 解析已删除章节，通过 spec 化标题匹配进行删除
 3. 解析已修改章节，通过 spec 化标题匹配进行替换（如已重命名则使用新名称）
 4. 解析新增章节并追加新需求
- **AND** 验证所有已修改/已删除的标题在当前 spec 中存在
- **AND** 验证新增标题不存在重复
- **AND** 在主要 specs/ 目录中生成更新后的 spec

#### 场景：处理 archive 期间的冲突

- **WHEN** delta 变更与当前 spec 状态冲突时
- **THEN** archive 命令应报告具体的冲突
- **AND** 要求手动解决后方可继续
- **AND** 提供解决冲突的明确指导
