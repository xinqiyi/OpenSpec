# OpenSpec 约定 - 变更

## 已修改的需求

### 需求：基于标题的需求标识

需求标题应当作为唯一标识符，用于当前规范与提议变更之间的程序化匹配。

#### 场景：以编程方式匹配需求

- **当** 处理增量变更时
- **则** 使用 `### 需求：[名称]` 标题作为唯一标识符
- **并且** 使用规范化标题进行匹配：`normalize(header) = trim(header)`
- **并且** 规范化后以大小写敏感的方式比较标题

#### 场景：处理需求重命名

- **当** 重命名一个需求时
- **则** 使用专门的 `## 已重命名的需求` 章节
- **并且** 明确指定新旧名称：
  ```markdown
  ## 已重命名的需求
  - 从：`### 需求：旧名称`
  - 到：`### 需求：新名称`
  ```
- **并且** 如果内容也发生变化，使用新标题将其包含在已修改部分

#### 场景：验证标题唯一性

- **当** 创建或修改需求时
- **则** 确保规范内不存在重复标题
- **并且** 验证工具应将重复标题标记为错误

### 需求：变更存储约定

变更提案应仅存储对规范的增补、修改和删除，而非完整的未来状态。

#### 场景：创建带有增补的变更提案

- **当** 创建添加新需求的变更提案时
- **则** 仅将新需求放在 `## 新增的需求` 下
- **并且** 每个需求应包含其完整内容
- **并且** 使用标准的结构化格式编写需求和场景

#### 场景：创建带有修改的变更提案

- **当** 创建修改现有需求的变更提案时
- **则** 将修改后的需求放在 `## 已修改的需求` 下
- **并且** 使用与当前规范相同的标题文本（规范化后）
- **并且** 包含完整的修改后需求（而非差异对比）
- **并且** 可选择使用内联注释标注更改内容，如 `← (原为 X)`

#### 场景：创建带有删除的变更提案

- **当** 创建删除需求的变更提案时
- **则** 将其列在 `## 已删除的需求` 下
- **并且** 使用规范化标题文本进行标识
- **并且** 说明删除原因
- **并且** 如适用，记录迁移路径


`changes/[name]/specs/` 目录应包含：
- 仅显示变更内容的增量文件
- 新增、已修改、已删除和已重命名需求的章节
- 用于需求标识的规范化标题匹配
- 使用结构化格式的完整需求
- 每个需求变更类型的明确指示

#### 场景：使用标准输出符号

- **当** 在 CLI 输出中显示增量操作时
- **则** 使用以下标准符号：
  - `+` 表示新增（绿色）
  - `~` 表示已修改（黄色）
  - `-` 表示已删除（红色）
  - `→` 表示已重命名（青色）

### 需求：归档流程增强

归档流程应使用基于标题的匹配，以编程方式将增量变更应用到当前规范。

#### 场景：使用增量归档变更

- **当** 归档已完成的变更时
- **则** 归档命令应：
  1. 首先解析已重命名章节并应用重命名
  2. 解析已删除章节，通过规范化标题匹配进行删除
  3. 解析已修改章节，通过规范化标题匹配进行替换（如已重命名则使用新名称）
  4. 解析新增章节并追加新需求
- **并且** 验证所有已修改/已删除的标题在当前规范中存在
- **并且** 验证新增标题不存在重复
- **并且** 在主要 specs/ 目录中生成更新后的规范

#### 场景：处理归档期间的冲突

- **当** 增量变更与当前规范状态冲突时
- **则** 归档命令应报告具体的冲突
- **并且** 要求手动解决后方可继续
- **并且** 提供解决冲突的明确指导
