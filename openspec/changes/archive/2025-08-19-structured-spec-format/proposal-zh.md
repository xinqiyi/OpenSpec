## 为什么

OpenSpec spec 缺乏一致的结构，使得各部分在不同 spec 之间无法通过视觉识别和程序化解析。这使得维护一致性和构建工具变得更加困难。

## 变更内容

**spec 格式部分**
- 从：对 spec 没有正式的结构要求
- 到：使用 `### Requirement:` 和 `#### Scenario:` 标题的结构化格式
- 原因：所有 spec 之间的视觉一致性和可解析性
- 影响：非破坏性 - 现有 spec 可以逐步迁移

**关键字格式化**
- 从：WHEN/THEN/AND 关键字使用不一致
- 到：场景要点中使用粗体关键字（**WHEN** 、**THEN** 、**AND** ）
- 原因：改进的可读性和一致的视觉层次
- 影响：非破坏性 - 仅格式化增强

**格式灵活性**
- 从：隐含理解不同内容需要不同格式
- 到：明确允许替代格式（OpenAPI、JSON Schema 等）
- 原因：解决并非所有 spec 都符合需求/场景 schema 的担忧
- 影响：非破坏性 - 澄清现有实践

**迁移指南**
- 从：没有迁移指导
- 到：记录渐进式迁移方法
- 原因：允许 delta 采用而不干扰现有 spec
- 影响：非破坏性 - 在修改 spec 时选择性地迁移

## 影响

- 受影响的 spec：openspec-conventions（对现有能力的增强）
- 受影响的代码：最初没有 - 这是文档标准的增强
- 迁移：渐进式 - 现有 spec 在修改时迁移
- 工具：支持未来的解析工具但不要求它们
