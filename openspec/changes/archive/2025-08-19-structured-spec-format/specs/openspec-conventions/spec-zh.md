# OpenSpec 约定规范

## 新增需求

### 需求：采用结构化格式

行为规范应采用结构化格式，默认使用 `### Requirement:` 和 `#### Scenario:` 标题。

#### 场景：对行为使用结构化标题

- **WHEN** 记录行为需求
- **THEN** 使用 `### Requirement:` 表示需求
- **AND** 使用 `#### Scenario:` 表示场景，并加粗 WHEN/THEN/AND 关键词

## 目的

OpenSpec 约定应定义系统能力如何记录、变更如何提议和跟踪，以及规范如何随时间演变。此元规范作为 OpenSpec 自身约定的真相来源。

## 核心原则

系统应遵循以下原则：
- 规范反映当前已构建和已部署的内容
- 变更包含应更改内容的提案
- AI 驱动文档编写过程
- 规范是与部署代码保持同步的活文档

## 目录结构

WHEN 一个 OpenSpec 项目被初始化
THEN 它应具有以下结构：
```
openspec/
├── project.md              # 项目特定上下文
├── README.md               # AI 助手说明
├── specs/                  # 当前已部署的能力
│   └── [capability]/       # 单一、专注的能力
│       ├── spec.md         # 什么和为什么
│       └── design.md       # 如何（可选，适用于既定模式）
└── changes/                # 提议的变更
    ├── [change-name]/      # 描述性变更标识符
    │   ├── proposal.md     # 为什么、什么和影响
    │   ├── tasks.md        # 实现检查清单
    │   ├── design.md       # 技术决策（可选）
    │   └── specs/          # 完整的未来状态
    │       └── [capability]/
    │           └── spec.md # 干净 markdown（无差异语法）
    └── archive/            # 已完成的变更
        └── YYYY-MM-DD-[name]/
```

## 规范格式

### 需求：行为规范的结构化格式

行为规范应使用一致的部分标题和关键词的结构化格式，以确保视觉一致性和可解析性。

#### 场景：编写需求部分

- **WHEN** 在行为规范中记录需求
- **THEN** 使用三级标题，格式为 `### Requirement: [名称]`
- **AND** 紧跟描述核心行为的 SHALL 语句
- **AND** 保持需求名称描述性且不超过 50 个字符

#### 场景：记录场景

- **WHEN** 记录特定行为或用例
- **THEN** 使用四级标题，格式为 `#### Scenario: [描述]`
- **AND** 使用带加粗关键词的要点表示步骤：
  - **GIVEN** 用于初始状态（可选）
  - **WHEN** 用于条件或触发条件
  - **THEN** 用于预期结果
  - **AND** 用于额外结果或条件

#### 场景：添加实现细节

- **WHEN** 一个步骤需要额外的细节
- **THEN** 在主步骤下使用子要点
- **AND** 保持一致的缩进
  - 子要点提供示例或具体说明
  - 保持子要点简洁

### 需求：格式灵活性

结构化格式应是行为规范的默认格式，但在更适合内容类型时可以使用替代格式。

#### 场景：记录 API 规范

- **WHEN** 记录 REST API 端点或 GraphQL schemas
- **THEN** 可以使用 OpenAPI、GraphQL SDL 或类似格式
- **AND** 规范应清晰指示所使用的格式
- **AND** 行为方面仍应遵循结构化格式

#### 场景：记录数据 schema

- **WHEN** 记录数据结构、数据库 schema 或配置
- **THEN** 可以使用 JSON Schema、SQL DDL 或类似格式
- **AND** 包括行为规则和约束的结构化格式

#### 场景：使用简化格式

- **WHEN** 记录没有复杂场景的简单能力
- **THEN** 可以使用没有完整结构的简化 WHEN/THEN 格式
- **AND** 这应在该能力内保持一致

## 变更存储约定

### 未来状态存储

WHEN 创建变更提案
THEN 存储受影响规范的完整未来状态
AND 使用干净的 markdown，不使用差异语法

`changes/[name]/specs/` 目录应包含：
- 变更后规范将存在的完整规范文件
- 不带 `+` 或 `-` 前缀的干净 markdown
- 最终预期状态的所有格式和结构

### 提案格式

WHEN 记录变更内容
THEN 提案应显式描述每个变更：

```markdown
**[部分或行为名称]**
- 从： [当前状态/需求]
- 到： [未来状态/需求]
- 原因： [为什么需要此变更]
- 影响： [破坏性/非破坏性，受影响者]
```

这种显式格式弥补了没有行内差异的不足，并确保审阅者准确理解将发生什么变化。

## 变更生命周期

变更过程应遵循以下状态：

1. **提议**：AI 创建包含未来状态规范和显式提案的变更
2. **审阅**：人类审阅提案和未来状态
3. **批准**：变更获批准进行实现
4. **实现**：遵循 tasks.md 检查清单（可以跨越多个 PR）
5. **部署**：变更部署到生产环境
6. **更新**：`specs/` 中的规范更新以匹配部署的现实
7. **归档**：变更移至 `archive/YYYY-MM-DD-[name]/`

## 查看变更

WHEN 审阅提议的变更
THEN 审阅者可以通过以下方式进行比较：
- 变更提交时的 GitHub PR 差异视图
- 命令行：`diff -u specs/[capability]/spec.md changes/[name]/specs/[capability]/spec.md`
- 任何比较当前状态与未来状态的视觉差异工具

系统依赖工具生成差异，而不是存储差异。

## 能力命名

能力应使用：
- 动名词模式（例如 `user-auth`、`payment-capture`）
- 连字符小写名称
- 单一关注点（每个能力一个职责）
- 无嵌套（`specs/` 下的扁平结构）

## 何时变更需要提案

以下情况需要创建提案：
- 新功能或新能力
- 对现有行为的破坏性变更
- 架构或模式变更
- 改变行为的性能优化
- 影响访问模式的安全更新

以下情况不需要提案：
- 恢复预期行为的错误修复
- 拼写或格式修复
- 非破坏性依赖更新
- 为现有行为添加测试
- 文档澄清

## 为什么采用这种方法

干净的未来状态存储提供：
- **可读性**：无差异语法污染
- **AI 兼容性**：AI 工具理解的标准 markdown
- **简单性**：无需特殊解析或处理
- **工具无关**：任何差异工具都可以显示变更
- **清晰的意图**：显式提案记录推理过程

结构化格式增加了：
- **视觉一致性**：Requirement 和 Scenario 前缀使部分立即可识别
- **可解析性**：一致的结构支持工具化和自动化
- **灵活性**：在适当的地方支持替代格式
- **渐进式采用**：现有规范可以逐步迁移
