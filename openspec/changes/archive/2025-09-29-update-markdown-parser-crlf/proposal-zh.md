# 更新 Markdown 解析器的 CRLF 处理

## 问题
Windows 用户报告 `openspec validate` 会引发"变更必须包含 Why 部分"的错误，即使该部分确实存在（参见 GitHub issue #77）。CLI 目前按 `\n` 分割 markdown，并在比较标题时未去除 `\r`，因此使用 CRLF 换行符保存的文件会在标题标记中保留尾随回车符。结果导致解析器无法检测到 `## Why`/`## What Changes`，触发错误的验证错误并破坏 Windows 默认编辑器上的工作流程。

## 解决方案
- 在解析器内部规范化 markdown 内容，使 CRLF 和单独的 CR 输入在章节检测之前被视为 `\n`，从标题和内容比较中去除所有回车符。
- 在所有构建 `MarkdownParser` 的地方复用规范化的读取器，以保持验证、查看、规范和列表流程的行为一致。
- 添加可重现该失败的回归测试覆盖（围绕 `parseChange` 的单元测试和一个写入 CRLF 变更然后运行 `openspec validate` 的 CLI 生成/e2e 测试）。
- 更新 `cli-validate` 规范，以确认无论换行符样式如何，必需章节都应被识别的期望。

## 优势
- 无需手动转换换行符即可恢复 Windows 编辑器的正确验证行为。
- 通过有针对性的测试锁定修复，使未来的解析器重构保持跨平台支持。
- 明确规范，使下游工作（例如跨 shell e2e 计划）了解不可协商的行为。

## 风险
- 低：解析器规范化会影响解析规范和变更的共享代码路径；需要确保其他命令消费者没有回归（通过现有解析器测试加上新的 CRLF 测试用例来缓解）。
