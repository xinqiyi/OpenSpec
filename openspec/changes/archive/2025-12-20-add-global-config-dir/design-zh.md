## 背景

OpenSpec 需要一个标准的用户级别配置位置，能够跨平台工作并遵循既定惯例。这将作为设置、功能标志以及未来产物（如工作流或模板）的基础。

## 目标 / 非目标

**目标：**
- 为全局配置提供单一的、定义良好的位置
- 遵循 XDG 基础目录规范（被 CLI 工具广泛采用）
- 支持跨平台使用（Unix、macOS、Windows）
- 保持实现最小化 - 仅为基础功能
- 支持未来扩展（缓存、状态、工作流）

**非目标：**
- 项目本地配置覆盖（不在范围内）
- 配置文件迁移工具
- 配置验证 CLI 命令
- 多个配置档案

## 决策

### 路径解析策略

**决策：** 使用 XDG 基础目录规范并带有平台回退。

```
Unix/macOS：$XDG_CONFIG_HOME/openspec/ 或 ~/.config/openspec/
Windows：    %APPDATA%/openspec/
```

**理由：**
- XDG 是 CLI 工具的事实标准（被 gh、bat、ripgrep 等使用）
- 环境变量覆盖允许用户自定义
- Windows 使用其原生约定（%APPDATA%）以获得更好的集成

**考虑的替代方案：**
- `~/.openspec/` - 简单但会使主目录杂乱
- macOS 上的 `~/Library/Application Support/` - 对 CLI 工具来说过于繁琐

### 配置文件格式

**决策：** JSON（`config.json`）

**理由：**
- 原生 Node.js 支持（无依赖）
- 人类可读且可编辑
- 通过 TypeScript 实现类型安全
- 符合 project.md 的"最小依赖"原则

**考虑的替代方案：**
- YAML - 需要依赖，编辑时更容易出错
- TOML - 在 Node.js 生态中不太常见
- 仅环境变量 - 对于结构化设置来说过于有限

### 配置模式

**决策：** 扁平结构，带类型化字段，从最小化开始。

```typescript
interface GlobalConfig {
  featureFlags?: Record<string, boolean>;
}
```

**理由：**
- `featureFlags` 支持新功能的受控发布
- 带默认值的可选字段避免破坏性变更
- 扁平结构易于理解和扩展

### 加载策略

**决策：** 每次调用时从磁盘读取，不进行缓存。

```typescript
export function getGlobalConfig(): GlobalConfig {
  return loadConfigFromDisk();
}
```

**理由：**
- CLI 命令是短生命周期的；缓存增加了复杂性但没有好处
- 读取一个小的 JSON 文件约需 1ms；开销可忽略
- 始终返回最新数据；无缓存失效问题
- 实现更简单

### 目录创建

**决策：** 仅在保存时创建目录，读取时不创建。

**理由：**
- 读取操作时不创建空目录
- 从不保存配置的用户不会产生不必要的目录
- 符合最少意外原则

## 风险 / 权衡

| 风险 | 缓解措施 |
|------|----------|
| 配置文件损坏 | 解析错误时返回默认值，记录警告 |
| 权限问题 | 保存前检查写权限，清晰的错误消息 |
| 未来模式变更 | 使用可选字段，如有需要后续添加版本字段 |

## 开放问题

无 - 此提案有意保持最小化。
