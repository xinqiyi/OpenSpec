## 背景

目前，delta 规范仅在运行 `openspec archive` 时才会应用到主规范。这捆绑了两个关注点：
1. 应用规范变更（delta → 主规范）
2. 归档变更（移动到归档文件夹）

用户希望更灵活地提前同步规范，特别是在迭代期间。归档命令已经包含 `buildUpdatedSpec()` 中的合并逻辑。

## 目标 / 非目标

**目标：**
- 将规范同步与归档解耦
- 为 Agent 提供 `/opsx:sync` 技能以按需同步规范
- 保持操作幂等（多次运行安全）

**非目标：**
- 跟踪规范是否已同步（无状态）
- 改变归档行为（它将继续应用规范）
- 支持部分应用（所有 delta 一起同步）

## 决策

### 1. 重用现有的合并逻辑

**决策**：将 `buildUpdatedSpec()` 逻辑从 `ArchiveCommand` 提取到共享模块。

**理由**：归档命令已经实现了 delta 解析和应用。与其重复，不如提取和重用。

**考虑的替代方案**：
- 在新命令中重复逻辑（被拒绝：维护负担）
- 让 sync 带标志调用 archive（被拒绝：耦合）

### 2. 无状态跟踪

**决策**：不跟踪规范是否已同步。每次调用读取 delta 和主规范，进行合并。

**理由**：
- 幂等操作不需要状态
- 避免标志和实际情况之间的同步问题
- 更简单的实现和心智模型

**考虑的替代方案**：
- 在 `.openspec.yaml` 中跟踪 `specsSynced: true`（被拒绝：不必要的复杂性）
- 存储已同步 delta 的快照（被拒绝：过度设计）

### 3. Agent 驱动的方法（无 CLI 命令）

**决策**：`/opsx:sync` 技能完全由 Agent 驱动 - Agent 读取 delta 规范并直接编辑主规范。

**理由**：
- 允许智能合并（添加场景而不复制整个需求）
- Delta 表示*意图*，而不是整体替换
- 更灵活和自然的编辑工作流
- 归档仍然使用程序化合并（用于最终确定的变更）

### 4. 归档行为不变

**决策**：归档继续在其流程中应用规范。如果规范已经合并，操作是无操作的。

**理由**：向后兼容。不使用 `/opsx:sync` 的用户获得相同的体验。

## 风险 / 权衡

**[风险] 多个变更修改同一规范**
→ 最后同步的胜出。与当前归档相同。用户应协调或使用顺序归档。

**[风险] 用户同步规范后继续编辑 delta**
→ 再次运行 `/opsx:sync` 会重新合并。幂等设计处理了这种情况。

**[权衡] 无撤销机制**
→ 用户可以在需要时 `git checkout` 主规范。显式撤销命令不在范围内。

## 实现方案

1. 将规范应用逻辑从 `ArchiveCommand.buildUpdatedSpec()` 提取到 `src/core/specs-apply.ts`
2. 在 `skill-templates.ts` 中添加 `/opsx:sync` 的技能模板
3. 在托管技能中注册技能
