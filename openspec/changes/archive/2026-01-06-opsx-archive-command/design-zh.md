## 背景

实验性工作流（OPSX）提供了创建变更的完整生命周期：
- `/opsx:new` - 使用模式搭建新变更
- `/opsx:continue` - 创建下一个产物
- `/opsx:ff` - 快进所有产物
- `/opsx:apply` - 实施任务
- `/opsx:sync` - 将 delta 规范同步到主规范

缺失的部分是归档。现有的 `openspec archive` 命令可以工作，但是：
1. 以编程方式应用规范（非 Agent 驱动）
2. 不使用产物图谱进行完成检查
3. 不与 OPSX 工作流理念集成

## 目标 / 非目标

**目标：**
- 添加 `/opsx:archive` 技能以完成 OPSX 工作流生命周期
- 使用产物图谱进行模式感知的完成检查
- 与 `/opsx:sync` 集成以实现 Agent 驱动的规范同步
- 在归档中保留 `.openspec.yaml` 模式元数据

**非目标：**
- 替换现有的 `openspec archive` CLI 命令
- 更改 CLI 命令中规范的应用方式
- 修改产物图谱或模式系统

## 决策

### 决策 1：仅技能实现（无新 CLI 命令）

`/opsx:archive` 将仅作为斜杠命令/技能，而不是新的 CLI 命令。

**理由**：现有的 `openspec archive` CLI 命令已经处理了核心归档功能（移动到归档文件夹、日期前缀）。OPSX 版本只需要不同的归档前检查和可选的同步提示，这些是更适合技能形式的 Agent 行为。

**考虑的替代方案**：
- 向 `openspec archive` 添加标志（例如 `--experimental`）- 被拒绝：增加了 CLI 的复杂性，更难维护两个代码路径
- 新 CLI 命令 `openspec archive-experimental` - 被拒绝：不必要的重复，Agent 技能是 OPSX 模式

### 决策 2：归档前提示同步

技能将检查未同步的 delta 规范，并在归档前提示用户。

**理由**：OPSX 理念是通过 `/opsx:sync` 进行 Agent 驱动的智能合并。我们不像常规归档命令那样以编程方式应用规范，而是提示用户首先进行同步（如果需要）。这保持了工作流的灵活性（用户可以拒绝并仅归档）。

**流程**：
1. 检查变更中是否存在 `specs/` 目录
2. 如果存在，询问："此变更有 delta 规范。是否要在归档前将其同步到主规范？"
3. 如果用户说是，执行 `/opsx:sync` 逻辑
4. 无论答案如何，继续进行归档

### 决策 3：使用产物图谱进行完成检查

技能将使用 `openspec status --change "<name>" --json` 检查产物完成情况，而不仅仅是验证 proposal.md 和规范。

**理由**：实验性工作流是模式感知的。不同的模式有不同的必需产物。产物图谱知道当前模式的哪些产物已完成/未完成。

**行为**：
- 如果任何产物未完成，显示警告
- 不阻止归档（用户可能有提前归档的正当理由）
- 列出未完成的产物，以便用户做出明智决定

### 决策 4：重用常规归档的 tasks.md 完成检查

技能将解析 tasks.md 并警告不完整的任务，与常规归档相同。

**理由**：无论工作流如何，任务完成检查都是有价值的。逻辑很简单（统计 `- [ ]` vs `- [x]`），不需要特殊的 OPSX 处理。

### 决策 5：将变更移动到 archive/ 并带日期前缀

与常规命令相同的归档行为：移动到 `openspec/changes/archive/YYYY-MM-DD-<name>/`。

**理由**：与现有归档约定一致。`.openspec.yaml` 文件随变更一起移动，保留模式元数据。

## 风险 / 权衡

**风险**：用户对何时使用 `/opsx:archive` 与 `openspec archive` 感到困惑
→ **缓解措施**：文档应澄清：如果你一直在使用 OPSX 工作流，使用 `/opsx:archive`；否则使用 `openspec archive`。两者产生相同的归档结果。

**风险**：如果用户拒绝并且有 delta 规范，同步不完整
→ **缓解措施**：提示是信息性的；用户有完全的控制权。他们可能想在不同步的情况下归档（例如，放弃的变更）。在输出中记录一条备注。

**权衡**：OPSX 归档中没有程序化规范应用
→ **已接受**：这是有意为之。OPSX 理念是 Agent 驱动的合并。如果用户想要程序化应用，请改用 `openspec archive`。
