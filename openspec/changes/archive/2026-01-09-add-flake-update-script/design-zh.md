## 上下文

先前变更中添加的 Nix flake 在以下情况下需要手动维护：
1. 包版本变更（必须更新 flake.nix 版本字段）
2. 依赖变更（必须更新 pnpmDeps 哈希）

目前这要求维护者：
- 手动编辑 flake.nix 版本
- 设置占位哈希
- 运行 nix build 获取错误信息
- 从错误消息中复制哈希
- 再次更新 flake.nix
- 验证构建是否有效

这既繁琐又容易出错，尤其对于不熟悉 Nix 的维护者。

## 目标

- 自动更新 flake.nix 的版本和哈希
- 使脚本具有幂等性，可安全多次运行
- 在执行期间提供清晰的反馈
- 轻松集成到发布工作流中

## 非目标

- 自动提交变更（由维护者决定何时提交）
- 支持非 pnpm 包管理器
- 处理超出 OpenSpec 用例范围的复杂 Nix 配置

## 决策

### 使用 Bash 而非 Node.js 脚本

**决策**：实现为 bash 脚本而非 Node.js。

**理由**：
- 需要调用 Nix 命令，这是 bash 原生的
- 在 bash 中使用 grep/sed 解析 Nix 输出更简单
- 更新 flake.nix 的维护者可能已安装 Nix（bash 环境）
- Node.js 会为 shell 操作增加不必要的复杂性

**考虑的替代方案**：使用 child_process 的 Node.js 脚本 - 为 shell 操作增加了对额外 npm 包的依赖，对于 Nix 工具链来说不够自然。

### 从构建错误输出中提取哈希

**决策**：使用占位哈希触发故意的构建失败以获取正确的哈希。

**理由**：这是更新固定输出派生值的标准 Nix 工作流。不存在无需构建即可计算哈希的 API。

**考虑的替代方案**：从 pnpm-lock.yaml 预计算哈希 - 需要理解 Nix 的哈希算法和 pnpm 的锁文件结构，脆弱且非标准。

### 使用 sed 进行就地文件编辑

**决策**：使用 `sed -i` 就地更新 flake.nix。

**理由**：简单，在所有 Unix 系统上可用，能处理所需的特定替换模式。

**考虑的替代方案**：
- 使用 Node.js 解析/修改：对于简单的字符串替换来说过于复杂
- 不带 `-i` 的手动 `sed`：需要临时文件，更复杂

### 哈希更新后验证构建

**决策**：在更新哈希后始终运行验证构建。

**理由**：立即捕获错误，让维护者确信更新成功。

**权衡**：花费额外时间（约 30 秒），但防止了损坏的 flake.nix 提交。

## 关键实现细节

### 路径解析

脚本相对于自身位置计算路径：
```bash
SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
PROJECT_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"
```

这允许从任何工作目录运行。

### 错误处理

使用 `set -euo pipefail` 进行严格的错误处理：
- `-e`：任何命令失败时退出
- `-u`：访问未定义变量时退出
- `-o pipefail`：捕获管道中的失败

### 哈希提取模式

使用带 Perl 正则表达式的 grep 提取哈希：
```bash
grep -oP 'got:\s+\Ksha256-[A-Za-z0-9+/=]+'
```

这可靠地提取哈希，不受周围文本影响。

## 风险/权衡

**[风险]** 脚本假设标准 Nix 错误消息格式 → **缓解措施**：如果提取失败，脚本退出并显示错误及完整输出

**[风险]** 构建可能因哈希不匹配以外的原因失败 → **缓解措施**：脚本在继续之前检查输出中是否有哈希

**[权衡]** 需要安装 Nix 才能运行 → **好处**：只有需要更新 flake 的维护者需要运行此脚本，而他们有 Nix
