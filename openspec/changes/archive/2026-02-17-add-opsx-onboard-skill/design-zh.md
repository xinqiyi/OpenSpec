## 上下文

OpenSpec 拥有完整的技能和斜杠命令生成系统。技能在 `src/core/templates/skill-templates.ts` 中定义为返回 `SkillTemplate` 对象（用于代理技能）和 `CommandTemplate` 对象（用于斜杠命令）的函数。这些在 `src/core/shared/skill-generation.ts` 中注册，并在 `openspec init` 和 `openspec update` 期间生成。

现有技能遵循一致的模式：
- `getXxxSkillTemplate()` 返回具有名称、描述、指令的技能
- `getOpsxXxxCommandTemplate()` 返回具有名称、描述、类别、标签、内容的斜杠命令
- 两者都在 `skill-generation.ts` 的各自数组中进行注册

## 目标 / 非目标

**目标：**
- 添加通过引导实践教授 OpenSpec 工作流的 `/opsx:onboard` 技能
- 遵循现有的技能/命令模板生成模式
- 提供解释每个步骤的综合解说
- 包含代码分析以建议真实的、范围适中的任务

**非目标：**
- 创建单独的"演示模式"或模拟工作流（我们做真实工作）
- 添加新的 CLI 命令（这纯粹是代理指令）
- 修改 init/update 流程（仅添加到模板数组）

## 决策

### 决策 1：单一整体技能

入门技能将是一个单一的综合指令集，而不是用标志组合现有技能。

**理由：**
- 斜杠命令不支持标志（它们只是提示）
- 整体技能可以完全控制解说和节奏
- 保持单一连贯的体验更易于维护
- 用户通过在解说中看到真实命令来学习它们

### 决策 2：代码分析模式

技能指令将指导代理在建议入门级任务时寻找特定模式：

1. 代码中的 TODO/FIXME 注释
2. 缺失的错误处理（吞没错误的 `catch` 块，危险操作周围没有 try-catch）
3. 没有测试的函数（将 src/ 与测试文件交叉引用）
4. TypeScript 文件中的 type: any
5. 非调试代码中的 console.log 语句
6. 面向用户输入上的缺失输入验证
7. 最近的 git 提交（了解用户正在处理的内容的上下文）

**理由：** 这些是普遍适用、易于检测并能产生范围良好的任务。

### 决策 3：解说集成风格

每个阶段将遵循一个模式：
1. **解释** 我们将要做什么以及为什么（1-2 句话）
2. **执行** 操作（运行命令、创建工件）
3. **展示** 发生了什么
4. **暂停** 在关键过渡点（不是每一步）

暂停发生在：
- 任务选择后（创建变更前）
- 起草提案后（保存前）
- 任务生成后（实现前）
- 归档后（最终回顾）

**理由：** 暂停太多变得乏味。太少则失去教学机会。这些是自然的"章节分隔。"

### 决策 4：范围防护方法

当用户选择的任务太大时，技能将：
1. 承认该任务有价值
2. 解释为什么第一次做小一点的更好
3. 建议较小的切片或替代方案
4. 如果用户坚持，允许覆盖

**理由：** 软性防护在不让人沮丧的情况下进行教学。用户在此体验中学习范围校准。

### 决策 5：模板结构

技能模板将包含约 400-600 行的指令文本，结构如下：

```
- 预检检查（init 状态）
- 阶段 1：欢迎与设置
- 阶段 2：任务选择（包含代码分析指令）
- 阶段 3：探索演示（简短）
- 阶段 4：变更创建
- 阶段 5：提案
- 阶段 6：规范
- 阶段 7：设计
- 阶段 8：任务
- 阶段 9：应用（实现）
- 阶段 10：归档
- 阶段 11：回顾与后续步骤
- 边界情况与优雅退出
```

命令模板将与技能模板相同（相同内容，不同包装器）。

**理由：** 遵循已建立的模式，即技能和命令共享相同的核心指令。

## 风险 / 权衡

**风险：指令长度**
该技能将比其他现有技能长得多（约 500 行 vs 约 100-200 行）。
→ 缓解措施：这是可以接受的，因为入门本质上是全面的。令牌成本是每次会话一次的。

**风险：代码分析可能找不到任何内容**
某些代码库（新项目、非常干净的代码）可能没有明显的改进机会。
→ 缓解措施：回退到询问用户想要构建什么。将"添加新功能"作为选项包含。

**风险：任务建议可能不合适**
代理可能建议触及敏感代码或具有隐藏复杂性的任务。
→ 缓解措施：用户总是选择；代理仅建议。范围估算有助于设定预期。

**风险：用户中途放弃**
入门大约需要 15 分钟；用户可能不会完成。
→ 缓解措施：优雅退出处理——注明变更是保存的，解释以后如何继续。
