# 规范：带配置的模式解析

## 新增的需求

### 需求：使用配置模式作为新变更的默认值

系统应在创建新变更时且在未提供显式 `--schema` 标志的情况下，使用 `openspec/config.yaml` 中的模式字段作为默认值。

#### 场景：不带 --schema 标志创建变更且配置存在
- **当** 用户运行 `openspec new change foo` 且配置包含 `schema: "tdd"`
- **则** 系统使用模式 "tdd" 创建变更

#### 场景：不带 --schema 标志创建变更且无配置
- **当** 用户运行 `openspec new change foo` 且不存在配置文件
- **则** 系统使用默认模式 "spec-driven" 创建变更

#### 场景：带显式 --schema 标志创建变更
- **当** 用户运行 `openspec new change foo --schema custom` 且配置包含 `schema: "tdd"`
- **则** 系统使用模式 "custom" 创建变更（CLI 标志覆盖配置）

### 需求：使用更新的优先级顺序解析模式

系统应按照以下优先级顺序解析变更的模式：CLI 标志、变更元数据、项目配置、硬编码默认值。

#### 场景：提供了 CLI 标志
- **当** 用户使用 `--schema custom` 运行命令
- **则** 系统使用 "custom"，无论变更元数据或配置如何

#### 场景：变更元数据指定模式
- **当** 变更的 `.openspec.yaml` 包含 `schema: bound` 且配置包含 `schema: tdd`
- **则** 系统使用来自变更元数据的 "bound"

#### 场景：仅项目配置指定模式
- **当** 没有 CLI 标志或变更元数据，但配置包含 `schema: tdd`
- **则** 系统使用来自项目配置的 "tdd"

#### 场景：任何地方都未指定模式
- **当** 没有 CLI 标志、变更元数据或项目配置
- **则** 系统使用硬编码默认值 "spec-driven"

### 需求：支持配置中的项目本地模式名称

系统应允许配置中的模式字段引用 `openspec/schemas/` 中定义的项目本地模式。

#### 场景：配置引用项目本地模式
- **当** 配置包含 `schema: "my-workflow"` 且 `openspec/schemas/my-workflow/` 存在
- **则** 系统解析为项目本地模式

#### 场景：配置引用不存在的模式
- **当** 配置包含 `schema: "nonexistent"` 且该模式不存在
- **则** 系统在尝试加载模式时显示错误，带有模糊匹配建议和所有有效模式列表

### 需求：为无效模式提供有帮助的错误消息

系统应显示带有模糊匹配建议、可用模式列表和修复说明的模式错误。

#### 场景：模式名称有拼写错误（接近匹配）
- **当** 配置包含 `schema: "spce-driven"`（拼写错误）
- **则** 错误消息包含 "您是不是想找：spec-driven (built-in)" 作为建议

#### 场景：模式名称无接近匹配
- **当** 配置包含 `schema: "completely-wrong"`
- **则** 错误消息显示所有可用的内置和项目本地模式列表

#### 场景：错误消息包含修复说明
- **当** 配置引用无效模式
- **则** 错误消息包含 "修复：编辑 openspec/config.yaml 并将 'schema: X' 改为有效的模式名称"

#### 场景：错误区分内置与项目本地模式
- **当** 错误列出可用模式
- **则** 输出清晰地将每个标记为 "built-in" 或 "project-local"

### 需求：保持现有变更的向后兼容性

系统应继续适用于没有项目配置的现有变更。

#### 场景：无配置的现有变更
- **当** 变更是在配置功能之前创建的，且不存在配置文件
- **则** 系统使用现有逻辑解析模式（变更元数据或硬编码默认值）

#### 场景：稍后添加配置的现有变更
- **当** 在项目已存在变更的情况下添加配置文件
- **则** 现有变更继续使用其来自 `.openspec.yaml` 的绑定模式
