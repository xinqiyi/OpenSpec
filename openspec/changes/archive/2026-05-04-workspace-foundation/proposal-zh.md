## 为什么

用户需要一个工作区，使其感觉像是跨多个仓库或文件夹进行规划的自然主目录。

他们应该能够这样思考：

```text
我有经常一起规划的仓库或文件夹。
我创建一个 OpenSpec 工作区。
该工作区是变更所在的地方。
我的代码保持在原处。
OpenSpec 将工作区链接到那些本地路径。
```

工作区不是一个功能。它是持久的规划主目录。各个功能、修复和项目是工作区内部的变更。

用户不必选择存储位置、提前创建变更或在 OpenSpec 能够定位之前了解内部工作区状态。

POC 证明了工作区状态是有用的。此重新实现应将其转化为一个简单的产品模型，用户和代理无需特殊词汇即可解释。

## 什么变更

此变更定义了 OpenSpec 工作区的面向用户基础。

一个 OpenSpec 工作区具有可识别的规划主目录：

```text
workspace-root/
  changes/
  .openspec-workspace/
```

`changes/` 是工作区级别规划所在的位置。`.openspec-workspace/` 将目录标识为 OpenSpec 工作区并存储工作区状态。

OpenSpec 管理工作区位于一个标准位置：

```text
<全局数据目录>/workspaces/
```

用户不应需要选择该位置。OpenSpec 仍在设置后显示工作区路径，以便用户知道规划文件所在位置。此基础切片不提供工作区特定的环境变量或配置覆盖，用于管理工作区存储。

OpenSpec 还在当前机器上维护已知工作区的轻量级本地注册表。注册表驱动全局命令、选择器和列表，但每个工作区文件夹保持为真实源。

工作区状态按用户期望进行拆分：

- 共享的工作区信息可以在机器之间移动
- 本地检出路径保持每台机器本地
- 链接的仓库和文件夹通过稳定的链接名称引用，而不是绝对路径

链接路径可以是完整的仓库、单体仓库内的文件夹或工作区应针对其进行规划的其他现有文件夹。链接路径在被纳入工作区规划之前不需要仓库本地 `openspec/` 状态。仓库本地 OpenSpec 状态以后可能对实施、验证或归档工作流很重要，但它不是规划可见性的先决条件。

本机 Windows/PowerShell 和 WSL2 都受支持。每个运行时使用自己的路径约定。OpenSpec 在此基础切片中不在 Windows 和 WSL 之间翻译路径。

## 成果

在此变更之后，后续工作区功能可以依赖一个清晰的产品契约：

- OpenSpec 可以判断用户何时在工作区内部。
- OpenSpec 知道默认在何处创建管理工作区。
- OpenSpec 可以维护已知工作区的本地注册表。
- 工作区有一个可见的规划区域：`changes/`。
- 工作区状态可与仓库本地 `openspec/` 状态区分。
- 共享工作区状态不会强制将一个用户的本地路径强加给另一个用户。
- 工作区规划可以通过稳定的链接名称引用现有仓库或文件夹。
- 链接的仓库或文件夹不需要仓库本地 OpenSpec 状态即可进行工作区规划。
- 多仓库和大型单体仓库工作可以使用相同的工作区规划模型。
- 仓库拥有的规范和实施仍由其仓库或源区域拥有。
- Windows、PowerShell 和 WSL2 路径行为是可预测的。

此变更不交付完整的工作区工作流。它为 `workspace-create-and-register-repos` 提供了添加第一个面向用户命令所需的基础。

## POC 发现

要保留的行为：

- 工作区是用于跨仓库规划的持久协调主目录。
- 工作区在其根目录有一个可见的 `changes/` 目录。
- 链接的仓库和文件夹提供工作区可以针对其进行规划的上下文。
- 稳定的链接名称比本地检出路径更重要。
- 本地机器路径不应成为共享工作区状态。
- 规范标准和实施仍属于拥有它们的仓库。

要继承的经验教训：

- POC 隐藏的 `.openspec/` 工作区元数据形状使工作区状态太容易与仓库本地 OpenSpec 状态混淆。
- 用户不应需要在工作区根目录内运行仓库本地的 `openspec init`。
- POC 要求已注册的仓库已有 `openspec/` 对于规划来说过于严格。仓库和文件夹在采用仓库本地 OpenSpec 状态之前应该是可链接的。
- 仓库或文件夹可见性不应依赖于创建变更。
- 工作区设置不应暗示仓库本地实施、分支、工作树、应用、验证或归档行为。
- `add-repo` 对于面向用户的模型来说过于狭窄。链接现有仓库或文件夹更清晰。

## 决策

- 工作区标识目录：`.openspec-workspace/`。
- 工作区标识文件：`.openspec-workspace/workspace.yaml`。
- 工作区名称：当前操作系统的有效文件夹名称，排除空名称、`.`/`..` 和路径分隔符。
- 工作区名称使用：存储在 `workspace.yaml` 中，用作默认管理工作区文件夹名称，并用作本地注册表名称。
- 规划表面：顶级 `changes/`。
- 本地机器状态：`.openspec-workspace/local.yaml`。
- 本地机器状态排除：OpenSpec 创建的工作区默认将 `.openspec-workspace/local.yaml` 从可移植协作状态中排除。
- 本地工作区注册表：`<全局数据目录>/workspaces/registry.yaml`。
- 默认工作区基础路径：`<全局数据目录>/workspaces/`。
- 平台行为：本机 Windows 和 WSL2 各自使用运行 OpenSpec 的运行时的路径约定。
- 链接路径可以是完整仓库、单体仓库文件夹或其他现有文件夹。
- 链接名称：非空、稳定的名称，在工作区内唯一，排除 `.`/`..` 和路径分隔符。
- 仓库本地 `openspec/` 状态不是工作区规划可见性的必要条件。
- 链接仅记录关系；它不在链接的仓库或文件夹内创建、复制、移动、初始化或编辑文件。

规划依赖：

- 无。这是第一个实施切片。

## 非目标

- 尚无完整的 `openspec workspace setup`、`openspec workspace link` 或 `openspec workspace relink` 流程。
- 第一个面向用户的工作区流程中没有公共的 `openspec workspace create` 命令。
- 没有用于更改标准工作区位置的面向用户命令、环境变量或配置设置。
- 没有询问用户 OpenSpec 默认应在何处存储工作区的问题。
- 没有自动的 Windows 到 WSL 或 WSL 到 Windows 路径翻译。
- 没有工作区打开代理启动行为。
- 没有工作区级别提案创建。
- 没有仓库切片应用、验证、归档、分支或工作树行为。
- 没有将工作区规划文件复制到链接的仓库或文件夹中，作为创建、检测或链接工作区的副作用。

## 能力

### 新能力

- `workspace-foundation`：定义 OpenSpec 工作区的产品基础。

### 修改的能力

- `openspec-conventions`：描述协调工作区与仓库本地 OpenSpec 项目的区别。

## 影响

- 工作区识别和路径行为。
- 工作区状态解析。
- 本地工作区注册表解析。
- 工作区心智模型的文档和代理指导。
- 后续工作区切片应基于此契约构建，而不是重新定义工作区存储、标识、注册表或路径行为。
