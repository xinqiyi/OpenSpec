## 新增需求

### 需求：工作区产品语言
OpenSpec 约定应使用面向用户的产品术语来描述协调工作区。

#### 场景：描述工作区结构
- **当** OpenSpec 文档描述工作区支持时
- **则** 应将工作区呈现为跨链接仓库或文件夹进行工作的规划中心
- **并且** 应将 `changes/` 描述为工作区规划区域

#### 场景：避免内部工作区词汇
- **当** OpenSpec 文档解释工作区包含的内容时
- **则** 应优先使用简洁的产品语言，例如"仓库或文件夹"
- **并且** 应避免在面向用户的内容中依赖诸如"工作集"、"代码区域"、"条目"、"别名"或"本地覆盖层"等术语

#### 场景：区分工作区和变更
- **当** OpenSpec 文档解释工作区规划时
- **则** 应将工作区描述为持久的规划中心
- **并且** 应将各个功能、修复和项目描述为工作区内的变更

#### 场景：区分工作区和仓库本地表面
- **当** OpenSpec 文档比较工作区和仓库本地流程时
- **则** 应解释工作区规划位于工作区根目录
- **并且** 应解释仓库本地规格和变更继续存放在每个仓库的 `openspec/` 目录下

#### 场景：安排工作区路线图顺序
- **当** 工作区重构工作分布在多个活动变更中时
- **则** 约定应允许这些变更作为 `openspec/changes/` 下的同级项保持扁平结构
- **并且** 在正式的变更堆叠元数据可用之前，依赖顺序可以通过提案文本来记录
