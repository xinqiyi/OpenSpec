## 新增需求

### 需求：引导式工作区设置
OpenSpec 应当为开始工作区规划的用户提供引导式设置流程。

#### 场景：通过设置创建工作区
- **当** 用户运行 `openspec workspace setup`
- **那么** OpenSpec 应引导用户创建 OpenSpec 工作区
- **且** 工作区应使用工作区基础架构中的标准工作区位置

#### 场景：先询问工作区名称
- **当** 交互式设置开始时
- **那么** OpenSpec 应在询问仓库或文件夹之前先询问工作区名称
- **且** 工作区名称应使用小写字母、数字和连字符组成的 kebab-case 格式

#### 场景：设置过程中重试无效的工作区名称
- **当** 交互式用户输入了无效的工作区名称
- **那么** OpenSpec 应说明工作区名称必须为 kebab-case 格式
- **且** 应让用户在继续设置之前输入另一个工作区名称

#### 场景：链接必需的第一个仓库或文件夹
- **当** 设置询问仓库或文件夹时
- **那么** 用户应提供至少一个现有的仓库或文件夹路径
- **且** 在至少链接一个路径之前，设置不应成功完成

#### 场景：设置过程中推断链接名称
- **当** 用户在设置过程中提供仓库或文件夹路径时
- **那么** OpenSpec 应从文件夹基本名称推断链接名称
- **且** 仅在推断的名称冲突时询问不同的名称

#### 场景：设置过程中处理推断的链接名称冲突
- **给定** 设置推断的链接名称已存在于工作区中
- **当** 设置为交互式时
- **那么** OpenSpec 应显示冲突的链接名称和该链接的现有路径
- **且** 应在继续之前询问用户不同的链接名称

#### 场景：保留文件夹风格的链接名称
- **当** OpenSpec 接受工作区链接名称时
- **那么** 它应允许在工作区基础架构的链接名称规则下有效的文件夹风格名称
- **且** 不应要求链接名称使用更严格的工作区名称 kebab-case 规则

#### 场景：设置过程中添加多个仓库或文件夹
- **当** 设置链接一个仓库或文件夹时
- **那么** OpenSpec 应让用户通过简单的重复提示添加另一个仓库或文件夹
- **且** 每个链接的路径应在不编辑目标仓库或文件夹的情况下记录

#### 场景：设置过程中存储已验证的绝对路径
- **当** 设置链接一个仓库或文件夹路径时
- **那么** OpenSpec 应验证该路径解析为现有的文件夹
- **且** 应将绝对运行时本地路径存储在机器本地状态中，而不是原始用户输入
- **且** 相对输入应相对于命令的当前工作目录进行解析

#### 场景：在设置链接路径中保留等号
- **当** 非交互式设置接收到的 `--link` 值解析为现有文件夹且包含 `=`
- **那么** OpenSpec 应将整个值作为路径处理
- **且** 应从文件夹基本名称推断链接名称
- **且** 显式的 `--link <name>=<path>` 输入应保留 `<path>` 内部的 `=` 字符

#### 场景：使用非交互式输入运行设置
- **当** `openspec workspace setup --no-interactive` 接收到工作区名称和至少一个有效链接
- **那么** OpenSpec 应在无需提示的情况下创建工作区
- **且** 应支持重复的 `--link` 值

#### 场景：非交互式设置重复链接名称
- **当** `openspec workspace setup --no-interactive` 收到两个具有相同推断或显式名称的链接
- **那么** OpenSpec 应失败并显示明确的重复链接名称错误
- **且** 错误信息应显示冲突的链接名称和第一个使用该名称的路径
- **且** 应建议使用具有不同名称的显式 `--link <name>=<path>` 值

#### 场景：缺少非交互式设置输入
- **当** `openspec workspace setup --no-interactive` 缺少工作区名称或链接
- **那么** OpenSpec 应失败并显示清晰的消息
- **且** 应说明哪些标志是必需的

#### 场景：完成设置
- **当** 设置完成
- **那么** OpenSpec 应显示工作区位置、规划路径和链接的仓库或文件夹
- **且** 应检查当前机器可以解析哪些内容

#### 场景：在本地记录已创建的工作区
- **当** 设置创建工作区
- **那么** OpenSpec 应将其记录在本地工作区注册表中
- **且** 工作区文件夹应保持为工作区状态的唯一真实来源

#### 场景：设置过程中重用现有工作区名称
- **给定** 具有所请求名称的托管工作区已存在
- **当** 用户使用该工作区名称运行设置
- **那么** OpenSpec 应说明该工作区已存在
- **且** 不应覆盖现有的工作区

### 需求：工作区发现
OpenSpec 应让用户看到当前机器上可用的 OpenSpec 托管工作区。

#### 场景：列出工作区
- **当** 用户运行 `openspec workspace list`
- **那么** OpenSpec 应列出已知的托管工作区
- **且** 每个工作区应包含工作区名称、工作区位置以及链接的仓库或文件夹

#### 场景：使用简短列表命令
- **当** 用户运行 `openspec workspace ls`
- **那么** OpenSpec 的行为应与 `openspec workspace list` 相同

#### 场景：没有工作区时列出
- **当** 用户运行 `openspec workspace list`
- **且** 没有托管工作区存在
- **那么** OpenSpec 应说明未找到工作区
- **且** 应向用户展示如何创建一个

#### 场景：列出过期的注册表条目
- **当** 本地注册表包含一个不再存在的工作区位置
- **那么** `workspace list` 应报告过期的工作区条目
- **且** 应避免静默删除注册表状态
- **且** 应避免自动重写或修复注册表状态

#### 场景：避免注册表清理命令
- **当** 用户在此切片中检查过期的工作区注册表条目时
- **那么** OpenSpec 应将过期条目视为仅报告诊断
- **且** 不应公开诸如 `workspace forget` 之类的注册表清理命令

### 需求：全局工作区命令
OpenSpec 应让工作区命令从工作区目录外部运行。

#### 场景：通过标志选择工作区
- **当** 需要一个工作区的命令接收到 `--workspace <name>`
- **那么** OpenSpec 应从本地注册表中使用该工作区
- **且** 如果工作区名称未知，应清晰地失败

#### 场景：使用当前工作区
- **给定** 命令从工作区文件夹或子目录运行
- **当** 命令需要一个工作区且未提供 `--workspace` 标志
- **那么** OpenSpec 应使用当前工作区

#### 场景：使用未注册的当前工作区
- **给定** 命令从有效的工作区文件夹或子目录运行
- **且** 该工作区未在本地工作区注册表中记录
- **当** 命令需要一个工作区且未提供 `--workspace <name>` 标志
- **那么** OpenSpec 应使用当前工作区
- **且** 应包含一个非致命警告状态，代码为 `workspace_not_in_local_registry`
- **且** 警告应说明用户如何让该工作区在本地记录

#### 场景：变更后记录未注册的当前工作区
- **给定** 一个可变工作区命令使用了未在本地工作区注册表中记录的有效当前工作区
- **当** `workspace link` 或 `workspace relink` 成功时
- **那么** OpenSpec 应将工作区名称和位置记录在本地工作区注册表中

#### 场景：Doctor 不注册当前工作区
- **给定** `workspace doctor` 使用了未在本地工作区注册表中记录的有效当前工作区
- **当** doctor 完成时
- **那么** OpenSpec 应报告非致命注册表警告
- **且** 不应写入注册表状态

#### 场景：从多个工作区中选择
- **给定** 存在多个已知工作区
- **当** 交互式命令需要一个工作区且未指定时
- **那么** OpenSpec 应显示工作区选择器
- **且** 选择器应包含工作区名称和路径

#### 场景：模糊的非交互式工作区选择
- **给定** 存在多个已知工作区
- **当** 非交互式命令需要一个工作区且未指定时
- **那么** OpenSpec 应失败并显示清晰的消息
- **且** 应建议传递 `--workspace <name>`

#### 场景：模糊的 JSON 工作区选择
- **给定** 存在多个已知工作区
- **当** 以 `--json` 运行的命令需要一个工作区且未指定时
- **那么** OpenSpec 应失败而不显示选择器
- **且** 应发出结构化的状态错误
- **且** 应建议传递 `--workspace <name>`

#### 场景：需要工作区的命令没有已知工作区
- **给定** 本地注册表中没有已知工作区
- **且** 命令不是从工作区文件夹或子目录运行
- **当** `workspace link`、`workspace relink`、`workspace doctor` 或其他需要一个工作区的命令在未带 `--workspace <name>` 的情况下运行
- **那么** OpenSpec 应失败，无论交互模式如何，都不显示选择器
- **且** 应打印 `未找到已知的 OpenSpec 工作区。请先运行 'openspec workspace setup'。`
- **且** 应说明在至少一个工作区已知后可以使用 `--workspace <name>`

### 需求：工作区链接
OpenSpec 应让用户在创建变更之前将现有仓库或文件夹链接到工作区。

#### 场景：使用推断名称链接
- **当** 用户运行 `openspec workspace link <path>`
- **那么** OpenSpec 应从文件夹基本名称推断链接名称
- **且** 应将验证后的绝对本地路径存储为机器本地状态

#### 场景：使用显式名称链接
- **当** 用户运行 `openspec workspace link <name> <path>`
- **那么** OpenSpec 应使用显式链接名称进行规划
- **且** 应将验证后的绝对本地路径存储为机器本地状态

#### 场景：要求路径存在
- **当** 用户链接仓库或文件夹路径时
- **那么** 该路径应在当前机器上存在
- **且** OpenSpec 应拒绝缺失路径并显示清晰的消息

#### 场景：存储前解析链接路径
- **当** 用户链接仓库或文件夹路径时
- **那么** OpenSpec 应存储当前运行时的验证绝对路径
- **且** 相对输入应相对于命令的当前工作目录进行解析
- **且** OpenSpec 不应在原生 Windows、WSL2 和 Unix 运行时之间转换路径

#### 场景：链接 monorepo 文件夹
- **当** 用户链接 monorepo 中的包、服务、应用或目录时
- **那么** OpenSpec 应将其存储为工作区链接
- **且** 不应要求该文件夹拥有自己的仓库本地 `openspec/` 目录

#### 场景：链接没有本地 OpenSpec 的仓库
- **当** 用户链接一个不包含仓库本地 OpenSpec 状态的路径
- **那么** OpenSpec 应保留该仓库或文件夹以供工作区规划使用
- **且** 不应将缺失的仓库本地 OpenSpec 状态视为链接失败

#### 场景：仅记录链接
- **当** 用户链接仓库或文件夹时
- **那么** OpenSpec 应记录工作区状态和本地路径状态
- **且** 不应在链接的仓库或文件夹中创建、复制、移动、初始化或编辑文件

#### 场景：本地状态无效时阻止链接
- **给定** 工作区机器本地状态文件存在但无法解析或验证
- **当** 用户运行 `openspec workspace link`
- **那么** OpenSpec 应失败，状态码为 `workspace_local_state_invalid`
- **且** 不应重写共享工作区状态或机器本地路径状态

#### 场景：重用链接名称
- **给定** 工作区已有一个具有给定名称的链接
- **当** 用户尝试用相同名称链接另一个路径时
- **那么** OpenSpec 应说明该链接名称已被另一个链接使用
- **且** 应显示现有的链接名称和路径
- **且** 应建议选择不同的链接名称
- **且** 应在用户意图更改现有链接路径时建议 `workspace relink <name> <path>`
- **且** 除非用户显式重新链接，否则应保留现有链接

### 需求：工作区重新链接
OpenSpec 应让用户无需重建工作区即可更新现有的链接路径。

#### 场景：更新本地路径
- **给定** 工作区有一个链接
- **当** 用户运行 `openspec workspace relink <name> <path>`
- **那么** OpenSpec 应保留稳定的链接名称
- **且** 应将当前机器的机器本地路径更新为验证后的绝对路径

#### 场景：要求重新链接路径存在
- **当** 用户重新链接到新路径时
- **那么** 新路径应在当前机器上存在
- **且** OpenSpec 应拒绝缺失路径并显示清晰的消息

#### 场景：存储前解析重新链接路径
- **当** 用户重新链接到新路径时
- **那么** OpenSpec 应存储当前运行时的验证绝对路径
- **且** 相对输入应相对于命令的当前工作目录进行解析

#### 场景：本地状态无效时阻止重新链接
- **给定** 工作区机器本地状态文件存在但无法解析或验证
- **当** 用户运行 `openspec workspace relink`
- **那么** OpenSpec 应失败，状态码为 `workspace_local_state_invalid`
- **且** 不应重写机器本地路径状态

#### 场景：更新未知链接
- **当** 用户尝试重新链接一个不存在的链接时
- **那么** OpenSpec 应说明该链接名称未知
- **且** 应保留现有的工作区状态

#### 场景：避免所有者和交接字段
- **当** 用户在此切片中链接或重新链接仓库或文件夹时
- **那么** OpenSpec 不应询问所有者或交接元数据
- **且** 链接维护应专注于名称和本地路径

### 需求：工作区健康检查
OpenSpec 应说明当前机器可以为工作区解析哪些内容。

#### 场景：Doctor 检查一个选定的工作区
- **当** 用户运行 `openspec workspace doctor`
- **那么** OpenSpec 应检查一个选定的工作区
- **且** 默认情况下不应扫描本地注册表中的每个已知工作区

#### 场景：Doctor 推断当前工作区
- **给定** 命令从工作区文件夹或子目录运行
- **当** 用户运行 `openspec workspace doctor` 而不带 `--workspace <name>`
- **那么** OpenSpec 应检查当前工作区

#### 场景：检查健康的工作区
- **当** 用户运行 `openspec workspace doctor`
- **那么** OpenSpec 应显示工作区位置和工作区规划路径
- **且** 应显示链接的仓库或文件夹以及哪些路径在当前机器上可解析

#### 场景：选定的工作区位置缺失
- **给定** 选定的工作区来自本地注册表
- **且** 注册的工作区位置缺失或无效
- **当** 用户运行 `openspec workspace doctor`
- **那么** OpenSpec 应报告选定的工作区状态错误
- **且** 不应尝试检查该工作区的链接

#### 场景：报告仓库本地规范路径
- **当** 链接的仓库或文件夹可解析时
- **那么** doctor 应在仓库本地 `openspec/specs` 存在时报告 `repo_specs_path`
- **且** 当仓库本地规范不存在时报告 `repo_specs_path: null`

#### 场景：检查缺失的路径
- **当** 链接指向当前机器上缺失的路径时
- **那么** doctor 应标识受影响的链接名称
- **且** 应包含建议的 `workspace relink` 修复

#### 场景：检查共享状态和本地状态漂移
- **当** 共享工作区状态和机器本地路径状态不一致时
- **那么** doctor 应说明哪些链接名称受影响
- **且** 应区分共享工作区链接和仅本地路径

#### 场景：报告无效的本地状态
- **当** list 或 doctor 读取的工作区其机器本地状态文件无法解析或验证时
- **那么** OpenSpec 应报告状态码 `workspace_local_state_invalid`
- **且** 应避免将无效的本地状态视为空路径映射以进行变更或修复建议
- **且** 不应重写工作区注册表状态或机器本地路径状态

#### 场景：不自动修复的报告
- **当** doctor 发现问题时
- **那么** 它应报告它能找到的所有问题
- **且** 不应自动修复工作区状态

#### 场景：使用可读的人类输出
- **当** doctor 打印人类可读输出时
- **那么** 它应显示可读的工作区摘要、链接的仓库或文件夹以及存在的问题（如果有）
- **且** 应避免打印原始 JSON 或依赖僵硬的 YAML 转储作为默认的人类体验

### 需求：可脚本化的工作区设置命令
OpenSpec 应为直接的工作区设置命令提供 JSON 输出。

#### 场景：请求 JSON 输出
- **当** 用户向直接的工作区设置命令传递 `--json`
- **那么** OpenSpec 应打印机器可读的输出
- **且** 输出应避免额外的人类可读文本
- **且** 输出应将主要对象与结构化的 `status` 条目分开

#### 场景：设置 JSON 需要非交互式设置
- **当** 用户运行 `openspec workspace setup --json` 而不带 `--no-interactive`
- **那么** OpenSpec 应清晰地失败
- **且** 应说明 `workspace setup --json` 需要 `--no-interactive`

#### 场景：JSON 输出禁用提示
- **当** 直接的工作区设置命令以 `--json` 运行
- **那么** OpenSpec 应避免交互式提示
- **且** 当必需的选择不明确时，应失败并输出结构化状态

#### 场景：JSON 状态条目格式
- **当** 直接的工作区设置命令在 JSON 输出中报告警告、错误或建议修复时
- **那么** 每个状态条目应包含稳定的 `code`、`severity` 和人类可读的 `message`
- **且** 当特定对象字段或建议命令有用时，状态条目可以包含 `target` 和 `fix` 字段

#### 场景：JSON 对象状态格式
- **当** 直接的工作区设置命令为工作区、链接或列表对象输出 JSON 时
- **那么** 每个对象可以包含一个 `status` 数组，用于对象特定的警告或错误
- **且** 顶层响应应包含一个 `status` 数组，用于命令级别的警告或错误
- **且** 健康的对象和健康的响应应使用空的 `status` 数组

#### 场景：支持 JSON 输出的命令
- **当** 用户运行 `workspace setup --no-interactive`、`workspace list`、`workspace link`、`workspace relink` 或 `workspace doctor`
- **那么** 每个命令应支持 JSON 输出
