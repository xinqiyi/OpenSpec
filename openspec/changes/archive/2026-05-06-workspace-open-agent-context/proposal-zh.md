## 为什么

用户创建工作区并链接仓库或文件夹后，他们需要用首选代理或编辑器打开该工作区，并立即可用工作集。

工作区应提供仓库和文件夹位置、链接名称以及区分规划与实施的上下文。

## 什么变更

添加工作区打开体验：

```text
打开此工作区。
默认使用我的首选打开程序，并遵守显式的打开程序覆盖。
打开程序看到工作区位置、链接的仓库或文件夹、当前变更和相关说明。
```

链接是规划上下文。本地注册表是在当前机器上查找已知工作区的工作区发现索引。

预期的用户表面：

```bash
openspec workspace open
openspec workspace open platform
openspec workspace open --agent codex
openspec workspace open platform --agent github-copilot
openspec workspace open --editor
```

`workspace open` 在从工作区内部运行时，应打开当前工作区；在工作区外部运行时，自动选择唯一已知的工作区；在有多个已知工作区时，显示交互式选择器。用户可以在想要显式选择时，将工作区名称作为位置参数传递。

工作区设置应询问并存储机器本地工作区状态中的首选打开程序。`workspace open` 默认使用该偏好。`--agent <tool>` 是一次会话的覆盖，保持保存的偏好不变。

`--editor` 将工作区作为编辑器工作区打开。这与 `--agent github-copilot` 相关但不同：GitHub Copilot 需要编辑器工作区支持加上代理提示上下文，而纯编辑器打开应专注于打开链接的工作集。

工作区指导应尽可能存在于持久的工作区文件中：

- 稳定行为属于工作区级别的 `AGENTS.md`
- 特定于打开程序的启动提示在必要时保持最小
- 在变更存在之前，链接的仓库或文件夹可见，用于探索和规划

此切片支持通过文档化的打开程序形式进行根工作区启动。公共预览（`--prepare-only`）和机器可读上下文（`--json`）表面属于未来的上下文/查询设计，如果出现明确的用户需求。

此切片专注于根工作区打开行为。变更范围的会话需要来自工作区变更规划的目标模型，然后才能被清晰地指定。

规划依赖：

- 依赖于 `workspace-create-and-register-repos`。

## 能力

### 新能力

- `workspace-open`：通过首选代理或 VS Code 编辑器打开工作区，链接的仓库或文件夹可用于探索和规划。

### 修改的能力

- `workspace-foundation`：使用首选打开程序和可维护的可打开工作区表面，扩展机器本地工作区状态和设置/链接/重新链接行为。

## 影响

- `openspec workspace open`
- 工作区设置首选打开程序提示和本地偏好存储。
- 工作区提示、编辑器工作区和代理启动上下文。
- 生成或提交的工作区模式代理指导。
- 测试涵盖：在工作区内部打开、自动选择一个已知工作区、从多个已知工作区中选择、按工作区名称打开、一次会话代理覆盖和编辑器打开。
