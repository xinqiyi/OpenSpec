## 上下文

工作区设置已经创建了规划主目录，记录了链接的仓库或文件夹，存储了首选打开程序，并维护了根打开表面。为了使工作区变更规划在实践中起作用，打开的代理还需要从该工作区根目录获得可用的 OpenSpec 工作流技能。

仓库本地的 `openspec init` 和 `openspec update` 已经为选择代理表面和生成技能提供了用户模型。工作区设置应感觉类似，但安装目标是工作区根目录，而不是任何链接的仓库或文件夹。

现有的工件工作流假设变更位于仓库本地的 `openspec/changes/<id>` 路径下。工作区规划需要相同的工作流词汇，但规划主目录可能是工作区根目录，而实施主目录可能是链接的仓库或文件夹。

## 目标 / 非目标

**目标：**
- 在工作区设置期间将 OpenSpec 代理技能安装到工作区根目录。
- 使用活动的全局配置文件选择在工作区中安装哪些工作流技能。
- 让用户使用熟悉的 `--tools` 语义选择哪些代理接收技能。
- 持久化工作区本地代理技能选择，以便后续更新可以刷新相同的代理。
- 让用户稍后通过 `workspace update` 刷新、添加或移除工作区本地技能。
- 检测并报告工作区本地技能与活动全局配置文件的差异。
- 让 `openspec config profile` 在工作区内部运行时提供将已更改的配置文件设置应用到当前工作区的选项。
- 将工作区用户从仓库本地的 `openspec update` 重定向到 `openspec workspace update`。
- 为工作区范围的变更添加内置的工作区规划模式。
- 在工作区规划路径下创建工作区变更。
- 表示受影响的区域，而无需将实施工件强制放入链接的仓库。
- 通过状态/说明输出为代理提供机器可读的规划上下文。
- 保持工作区边界：设置/更新期间链接的仓库和文件夹保持未触及。

**非目标：**
- 在工作区设置中生成斜杠命令。
- 通过生成工作区命令文件来遵守全局 `delivery: commands`。
- 将技能安装到链接的仓库或文件夹。
- 添加独立于全局配置的工作区本地工作流配置文件。
- 在第一个设置技能步骤中解决工作区范围的工件路径发现。
- 在第一个版本中添加单独的工件上下文 CLI 命令。
- 端到端实现工作区应用、验证或归档语义。
- 更改仓库本地的 `openspec init` 或 `openspec update` 行为。

## 决策

### 在工作区 UX 中使用代理技能语言

工作区设置应询问"哪些代理应在此工作区中获得 OpenSpec 技能？"，而不是使用更宽泛的"AI 工具"措辞。用户可见的操作是为编码代理安装技能，目标是工作区规划主目录。

考虑的替代方案：直接复用 `init` 的措辞。这虽熟悉，但它隐藏了打开工作区和向工作区安装技能之间的重要区别。

### 复用现有的工具 ID 模型

CLI 应对非交互式设置和更新使用现有的 `--tools all|none|<ids>` 语法。复用现有工具 ID 避免了为相同的已配置代理发明第二个命名系统。

考虑的替代方案：添加 `--agents`。这单独看可读性更好，但它会在 `openspec init --tools` 旁边产生不必要的并行词汇。

### 让配置文件选择工作流，工具选择代理

工作区设置/更新应使用活动的全局配置文件来决定安装哪些 OpenSpec 工作流技能。配置文件回答"哪些操作可用？"，而 `--tools` 回答"哪些代理获得这些操作？"保持这些关注点分离，保留了现有的配置文件模型，并避免了在此切片中添加工作区本地工作流选择。

如果全局配置是 `core`，工作区技能应包括核心工作流集。如果全局配置是 `custom`，工作区技能应仅包括已配置的自定义工作流。`--tools none` 仍应意味着不安​​装任何代理技能，无论配置文件如何。

考虑的替代方案：添加工作区本地配置文件。对于团队共享的工作区默认值，这可能在以后有用，但此切片已存储机器本地代理路径，应在全局配置文件行为生效之前避免引入另一个配置权限。

### 尽可能预选首选打开程序

交互式设置应在首选打开程序映射到具备技能能力的代理时预选它。用户可以接受默认值、添加更多代理或取消选择。

考虑的替代方案：仅为首选打开程序安装技能。这更简单，但打开程序选择意味着"我应该如何打开这个工作区"，而技能选择意味着"哪些代理应该理解这里的 OpenSpec"。

### 持久化所选的工作区技能代理本地状态

工作区设置应将所选的有技能能力的代理存储在 `.openspec-workspace/local.yaml` 中，因为代理路径和已安装的工具表面是机器本地的。当用户未传递 `--tools` 或进行新的交互式选择时，工作区更新应使用该存储的选择。

工作区设置/更新上的显式 `--tools` 应替换存储的选择。`--tools none` 应存储空选择，并仅移除已知的 OpenSpec 管理工作区技能目录。

本地状态还应记录足够的最后应用信息以支持差异检测，例如为每个所选代理安装的工作流 ID 以及最后成功同步时的有效全局配置文件/交付。这是诊断状态，不是第二真实源。

考虑的替代方案：通过扫描 `.codex/skills/`、`.claude/skills/` 等目录来推断所选代理。扫描作为回退方案很有用，但持久化的选择提供了可预测的更新行为，并避免将用户自建的文件视为 OpenSpec 管理的状态。

### 保持非交互式设置向后兼容

`openspec workspace setup --no-interactive` 不应要求 `--tools`。如果省略 `--tools`，设置应创建工作区并跳过技能安装，保留现有的脚本化工作区设置行为。人类和 JSON 输出应说明未安装工作区技能，以及 `openspec workspace update --tools <ids>` 可以稍后添加它们。

不带 `--tools` 的 `openspec workspace update --no-interactive` 应刷新存储的工作区技能代理选择。如果未存储选择，它应在不安装技能的情况下完成，并报告清晰的无操作指导，要求传递 `--tools`。

考虑的替代方案：只要工作区设置/更新是非交互式的，就要求 `--tools`。这镜像了仓库本地 init，但会破坏早于工作区本地技能安装的现有工作区设置脚本。

### 仅生成工作区本地技能

工作区设置/更新应在工作区根目录下生成技能，例如 `.codex/skills/` 或 `.claude/skills/`。在此切片中不应生成斜杠命令，因为某些命令适配器解析到全局位置，而工作区设置应保持本地和可预测。

当全局交付为 `commands` 或 `both` 时，工作区设置/更新仍应仅生成技能，并报告工作区命令生成不在此切片范围内。这保持了配置文件工作流选择的有用性，而无需工作区设置执行全局或仓库本地命令写入。

考虑的替代方案：完全镜像 `init`，同时生成技能和命令。这有风险，可能会产生意外的全局写入，并使设置边界更难解释。

### 添加 `workspace update` 用于技能刷新

`openspec workspace update` 应在设置后刷新、添加或移除工作区本地的 OpenSpec 技能。从工作区内部运行时，它应解析当前工作区，并支持命名和非交互式形式。

工作区更新应将活动全局配置文件的工作流选择与最后应用的工作区技能状态进行比较。如果不同，更新应为所选代理仅添加/移除 OpenSpec 管理的工作流技能目录。工作区 doctor/list/status 表面可以将差异报告为警告，工作区内部的 `openspec config profile` 无操作应使用相同的差异检查来提供指导。

考虑的替代方案：从工作区内部复用 `openspec update`。该命令当前意味着仓库/项目更新，而工作区更新需要工作区选择、工作区 JSON/状态行为和链接仓库安全规则。

### 使 `config profile` 感知工作区

`openspec config profile` 应保持为全局配置命令。当它在仓库本地 OpenSpec 项目内部运行且用户选择应用更改时，它应继续运行 `openspec update`。

当它在 OpenSpec 工作区内部运行且配置文件或交付设置实际更改时，它应提示将更改应用于当前工作区。如果确认，它应为该工作区运行 `openspec workspace update`。如果拒绝，它应解释全局配置已更改，用户可以稍后运行 `openspec workspace update`。

预设快捷方式 `openspec config profile core` 应保持其非交互式特性，不启动应用提示。当从工作区内部运行时，它应保存全局配置并打印工作区特定的后续指导，提示运行 `openspec workspace update`。当在仓库本地项目内部运行时，它应保持现有的仓库本地指导。

在此切片中，自动工作区上下文应来自工作区规划主目录及其自己的子目录。从链接的仓库或文件夹内部运行命令应保持该位置的仓库本地行为，除非用户通过工作区命令选项显式选择工作区。这避免了仅仅因为仓库注册为工作区链接而使仓库本地命令出现意外。

如果目录同时位于工作区规划主目录内部和仓库本地 OpenSpec 项目内部，最近的主目录应确定应用提示。这避免了当用户有意从工作区规划主目录操作时，将工作区配置文件更改应用到链接的仓库。

考虑的替代方案：使 `openspec config profile` 更新所有已知的工作区。在小规模设置中这很方便，但全局配置更改不应在没有显式的每个工作区操作的情况下扇出到多个规划主目录。

### 在操作前解析规划主目录

工作流命令应在计算路径之前，解析当前变更属于仓库本地规划主目录还是工作区规划主目录。解析器应识别规划根目录、变更根目录、存在的链接区域以及是否允许实施编辑。链接的仓库不会仅仅因为它们在某个工作区中注册就被隐式视为工作区规划主目录；工作区范围的行为是从工作区规划主目录或通过显式工作区选择来选择的。

考虑的替代方案：在用到路径的地方添加工作区特定的命令分支。这会使工作区模型泄漏到每个工作流中，并使生成的技能更加脆弱。

### 将工作区变更存储在工作区规划路径中

工作区变更应位于工作区规划路径下，最初为工作区根目录下的 `changes/<id>`。创建工作区变更应一次性捕获共享意图，并可以记录受影响的区域，但不应在链接的仓库中创建仓库本地的 `openspec/changes/<id>` 目录。

考虑的替代方案：在工作区变更创建期间，在每个受影响的仓库中物化一个仓库本地变更。在 POC 中这很容易推理，但它过早提交，使探索看起来像实施。

### 添加工作区规划模式

工作区范围的变更默认应使用内置的 `workspace-planning` 模式。这保持了工作流动词的熟悉性，同时让工作区变更具有适合跨区域规划的结构。

初始工件结构：

```text
changes/<id>/
  .openspec.yaml          # schema: workspace-planning
  proposal.md             # 共享目标和范围
  design.md               # 跨区域决策
  tasks.md                # 协调任务，可选地按受影响的区域分组
  specs/
    <区域或仓库>/
      <能力>/spec.md
```

第一个模式应有意图地保持接近正常的 OpenSpec 工件结构：提案、规范、设计和任务。特定区域的需求位于 `specs/` 下，特定区域的工作可以用 `tasks.md` 中的章节表示。此切片不会在这些正常规划工件之外引入另一个区域清单。

考虑的替代方案：不变地复用 `spec-driven`，并使所有工作区差异隐含在状态输出中。这隐藏了工作区规划需要不同指令来按受影响区域组织需求和任务的事实。

考虑的替代方案：创建单独的工作区工作流技能而不是模式。这会重复工作流指导，并使工作区模式感觉像不同的产品。

### 在模式中支持嵌套的工作区规范路径

`workspace-planning` 模式应定义其规范工件，使嵌套的工作区路径成为一等公民，而不是偶然的。预期的输出模式是 `specs/**/*.md`，模式说明应明确描述 `specs/<区域或仓库>/<能力>/spec.md` 作为区域特定需求的默认约定。

状态和说明输出应保留其发现的具体嵌套路径。假设 `specs/<能力>/spec.md` 的仓库本地规范同步、归档和验证路径，不应将工作区范围的规范视为仓库本地能力规范，直到后续的显式实施、同步或归档工作流选择受影响的区域并定义目标。

### 使用受影响的区域，而非目标或仓库切片

规划模型应将所有权或实施边界称为"受影响的区域"。受影响的区域可以从已注册的工作区链接名称开始，但语言应留有空间给文件夹、包、服务、应用或文档站点。交付分解仍然是独立的概念，不应被称为区域。

考虑的替代方案：保留"目标"，因为它映射到旧的 POC 标志。该术语是实施优先的，鼓励用户在计划明确之前选择仓库。

### 使状态 JSON 成为代理上下文契约

`openspec status --change <id> --json` 应成为机器可读操作上下文的主要来源。它应包括规划主目录、变更根目录、具体的工件路径、受影响的区域、下一步和约束，例如当实施在范围内时的允许编辑根。

考虑的替代方案：立即创建一个单独的上下文命令。状态已被生成的工作流技能使用，因此首先丰富它给代理提供了一个单一的查找位置。

### 保持生成的技能路径无关

生成的工作流技能应询问 OpenSpec 工件的存放位置，而不是嵌入仓库本地路径，例如 `openspec/changes/<name>`。标准技能模式应为：

```text
1. 运行 `openspec status --change "<name>" --json`。
2. 使用返回的规划主目录、工件、下一步和操作上下文。
3. 在编写工件之前运行 `openspec instructions <artifact> --change "<name>" --json`。
4. 写入 CLI 返回的解析路径。
```

这使同一技能在仓库本地和工作区范围的变更中可用。如果状态/说明输出后来变得过于拥挤，可以在未来的变更中引入单独的上下文命令，而无需更改高级技能规则。

考虑的替代方案：立即添加新的 `openspec context` 命令。这以后可能有用，但它在证明丰富的状态/说明不足之前添加了新的表面。

### 保护不受支持的工作区工作流操作

全局配置文件可能选择在此切片中尚未实现工作区范围行为的工作流，例如完整的工作区应用、验证或归档。为这些工作流生成的本地技能应是安全的：它们应检查状态/说明，解释不受支持的工作区操作，并避免编辑链接的仓库，除非后来的显式实施工作流提供了允许的编辑根。

这使工作区技能集与用户的配置文件保持一致，同时防止仓库本地回退假装实现工作区语义。

考虑的替代方案：过滤掉工作区技能生成中不受支持的工作流。这可以避免不受支持的命令，但会使工作区技能集与用户的配置安静地产生分歧，并使差异更难解释。

### 从工作区根重定向仓库更新

`openspec update` 应保持为仓库/项目更新命令。当从 OpenSpec 工作区规划主目录运行时，它不应尝试将工作区视为仓库本地项目。它应失败或重定向，并给出清晰的指导，提示运行 `openspec workspace update`。

考虑的替代方案：使 `openspec update` 多态，在工作区内执行工作区更新。这很方便，但它模糊了此变更试图明确的仓库/项目与工作区边界。

### 更新文档、帮助和补全

CLI 帮助、命令注册表/补全和用户文档应包括 `openspec workspace update`、其 `--tools` 行为、全局配置文件关系以及仅技能工作区交付规则。

考虑的替代方案：仅在实施后记录。由于配置文件/更新行为容易与仓库本地更新混淆，因此文档和帮助更新是面向用户功能的一部分。

### 将验收和 UX 审查视为阶段关口

每个阶段应产生用户可测试的增量，即使大部分工作是内部的。在用户可以通过 CLI 行使命名的行为、检查输出或文件并理解变更内容之前，该阶段不算完成。

每个实施阶段除了自动化测试外，还应包括手动验收。手动验收应行使真实的 CLI 流程，检查生成的文件或输出，并在合同要求时确认链接的仓库或文件夹保持未触及。

每个阶段还应包括对提示、命令形式、人类输出、JSON 输出、工件路径和下一步指导的轻度 UX 审查。审查中发现任何令人困惑的 UX 应在同一阶段修复，或记录为有意的后续事项，然后该阶段才被视为完成。

考虑的替代方案：仅在最终验证阶段保留审查。这会在端到端方面发现问题的较晚，但工作区规划主要是工作流和面向代理的 UX，因此每个阶段需要在行为仍新鲜时进行各自的人工检查。

### 用基于证据的审查减少自我验证偏见

实施应在标记任务完成前定义验收证据。对于每个阶段，实施者应捕获确切的手动命令或交互路径、预期观察和实际观察。一个任务不能仅仅因为实施者认为代码符合设计就算完成。

当可行时，单独的审查者或新的代理上下文应仅使用变更工件、CLI 输出和观察到的文件系统状态来运行手动验收检查清单和 UX 审查。如果没有单独的审查者，实施者应从干净的临时工作区重新运行检查清单，并在变更说明或最终实施摘要中记录证据。

考虑的替代方案：依赖自动化测试加上实施者的最终审查。自动化测试是必要的，但此变更是工作流密集型和面向代理的，因此独立证据比仅有信心更有用。

## 推迟的方向

早期的产品说明指向比此切片交付的更丰富的工作区模型。将该方向保持为后续材料，而不是竞争的当前范围。

- 完整的工作区应用应在实施前选择或确认一个工作焦点。第一个工作焦点应是具有允许编辑根的受影响区域；后续工作可以在大型变更需要排序时添加可选的交付阶段。在此模型存在之前，工作区应用/验证/归档技能保持受保护。
- 工作区验证和归档应等待部分区域完成、最终整体变更完成以及工作区范围规范如何成为仓库本地规范标准的清晰模型。
- 作用域计划文件最终可能附加在变更、阶段、受影响区域或工作焦点级别。此切片有意使第一个工作区模式接近正常的 OpenSpec 工件：提案、规范、设计和任务。
- 受影响的区域可以从已注册的工作区链接名称开始，但未来的流程可以完善或从规划工件中推导它们。该推导应避免重新引入目标优先或仓库切片语言。
- 工作流技能以后可能将通用 OpenSpec 工作流语义与特定于代理的功能（如提问、跟踪待办事项或委派工作）分开。此切片仅使生成的工作流技能路径无关。
- OpenSpec 可能需要一个命名的探索性笔记约定，用于在将其提升为提案、设计、规范或任务之前保留未确定的思考。此清理使当前变更文件夹专注于标准工件。

## 风险 / 权衡

- 技能生成逻辑可能与 `init/update` 有差异 → 在实际可行时共享相同的模板生成和工具验证助手。
- 移除未选中的技能可能移除用户修改的文件 → 仅按显式工作流列表移除已知的 OpenSpec 管理工作流技能目录。
- `--tools` 在工作区 UX 中不如 `--agents` 精确 → 保持 `--tools` 以实现 CLI 一致性，但在提示和人类输出中使用"代理"。
- 全局交付可以说 `commands` 而工作区更新保持仅技能 → 显式报告此情况，以便用户知道命令生成被推迟，而非静默失效。
- `config profile` 可能从已打开工作区内的链接仓库运行 → 仔细解析当前规划主目录并仅应用于该主目录。
- 存储的工作区技能状态可能过时或手动编辑 → 将其视为诊断性的机器本地状态，并在更新期间始终从活动全局配置文件协调管理的文件。
- 配置文件选中的工作流可能尚未具备完整的工作区语义 → 生成的技能必须保护不支持的操作并避免仓库本地回退。
- 现有的生成技能仍包含仓库本地路径假设 → 在工作区本地技能可以安装后，将其作为后来的工件上下文步骤处理。
- 状态 JSON 可能变得过于宽泛 → 保持字段简洁且以操作为导向，例如 `planningHome`、`artifacts`、`affectedAreas`、`nextSteps` 和 `actionContext`。
- 受影响区域发现可能模糊 → 从显式的已注册工作区链接开始，并允许后续精炼，而不是将自由格式的 Markdown 标题解析为唯一的真实源。
- 新模式可能与仓库本地工作流期望有差异 → 保持工件 ID 简洁，让状态/说明携带模式特定的路径。
- 技能说明可能落后于 CLI 行为 → 审计源工作流模板中硬编码的仓库本地路径，并用路径无关的状态/说明模式替换它们。
