## 新增需求

### 需求：工作区感知的变更创建
变更创建应同时支持仓库本地和工作区规划目录。

#### 场景：从工作区根目录创建变更
- **给定** 命令从 OpenSpec 工作区根目录运行
- **当** 用户创建新变更时
- **则** OpenSpec 应在工作区规划路径下创建变更
- **并且** 不应在链接仓库的 `openspec/changes/` 目录下创建变更
- **并且** 当未提供显式 schema 时，应使用 `workspace-planning` schema

#### 场景：从工作区内部创建变更
- **给定** 命令从 OpenSpec 工作区规划目录的子目录运行
- **当** 用户创建新变更时
- **则** OpenSpec 应将当前工作区解析为规划目录
- **并且** 应在此工作区的规划路径下创建变更
- **并且** 当未提供显式 schema 时，应使用 `workspace-planning` schema

#### 场景：从链接仓库内部创建变更
- **给定** 仓库或文件夹已注册为工作区链接
- **并且** 命令从该链接仓库或文件夹内部运行，而非工作区规划目录
- **当** 用户创建新变更但未显式选择工作区
- **则** OpenSpec 应为该位置保留仓库本地变更创建行为
- **并且** 不应仅因为该位置注册为工作区链接就创建工作区范围的变更

#### 场景：保留仓库本地变更创建
- **给定** 命令在 OpenSpec 工作区外部运行
- **当** 用户在仓库本地 OpenSpec 项目中创建新变更
- **则** OpenSpec 应继续在 `openspec/changes/` 下创建变更

#### 场景：拒绝无效的工作区影响区域
- **给定** 工作区变更创建请求包含影响区域名称
- **当** 一个或多个名称不是已注册的工作区链接
- **则** OpenSpec 应拒绝这些无效的影响区域
- **并且** 应列出有效的工作区链接名称

#### 场景：无影响区域创建
- **给定** 用户仍在探索范围
- **当** 用户创建工作区变更时没有影响区域
- **则** OpenSpec 应创建工作区变更
- **并且** 应允许稍后识别影响区域
