## 新增需求

### 需求：工作区变更规划中心
OpenSpec 应支持工作区级别的变更，其共享计划位于工作区规划中心。

#### 场景：创建工作区变更
- **给定** 命令从 OpenSpec 工作区运行
- **当** 用户创建工作区规划的变更
- **那么** OpenSpec 应在工作区规划路径下创建变更
- **并且** 应将工作区视为该变更的规划中心
- **并且** 当未提供显式模式时，应使用工作区规划模式

#### 场景：工作区规划工件结构
- **给定** 工作区变更使用工作区规划模式
- **当** OpenSpec 报告或创建该变更的规划工件
- **那么** 应使用工作区级别的工件用于 proposal、specs、跨区域设计和协调任务
- **并且** 这些工件应位于工作区变更根目录下
- **并且** 不应要求在这些正常规划工件之外额外添加区域清单

#### 场景：一次性捕获共享目标
- **当** 提出工作区变更时
- **那么** OpenSpec 应在工作区变更级别捕获产品目标
- **并且** 应避免在了解受影响区域之前要求单独的仓库本地 proposal

#### 场景：在变更创建期间保留链接仓库
- **当** OpenSpec 创建工作区级别的变更时
- **那么** 不应在链接的仓库或文件夹内创建仓库本地的 OpenSpec 变更目录
- **并且** 不应编辑链接仓库或文件夹中的实现文件

### 需求：工作区受影响区域
OpenSpec 应将工作区变更中的所有权或实现边界表示为受影响区域。

#### 场景：使用注册的工作区链接作为区域
- **给定** 工作区有链接的仓库或文件夹
- **当** 工作区变更通过注册的链接名称标识受影响区域
- **那么** OpenSpec 应针对工作区链接验证这些区域名称
- **并且** 应清晰报告无效的区域名称

#### 场景：在所有区域确定之前进行规划
- **当** 用户仍在探索工作区变更时
- **那么** OpenSpec 应允许在所有受影响区域确定之前存在共享计划
- **并且** 应在正常的规划工件和状态输出中保持未解决的受影响区域问题可见

#### 场景：按区域组织需求
- **给定** 工作区变更的需求由一个或多个受影响区域拥有
- **当** OpenSpec 报告或创建工作区范围的规范
- **那么** 应允许将特定区域的需求组织在 `specs/<区域或仓库>/<能力>/spec.md` 下
- **并且** 不应要求在正常的 `specs/` 工件树之外设置单独的区域文件夹
- **并且** 应保留区域或仓库路径段作为工作区规划上下文，而不是将其扁平化为仓库本地的能力名称

#### 场景：区分区域与交付切片
- **当** 工作区变更报告受影响区域时
- **那么** OpenSpec 应区分受影响区域与交付切片或阶段
- **并且** 不应要求用户为小型跨区域变更定义交付切片

### 需求：工作区规划事实源头
OpenSpec 应将工作区变更计划作为事实源头，直到选定受影响区域的实现开始。

#### 场景：在实现之前进行探索
- **当** agent 探索工作区变更时
- **那么** 应使用工作区级别的规划工件作为共享规划源
- **并且** 应将链接的仓库和文件夹视为可用上下文，而不是已承诺的实现目标

#### 场景：推迟仓库本地实现
- **当** 工作区变更需要仓库本地的实现工作
- **那么** OpenSpec 应要求使用选定的受影响区域进行显式的实现工作流
- **并且** 应在实现编辑开始前暴露该选定区域的允许编辑根目录
