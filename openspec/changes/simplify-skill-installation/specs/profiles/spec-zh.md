## 目的

配置文件应定义安装哪些工作流，使新用户能够获得简化的核心体验，同时允许高级用户自定义其工作流选择。

## 新增需求

### 需求：配置定义
系统应支持两个工作流配置：`core` 和 `custom`。

#### 场景：核心配置内容
- **当** 配置设置为 `core`
- **那么** 该配置应包含工作流：`propose`、`explore`、`apply`、`archive`

#### 场景：自定义配置内容
- **当** 配置设置为 `custom`
- **那么** 该配置应仅包含全局配置 `workflows` 数组中指定的工作流

### 需求：交付独立于配置
交付设置应控制工作流的安装方式（技能、命令或两者兼有），与安装哪些工作流分开。

#### 场景：交付选项
- **当** 配置交付时
- **那么** 系统应支持三个选项：`both`（技能和命令）、`skills`（仅技能文件）、`commands`（仅命令文件）

#### 场景：两者交付
- **当** 交付设置为 `both`
- **那么** 系统应为每个工作流同时安装技能文件和命令文件

#### 场景：仅技能交付
- **当** 交付设置为 `skills`
- **那么** 系统应为每个工作流仅安装技能文件
- **那么** 系统应不安装命令文件

#### 场景：仅命令交付
- **当** 交付设置为 `commands`
- **那么** 系统应为每个工作流仅安装命令文件
- **那么** 系统应不安装技能文件

#### 场景：带自定义交付的核心配置
- **当** 配置设置为 `core`
- **并且** 交付设置为 `skills`
- **那么** 系统应将核心工作流仅安装为技能（无命令）

#### 场景：交付默认值
- **当** 全局配置中未设置交付
- **那么** 系统应默认为 `both`

### 需求：通过交互式选择器进行配置配置
系统应提供用于配置配置的交互式选择器。

#### 场景：交互式配置配置
- **当** 用户运行 `openspec config profile`
- **那么** 系统应显示交互式选择器，包含：
  - 交付选择：`skills`、`commands`、`both`
  - 所有可用工作流的工作流开关
- **那么** 系统应预选当前配置值
- **那么** 确认后，系统应更新全局配置
- **那么** 如果选择的工作流与核心默认值不同，系统应将配置设置为 `custom`
- **那么** 如果选择的工作流与核心默认值完全匹配（propose、explore、apply、archive），无论交付设置如何，系统应将配置设置为 `core`
- **那么** 系统应不修改任何项目文件
- **那么** 系统应显示："配置已更新。在你的项目中运行 `openspec update` 以应用。"

#### 场景：核心预设快捷方式
- **当** 用户运行 `openspec config profile core`
- **那么** 系统应将配置设置为 `core`
- **那么** 系统应将工作流设置为 `['propose', 'explore', 'apply', 'archive']`
- **那么** 系统应不更改交付设置（保留用户偏好）
- **那么** 系统应不修改任何项目文件
- **那么** 系统应显示："配置已更新。在你的项目中运行 `openspec update` 以应用。"
- **那么** 新配置将在下次运行 `openspec init` 或 `openspec update` 时生效

#### 场景：在项目内运行配置配置
- **当** 用户在 OpenSpec 项目目录内运行 `openspec config profile`
- **那么** 更新全局配置后，系统应提示："立即应用于此项目？(y/n)"
- **当** 用户确认时
- **那么** 系统应自动运行 `openspec update`
- **那么** 系统仍应显示："在你的其他项目中运行 `openspec update` 以应用。"

#### 场景：配置配置 - 用户拒绝应用
- **当** 用户在 OpenSpec 项目目录内运行 `openspec config profile`
- **并且** 用户拒绝"立即应用于此项目？"提示
- **那么** 系统应显示："配置已更新。在你的项目中运行 `openspec update` 以应用。"
- **那么** 系统应成功退出，不修改项目文件

#### 场景：非交互式配置配置
- **当** 用户以非交互方式运行 `openspec config profile`（例如，在 CI 中，无 TTY）
- **那么** 系统应显示错误："需要交互模式。使用 `openspec config profile core` 或通过环境变量/标志设置配置。"
- **那么** 系统应以退出码 1 退出

### 需求：配置设置存储在全局配置中
配置和交付设置应存储在现有的全局配置文件中（`~/.config/openspec/config.json`），与遥测和功能标志一起。

#### 场景：配置模式
- **当** 读取配置配置时
- **那么** 配置应包含 `profile`（core|custom）、`delivery`（both|skills|commands）以及可选的 `workflows`（工作流名称数组）

#### 场景：模式演进
- **当** 加载没有配置/交付字段的配置时
- **那么** 系统应使用默认值（profile=core、delivery=both）
- **并且** 现有的配置字段（telemetry、featureFlags）应被保留

#### 场景：配置列表显示配置文件设置
- **当** 用户运行 `openspec config list`
- **那么** 系统应显示配置、交付和工作流设置
- **并且** 应指示哪些值是默认值，哪些是显式设置的

### 需求：配置是全局的，项目是显式的
配置更改不应自动传播到项目。

#### 场景：配置更新不修改项目
- **当** 用户通过 `openspec config profile` 更新配置
- **那么** 系统应仅更新全局配置（`~/.config/openspec/config.json`）
- **那么** 系统应不修改任何项目技能/命令文件
- **那么** 现有项目保留其当前工作流文件，直到用户运行 `openspec update`

### 需求：通过更新命令应用配置更改
现有的 `openspec update` 命令应将当前全局配置应用到项目。有关详细的更新行为，请参见 `specs/cli-update/spec.md`。

#### 场景：配置更改需要显式项目同步
- **当** 用户通过 `openspec config profile` 更新配置或交付
- **那么** 全局配置应立即更新
- **并且** 项目文件应保持不变，直到对该项目运行 `openspec update`

### 需求：配置默认值
系统应将 `core` 作为新用户的默认配置，同时通过迁移保留现有用户的工作流。

#### 场景：无全局配置（新用户）
- **当** 全局配置文件不存在
- **并且** 项目中未安装现有工作流
- **那么** 系统应表现得如同配置是 `core`

#### 场景：全局配置存在但配置字段缺失（新用户）
- **当** 全局配置文件存在但不包含 `profile` 字段
- **并且** 项目中未安装现有工作流
- **那么** 系统应表现得如同配置是 `core`

#### 场景：配置字段缺失但存在现有工作流（现有用户迁移）
- **当** 全局配置不包含 `profile` 字段
- **并且** `update` 命令检测到项目中的现有工作流文件
- **那么** 系统应执行一次性迁移（详见 `specs/cli-update/spec.md`）
- **那么** 系统应将配置设置为 `custom`，并使用检测到的工作流
- **那么** 系统应在迁移期间不添加或移除任何工作流文件
