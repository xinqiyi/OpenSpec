## 为什么

状态：已被 context-store-and-initiatives 方向推迟。生成的工作区指导仍然重要，但持久交接应围绕与仓库本地 OpenSpec 变更关联的倡议进行设计，而非围绕工作区拥有的跨仓库规划归属。

其余部分保留了原始的工作区代理指导方向，供日后参考。这项工作在倡议和与倡议关联的仓库本地变更出现后仍具有重要意义；但目前不是最优先的关注点。

OpenSpec 工作区允许用户创建规划归属并链接仓库或文件夹以进行跨区域探索。设置完成后，用户的下一期望很简单：

> 我用代理打开了工作区。代理应该知道它在哪里，可以安全地检查什么，以及如何帮助我把产品目标转化为工作区提案。

如今这种交接过于薄弱。工作区本地技能已安装，CLI 可以创建工作区范围的变更，但代理的行为仍然大多像是在普通的仓库本地 OpenSpec 项目中。在创建变更之前，它们没有清晰的工作区原生起始模型。

这造成了可以避免的困惑：

- 链接的仓库或文件夹可能看起来像是实施目标，而非只读的规划上下文
- 代理可能不知道哪些已注册的链接名称是有效的受影响区域
- 用户可能感到在规划开始之前就需要知道每个受影响区域
- 产品目标可能在工作区探索和变更创建之间丢失
- 工作区规划可能感觉像是一种独立的模式，而非跨链接区域的普通 OpenSpec

此项变更应强化的原则是：

> 工作区可见性不等于变更承诺。

链接的仓库和文件夹可供探索。创建工作区变更捕捉了规划承诺。实施编辑仍需明确的工作流和允许的编辑根路径。

## 目标

使工作区本地规划技能为代理提供一个小型、可靠的操作模型，用于启动工作区提案。

在工作区中打开的代理应能够：

1. 识别其正在从工作区规划归属运行
2. 检查已注册的工作区链接作为规划上下文
3. 在规划期间保持链接的仓库和文件夹为只读
4. 从用户请求中推导出简洁的工作区变更名称和产品目标
5. 仅在已知的受影响区域匹配已注册的工作区链接名称时传递它们
6. 即使受影响区域尚未解决也能继续，使这些问题在正常规划工件中保持可见

这对用户来说应该感觉像是普通的 OpenSpec 提案流程，只是多了工作区感知的上下文和安全性。

## 初始范围

从最小的有用表面开始：

- 工作区本地生成的技能指导
- 从工作区规划归属使用的变更启动工作流
- 用户产品目标、已注册链接名称和工作区变更元数据之间的关系
- 将规划与实施编辑分开的护栏

首次实施应优先选择清晰的代理指导，而非新的工作流机制。如果现有 CLI 已暴露足够的工作区上下文，技能应使用它。如果不够，应在添加更重量的行为之前明确识别缺失的上下文。

## 非目标

此项变更无需解决完整的工作区生命周期。

此切片范围之外：

- 工作区应用语义
- 工作区验证或归档语义
- 分支或工作树编排
- 为每个受影响区域创建仓库本地变更
- 共享/团队协作仓库行为
- 规范的共享合约所有权流程
- 强制用户在创建提案之前确定所有受影响区域

## 需要解决的问题

- 代理在创建变更之前应读取哪些确切的工作区上下文？
- 现有的 workspace/status/doctor 输出是否足够，还是我们需要一个更清晰的变更前上下文命令？
- 生成的技能应如何决定受影响区域足够确定可以传递为 `--areas`？
- `--goal` 应该是仅工作区的元数据，还是也应记录仓库本地行为？
- 未解决的受影响区域问题应出现在哪里，以便用户和代理从同一真实来源继续？
