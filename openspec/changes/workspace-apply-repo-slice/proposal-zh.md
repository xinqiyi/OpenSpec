## 为什么

状态：已被上下文存储和倡议方向推迟。apply 即实现的原则仍然有用，但持久化的交接应围绕链接到仓库本地 OpenSpec 变更的倡议来设计，而不是围绕工作区拥有的跨仓库计划。在此链接存在之前，不要将其作为一等公民的工作区生命周期命令实现。

剩余部分保留了原始的工作区 apply 方向以供后续参考。在倡议和与倡议链接的仓库本地变更存在后，这项工作仍预计会发挥作用；它不是当前立即关注的重点。

在工作区 proposal 存在之后，用户需要一种实用的方式来一次实现一个仓库切片。

在适当的工作区模型中，apply 意味着实现：

```text
获取选定的工作区变更。
获取选定的仓库切片。
打开或使用正确的检出。
实现该切片，同时保留工作区计划。
```

它不应意味着将规划文件复制或物化到每个仓库中作为用户面对的工作流。

## 变更内容

添加工作区变更的仓库切片 apply 工作流：

- 选择一个工作区变更
- 选择一个目标仓库别名
- 解析该别名的本地检出
- 向 agent 提供工作区计划和仓库特定的实现上下文
- 跟踪进度，不使工作区失去对计划的所有权

该工作流应支持跨不同分支或会话的实现，同时保持工作区 proposal 作为连续性层。

规划依赖：

- 依赖于 `workspace-change-planning`。

## 能力

### 新能力

- `workspace-repo-slice-apply`：将工作区变更的一个仓库切片作为实现工作流应用。

### 修改的能力

- `cli-artifact-workflow`：将工作区 apply 定义为实现而非物化。
- `context-injection`：从工作区变更提供仓库特定的实现上下文。

## 影响

- 工作区 apply 命令行为。
- 用于仓库切片实现的 agent 交接文本。
- 本地检出解析和分支/工作树假设。
- 测试 apply 操作在一个目标仓库切片上运行，并且不需要复制工作区规划工件作为主要用户契约。
