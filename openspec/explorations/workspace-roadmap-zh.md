# workspace 路线图

## 目的

本文档为 OpenSpec 中的 workspace、monorepo 和多 repository 支持提出一个轻量级路线图。

它假定：

- 单 repository 是当前默认体验
- monorepo 的痛点已经真实存在
- 多 repository 协调并非假设
- 大型工程组织已经需要这个

这个路线图有意分阶段进行。

目标不是一次性构建完整的概念系统。

目标是在交付跨边界支持的最小可信版本的同时，保留通往更强长期模型的路径。

---

## 产品原则

> 选择能解决真实跨边界工作且不妨碍长期方向的最小功能集。

这意味着：

- 不要在使用证明之前过度构建治理
- 如果真实团队已经需要协调，也不要构建不足
- 如果不能满足成本效益，不要为单 repository 路径增加复杂性

---

## 我们现在的信念

基于当前的探索工作，有几件事越来越清晰。

### 1. 嵌套 spec 组织是需要的

OpenSpec 需要更好的方式来组织：

- 共享契约
- 本地实现 spec
- 单根内的多领域行为

### 2. 信息性引用风险低且有用

引用帮助 agent 和人类导航相关 spec，而无需 OpenSpec 在第一天就构建依赖图系统。

### 3. 行动倡议加链接的每个 repository 变更是正确的原语

对于真正的多 repository 工作，可能的持久原语是：

- 一个行动倡议作为共享 planning 对象
- 每个拥有 repository 一个链接的变更作为执行产物
- 连接它们的稳定标识符

### 4. 跨 repository 工作需要一个中立的 planning 位置

对于多 repository 工作，单个 repository 不是整个 planning 产物的诚实家园。

某种形式的协调 workspace 或协调 repository 对于行动倡议级计划是必要的。

### 5. 团队共享协调是一个真实需求

这不仅仅是单人用户的思想实验。

真实团队和大型工程组织已经需要一种协调多 repository 工作的方式。

### 6. 风险是一次性交付太多

即使需求是真实的，完整模型也有许多移动部分：

- 嵌套 spec 路径
- 共享契约
- 链接的变更
- 跨根 planning
- 部分 repository 解析
- Agent 能力差异
- 团队共享协调状态

路线图应仔细排序这些内容。

---

## 阶段 1：单根内更好的结构

### 目标

在不引入协调机制的情况下减少单 repository 和 monorepo 设置中的痛点。

### 交付

1. 单个 `openspec/` 根内的嵌套 spec 路径
2. spec 中的信息性 `references`
3. planning 期间更好的相关 spec 路径过滤
4. 单根内多领域变更的更好处理

### 用户价值

- monorepo 用户可以更自然地将共享和本地 spec 组织起来
- 大的根变得不那么嘈杂
- 单根内的共享契约变得更容易建模

### 暂不交付

- 协调 workspace
- 链接的多 repository 变更
- 团队共享协调 repository
- 发起人/拥有者 workflow 机制

### 成功标准

- 用户可以在不将一切扁平化到顶层的情况下建模大型 monorepo
- 用户可以在一个根内表示共享契约
- planning 上下文变得更小、更相关

---

## 阶段 2：薄层跨 repository 协调

### 目标

用最薄的可信协调层支持真实的多 repository planning 需求。

### 交付

1. 用于中立法协调 workspace 或协调 repository 中共享 planning 的行动倡议产物
2. 使用稳定项目标识符的链接每个 repository 变更
3. 通过项目 ID 的显式 repository 链接
4. 通过以下方式解析：
 - 显式输入
 - git remote 匹配
5. 部分解析支持
6. 用于协调 planning 的基本 agent 交接指令

### 用户价值

- 用户有一个诚实的立足点进行多 repository 工作
- 跨 repository 计划不再埋在一个 repository 中
- 共享 planning 和 repository 本地执行明确分离
- 所有权留在真实 repository 中
- Agent 可以被告知哪些根重要

### 关键约束

此阶段应保持薄层。

避免：

- 跨 repository 的依赖验证
- 丰富的治理流程
- CLI 中太多新抽象
- 重量级的本地/共享状态语义

### v1 形态

此阶段应感觉像：

- 默认本地 planning
- 在需要时升级为协调行动倡议
- 协调 workspace 中的行动倡议级 planning
- 下面的链接 repository 本地变更

而不是：

- 一个带有许多管理概念的完整第二产品 schema

### 成功标准

- 团队可以协调多 repository 变更，而无需发明临时电子表格或命名约定
- 用户理解 planning 在哪里，实现在哪里
- Agent 能够以操作上可用的方式跨根 planning

---

## 阶段 3：团队共享协调加固

### 目标

使协调 planning 在团队成员和团队之间干净地工作。

### 交付

1. 共享协调 repository/workspace 支持作为第一类 schema
2. 以下内容之间的清晰分离：
 - 已提交的共享行动倡议状态
 - 本地特定机器的路径解析
3. 轻量级重新链接/修复流程
4. 加入行动倡议的团队成员更好的入职体验
5. 共享 workspace 更好的 agent 指令生成

### 用户价值

- 团队可以共享稳定的跨 repository 行动倡议
- 每个团队成员可以将项目 ID 映射到自己的本地克隆
- 新参与者可以在不逆向工程行动倡议设置方式的情况下加入

### 重要约束

此模型的本地端应保持尽可能薄。

理想的本地层是：

- 可重新生成的
- 非权威的
- 在路径解析之外不具有语义重要性

### 成功标准

- 团队共享协调无需将本地路径泄漏到已提交状态中即可工作
- 加入行动倡议感觉轻量
- 维护成本保持可接受

---

## 阶段 4：共享契约和治理成熟

### 目标

支持需要更强契约所有权和更正式跨边界 planning 的组织。

### 仅在需求证明时交付

1. 引导式的共享契约所有权流程
2. 将仅行动倡议的草稿行为提升为 spec 化共享契约
3. 更强的角色可见性：
 - spec 化共享契约拥有者
 - 行动倡议发起人/推动者
4. 可选的 linting 或策略检查
5. 关于缺失拥有者或未解析引用的可选验证

### 用户价值

- 大型组织可以干净地创建持久的共享契约
- 在需要时治理变得明确
- 跨团队所有权变得更容易理解

### 重要约束

这不应成为普通用户的强制要求。

这些功能应保持：

- 选择加入
- 高级
- 与组织复杂性成比例

### 成功标准

- 共享契约 workflow 解决真实组织规模的问题，而不让普通 planning 感觉官僚化

---

## 不应推迟的内容

由于需求已经是真实的，有些东西不应被视为纯未来工作。

### 应该尽快进行

- 嵌套 spec 路径
- 引用
- 行动倡议产物 + 链接变更原语
- 稳定的项目标识符
- 用于多 repository planning 的薄层协调

### 可以等待

- 丰富的所有权 workflow
- 强的依赖语义
- 广泛的策略和治理功能
- 过多的 agent 特定机制

---

## 所有阶段的用户体验护栏

无论什么阶段，用户体验应遵循以下规则。

### 1. 默认本地

用户应从他们当前所在的位置开始。

### 2. 仅在必要时升级

协调 planning 应作为升级路径出现，而不是默认 schema。

### 3. 高级概念大多保持隐式

仅在用户真正需要做决定时才暴露共享拥有者、发起人角色、覆盖和清单等概念。

### 4. spec 化存储跟随所有权

spec 和 repository 本地变更与拥有根共存。

### 5. 共享协调不是 spec 化 spec 存储

协调数据帮助 planning，但不替代事实来源。

### 6. 隐藏的本地状态必须保持薄层

如果 OpenSpec 使用本地路径缓存或特定机器的映射，它们应：

- 可修复
- 可替换
- 非权威的

---

## 可能的交付序列

如果将此路线图转化为实际的变更提议，序列很可能是：

1. 嵌套 spec 路径 + 引用
2. monorepo 范围过滤和多领域 planning 改进
3. 用于共享 planning 的行动倡议产物
4. 跨 repository 的链接变更元数据
5. 用于多 repository planning 的薄层协调 workspace/repository
6. 团队共享协调加固
7. 可选的共享契约成熟功能

---

## 开放风险

### 1. 协调在 v1 中可能仍然过于沉重

即使是薄层协调，如果交接笨拙，可能感觉还是太多。

### 2. 隐藏的本地状态可能变得比预期更重要

如果路径解析或本地 repository 链接变得具有语义重要性，系统将变得更难信任和调试。

### 3. Monorepo 和多 repository 可能意外分叉

产品应抵制演化出两种完全独立的心智模型。

### 4. Agent 能力差异可能扭曲设计

用户体验不应假设每个编码 agent 都同样擅长处理多根 planning。

### 5. 团队规模需求可能对早期治理施加压力

大型组织可能很快要求所有权、权限和审查结构。这不应迫使所有用户进入重量级流程。

---

## 总结

路线图不应该是：

- "等以后再做多 repository"

因为需求已经是真实的。

它也不应该是：

- "现在就构建完整的 workspace 模型"

因为复杂性面太大。

正确的路线图是：

1. 改进单根内的结构
2. 为多 repository 工作交付一个薄层但真实的协调层
3. 加固团队共享协调
4. 仅在合理时添加更正式的共享契约和治理支持
