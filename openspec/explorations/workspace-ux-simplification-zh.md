# 工作区用户体验简化

## 目的

本文档聚焦于一个用户体验目标：

> OpenSpec 应该有一条默认路径、一条升级路径，并且除非系统确实需要用户做出决定，否则向用户展示更少的概念。

本文是对 `workspace-user-journeys.md` 的后续跟进。那份文档在完整性上很有用，但过早地暴露了过多的概念模型。

本文关乎产品应该给用户带来的**感受**。

---

## 用户体验问题

当前的用户旅程探索是连贯的，但在初次接触时过于沉重。

主要问题在于：

1. 用户在什么都没做之前就看到了太多概念：
   - 范围（scope）
   - 项目（project）
   - 拥有根（owning root）
   - 共享契约拥有者（shared contract owner）
   - 协调工作区（coordination workspace）
   - 行动倡议发起人（initiative sponsor）
   - 共享清单 vs 本地覆盖（shared manifest vs local overlay）

2. 跨根工作感觉像是重新开始工作流：
   - 用户从一个仓库开始
   - OpenSpec 说这是多仓库的
   - 用户创建一个工作区
   - 用户在那里重新打开 agent
   - 用户实际上又重新开始了

3. 共享契约的决策被过早且过于明确地询问。

4. 团队级别的协调在概念上是正确的，但读起来更像是基础设施设置而非轻量级工作流。

系统内部是清晰的，但产品体验应该更加渐进。

---

## 设计目标

用户应该感受到：

- "我就在当前位置开始"
- "OpenSpec 会判断这是否需要保持本地化或需要扩展"
- "如果需要扩展，它会带我前进，而不是让我重新开始"
- "只有当 OpenSpec 确实需要我做出决定时，我才会看到高级概念"

---

## 核心用户体验形态

### 一条默认路径

默认路径应该始终是：

1. 进入一个仓库或 monorepo 根目录
2. 运行 `/opsx:explore` 或 `/opsx:propose`
3. OpenSpec 在本地进行规划，除非有充分的理由不这样做

这应该适用于：

- 单个仓库
- 常规 monorepo 工作
- 许多用户在许多情况下

默认假设应该是：

> 在证明需要扩展开来之前，这只是一个本地变更。

### 一条升级路径

唯一的升级路径应该是：

> 这项工作跨越了多个拥有领域，程度足以让 OpenSpec 需要将其升级为协调行动倡议。

这种升级可能发生在以下情况：

- 大型 monorepo 跨团队工作
- 真正的多仓库工作
- 创建共享跨边界契约

重要的用户体验点是，这些都应该感觉像是同一种升级：

- "OpenSpec 正在将此升级为协调行动倡议"

而不是：

- 一种流程用于多仓库
- 另一种流程用于大型 monorepo
- 另一种流程用于共享契约

## 渐进式信息揭示

用户不应该一开始就必须理解完整的数据模型。

### 用户默认应看到的概念

在开始时，用户主要应该看到：

- 变更（change）
- 受影响领域（affected area）
- 如果相关的话，可能还有仓库（repo）

这对于第一步规划来说已经足够了。

### OpenSpec 应保持隐式直到需要时才展示的概念

这些通常应该保持隐藏，直到升级时：

- 范围（scope）
- 协调工作区（coordination workspace）
- 行动倡议（initiative）
- 共享契约拥有者（shared contract owner）
- 发起人/推动者（sponsor/driver）
- 清单 vs 本地覆盖（manifest vs local overlay）

### OpenSpec 仅当需要真正决策时才展示的概念

仅在行动节点展示这些：

- "这跨越多个仓库。是否创建协调行动倡议？"
- "这看起来是共享行为。规范契约应该放在哪里？"
- "此行动倡议是团队共享的。是否要将其提交到共享协调仓库中？"

系统不应将概念作为理论预先加载。

---

## 最简单的用户故事

这是用户体验应该优化的基线故事。

### 故事

用户在一个仓库中并输入：

```text
/opsx:propose add-3ds
```

OpenSpec 应该：

1. 检查本地上下文
2. 推断可能受影响的领域
3. 仅在需要时要求确认
4. 立即继续

用户应该感觉他们只做了一件事：

```text
我在提议一个变更。
```

而不是：

```text
我在多个规划抽象之间做选择。
```

---

## 升级故事

如果 OpenSpec 意识到工作不再是本地化的，它应该一次性升级。

### 期望的感觉

```text
此变更影响多个拥有领域。
我可以将其升级为协调行动倡议，并带你当前的规划上下文一起前进。
```

这个措辞很重要。

它应该感觉像是：

- 一次升级
- 一次延续
- 一种便利

它不应该感觉像是：

- 一个错误
- 一个硬停止
- 一个独立的设置工作流

### 升级期间应该发生什么

如果需要升级，OpenSpec 应尽可能多地自动完成：

1. 携带当前的变更名称/描述
2. 保留已推断出的受影响领域
3. 创建协调工件
4. 解析它能解析的任何本地根
5. 生成 agent 指令
6. 然后告诉用户下一步

### 升级用户体验示例

```text
这项工作跨越多个拥有领域：
- contracts
- billing-service
- web-client
- ios-client

OpenSpec 可以将其升级为协调行动倡议。

建议的下一步：
- 在 ~/work/openspec-workspaces/add-3ds 创建协调工作区

我会携带：
- 你当前的变更描述
- 受影响的仓库
- 已收集的任何规划笔记
```

这比让用户觉得他们必须重新开始要好得多。

---

## 最小决策集

当 OpenSpec 必须提问时，它应该问最有用的最小集合。

### 决策 1：这是本地还是协调的？

最重要的产品问题。

用户面对的形式：

```text
这似乎跨越了多个拥有领域。

我该如何处理？
- 保持为单一的本地变更
- 升级为协调行动倡议
```

这应谨慎使用，且仅在有意义的歧义时才使用。

### 决策 2：哪些领域受影响？

用户面对的形式：

```text
哪些领域受影响？
```

这比先问用户关于"范围"的问题直观得多。

内部这是范围选择，但用户不需要这个术语，除非高级用户想要它。

### 决策 3：这是共享行为吗？

仅当 OpenSpec 有强烈证据表明存在跨边界契约时才询问。

用户面对的形式：

```text
这看起来像是多个领域需要遵循的行为。

我应该将其视为：
- 仅本地变更
- 一个共享契约
- 暂时作为草稿协调笔记
```

### 决策 4：共享所有权应该放在哪里？

仅当用户确认了共享契约行为且没有明显的现有拥有者时才询问。

用户面对的形式：

```text
规范共享契约应该放在哪里？
```

这应该晚出现，而不是早出现。

---

## 推荐术语

内部模型可能使用许多精确术语。UI 应该使用更简单的术语。

### 在面向用户的界面中首选

- 默认使用"领域"而非"范围"
- 使用"协调行动倡议"而非"工作区模型"
- 使用"共享契约"而非"跨边界规范规范"
- 使用"拥有者"而非"拥有根"
- 使用"团队共享行动倡议"而非"共享协调清单"

### 保留给高级用户界面或文档

- 范围（scope）
- 项目根（project root）
- 本地覆盖（local overlay）
- 发起人/推动者（sponsor/driver）
- 协调工作区（coordination workspace）

这些术语有用，但不宜作为用户首先要吸收的概念。

---

## 推荐的默认行为

为了保持用户体验直观，OpenSpec 应该主动选择默认值。

### 默认 1：保持本地

除非有强有力的证据表明其他情况，否则规划停留在当前根目录。

### 默认 2：推断受影响领域

OpenSpec 应从以下方面推断受影响的领域：

- 请求措辞
- 当前仓库
- 已知的规范布局
- 最近的行动倡议上下文

仅当存在有意义的歧义时才询问用户。

### 默认 3：重用现有共享拥有者

如果已存在共享契约拥有者，OpenSpec 应建议使用它，而不是询问抽象的所有权问题。

### 默认 4：将未解析的根视为部分可用，而非致命错误

对于协调行动倡议，未解析的仓库不应阻止规划，除非用户明确需要在那里进行实现。

### 默认 5：仅在真正需要协作时才设为团队共享

不要为单人探索性工作强制进行团队/共享设置。

OpenSpec 可以从本地协调工作区开始，然后稍后提供：

```text
这现在看起来是协作性的。是否要将其移入共享协调仓库？
```

---

## 如何让团队用户体验感觉轻量

团队故事不应该感觉像是管理仪式。

### 期望的团队体验

1. 一个人正常开始规划
2. OpenSpec 在需要时升级为协调行动倡议
3. 当工作变得协作时，OpenSpec 提议将其设为团队共享
4. 团队成员克隆行动倡议仓库并运行一个链接命令
5. 每个人都从相同的共享行动倡议上下文开始

### 团队入职应该感觉像这样

```text
克隆行动倡议仓库。
运行 `openspec workspace doctor`。
在这里打开你的 agent。
```

而不是像这样：

```text
学习新的规划模型，理解清单，配置覆盖，并手动附加根。
```

实现可能需要这些概念，但用户体验应将其压缩为几个操作。

---

## 用户体验启发式提示

OpenSpec 应避免以抽象方式要求用户对工作进行分类，如果它能推断出合理的默认值的话。

### 好的提示

```text
这影响：
- web checkout
- billing API
- 共享 checkout 行为

我认为这应该成为协调行动倡议。
是否继续？
```

为什么这很好：

- 具体
- 包含建议
- 低认知负荷

### 较弱的提示

```text
您是否要创建一个带有链接变更和共享所有权元数据的协调工作区？
```

为什么这较弱：

- 暴露了太多内部机制
- 用户在说"是"之前必须先解析产品架构

### 好的所有权提示

```text
我找到了一个现有的共享契约领域：`contracts/checkout`。
将其用作规范拥有者？
```

### 较弱的所有权提示

```text
为此跨边界行为选择一个规范共享契约拥有者。
```

后者是精确的，但除非用户已经深入工作流，否则过于抽象。

---

## 我们应该追求的用户体验

默认情况下，OpenSpec 应该感觉像是：

- "从这里开始"
- "描述工作内容"
- "我会处理形态，除非我需要你的判断"

当系统升级时，应该感觉像是：

- "这变得比一个本地变更更大了"
- "我已经为你准备好了协调设置"
- "这是下一个明显的步骤"

当协作扩展时，应该感觉像是：

- "这现在是团队共享的了"
- "提交稳定的计划"
- "每个人都链接他们自己的本地克隆"

用户不应该感觉他们在不断地切换概念框架。

---

## 建议对旅程文档的后续修改

为了让 `workspace-user-journeys.md` 更简单直观，下一个修订版应该：

1. 将最简单的单仓库和 monorepo 旅程移到最前面。
2. 将大多数术语和内部模型部分挪到后面或附录中。
3. 将"协调工作区"重新定义为升级产物，而不是起始抽象。
4. 在面向用户的示例中将"范围"替换为"领域"。
5. 将抽象的所有权问题转换为建议优先的提示。
6. 将团队级设置压缩为一个简单的故事：
   - 共享行动倡议仓库
   - 本地链接命令
   - 在这里打开 agent
7. 明确让升级流程保留用户上下文，使其读起来像是延续，而不是重新开始。

---

## 总结

当前的工作区思考方向正确，但用户体验应该变得更加有主见，并且减少前期的解释性。

最简单的产品形态是：

- 一条默认路径：从用户当前位置进行本地规划
- 一条升级路径：在需要时升级为协调行动倡议
- 渐进式信息揭示：仅当 OpenSpec 需要真正决策时才展示高级概念

如果 OpenSpec 做得好，同一系统可以为以下用户群体提供直观体验：

- 个人用户
- 小团队
- 大型 monorepo
- 多仓库团队
- 跨团队行动倡议
