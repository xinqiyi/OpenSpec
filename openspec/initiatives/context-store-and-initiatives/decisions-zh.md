# 上下文存储与计划方案决策

## 2026-05-20：在计划方案内部跟踪路线图执行

决策：在 `openspec/initiatives/context-store-and-initiatives/` 内部跟踪计划方案路线图实现，而不是为每个路线图项创建 OpenSpec 变更。

原因：计划方案是此工作的持久协调对象。repository 本地的 OpenSpec 变更应保留给由 repository 或团队拥有的实现切片。路线图项跟踪属于计划方案，直到某个任务需要 repository 拥有的实现计划。

影响：

- 使用 `tasks.md` 作为计划方案范围的进度仪表板。
- 使用 `work-items/<nn-slug>/` 存储一个路线图项的详细执行记录。
- 当实现进入 repository 拥有的切片时，稍后将 repository 本地 OpenSpec 变更链接回计划方案。

## 2026-05-20：锁定工作空间到计划方案的产品边界

决策：工作空间是本地工作视图，不是持久的共享 planning 对象。持久协调属于上下文存储和计划方案。repository 本地变更拥有实现。

影响：

- 保留工作空间 setup、link、relink、list、open、update 和 doctor 作为 Beta 本地视图基础设施。
- 将工作空间 planning 行为视为 Beta 或过渡性兼容性。
- 推迟工作空间 apply、verify 和 archive，直到计划方案链接的 repository 本地变更存在。

## 2026-05-21：在行为改变之前保持 spec 不变

决策：不使用初始方向锁定来重写 OpenSpec spec。spec 应描述代码背后的当前行为契约。计划方案产物应承载产品意图、路线图决策和未来方向，直到后续的实现变更有意地一起更新行为及其 spec。

影响：

- 项目 1 的初始清理应聚焦于计划方案文档、历史路线图产物、活动 proposal 处理和面向用户的文档。
- 现有的工作空间 planning spec 和 schema 可以继续描述当前已实现的行为。
- 未来对 spec 的更改应与其所治理的行为同步进行。

## 2026-05-21：保留已推迟的工作空间变更作为参考占位符

决策：保留活跃的工作空间变更（agent 指南、repository 切片 apply、verify/archive 和重新实现路线图）作为推迟的参考占位符。

原因：这些领域在上下文存储、计划方案和计划方案链接的 repository 本地变更存在之后仍然预计会很重要。现在 archive 或删除它们会丢失有用的研究和连续性。

影响：

- 不要将它们作为立即的下一个实现重点。
- 将其当前 proposal 视为历史/推迟的方向。
- 在计划方案链接的 repository 本地变更定义了持久交接模型之后，重新审视并重新构建它们。

## 2026-05-21：生成的工作空间指南按所有权路由工作

决策：生成的工作空间指南应将工作空间描述为本地工作视图，并将持久工作路由到拥有的产物：计划方案拥有跨团队或跨 repository 的意图，repository 本地 OpenSpec 变更拥有实现计划，链接的 repository 或文件夹拥有其实现。

原因：计划方案方向取代了旧模型中工作空间级别的 `changes/` 树拥有 spec 共享跨 repository 计划。新的 agent 指南不应强化旧模型。

影响：

- 移除告诉 agent 使用工作空间级别的 `changes/` 作为协调工作 planning 中心的指南。
- 保留旧的或 Beta 工作空间 planning 文件作为兼容性上下文（当存在时）保持可读。
- 在广泛的面向用户文档或 spec 之前更新生成的工作空间指南。
- 保持 spec 不变，直到相应的行为有意图地改变。

## 2026-05-21：工作空间操作上下文是本地兼容性上下文

决策：工作空间 planning 操作上下文不应再将工作空间级别产物描述为真相来源。它应报告 `sourceOfTruth: "workspace-local"`，并将工作空间本地 planning 产物描述为当前本地视图的兼容性上下文。

原因：工作空间 planning 产物在 Beta workflow 中仍然可以存在，但计划方案方向将持久协调分配给计划方案，将实现 planning 分配给 repository 本地变更。

影响：

- 保留 `actionContext.mode: "workspace-planning"` 以保持兼容性。
- 保留 `allowedEditRoots: []`，直到显式编辑根目录被选定。
- 保留链接的 repository 和文件夹作为上下文，而非隐式编辑根目录。
- 当计划方案上下文存在时，将持久协调路由到计划方案。

## 2026-05-21：围绕 agent 优先的计划方案交接重新排序路线图

决策：将计划方案视为 agent 优先的 workflow。用户应能够向 agent 提示意图，如"使用计划方案 X，探索 Y 并创建 proposal"；OpenSpec 应提供 agent 可以组合的小型 CLI 原语。

原因：实际的用户体验不是人类手动输入每个协调命令。agent 需要可靠的、结构化的答案，关于 spec 的计划方案上下文在哪里以及 repository 本地变更如何引用它。本地路径来自工作空间状态，而不是来自计划方案命令。

影响：

- 在工作空间计划方案打开之前，优先推进最小上下文存储设置、注册、列出和诊断功能。
- 在更广泛的进度/状态概念之前添加 `initiative show --json`。
- 通过检入的计划方案元数据（而非检入的计划方案内容快照）连接 repository 本地变更。
- 不添加 `initiative resolve`；工作空间本地视图状态拥有本地路径映射。
- 在 show 和 repository 变更链接语义存在后，让工作空间打开了解计划方案。

## 2026-05-26：工作空间计划方案打开使用生成的运行时文件

决策：将工作空间计划方案打开视为私有本地视图记录加上生成的运行时文件。工作空间不包含工作。它记住本次运行时如何打开工作。

原因：计划方案上下文是上下文存储中的共享真相，repository 本地变更拥有实现，agent/编辑器功能需要存在于 agent 实际运行的运行时中。将生成的文件持久化为工作空间真相会模糊本地视图状态与共享协调之间的界限，并产生过期或隐私敏感的产物。

影响：

- 仅持久化微小的私有本地视图选择：选定的存储、选定的计划方案、选定的本地链接、开启器和选定的工具。
- 在私有工作空间记录中保留选定的上下文存储选择器，使得通过运行时本地 `--store-path` 打开的视图可以在不将机器本地路径写入检入的 repository 元数据的情况下重新打开。
- 在打开或准备视图时，生成 agent 指南、skill、启动提示和编辑器工作空间文件作为运行时支持。
- 仅打开现有的本地路径；在项目 10 中不克隆、不分支、不创建工作树、不使用子模块、不推断本地 repository。
- 将生成的运行时文件视为可丢弃和可重新生成的。
- 允许仅上下文的计划方案打开；链接的 repository 是可选的本地视图选择。
- 在项目 10 中保持编辑边界为建议性，直到强制机制被设计出来。

## 2026-05-26：工作空间存储按工作空间名称键控

决策：将私有工作空间视图存储在 `getGlobalDataDir()/workspaces/<workspace-name>/` 下。工作空间名称是本地标识。选定的上下文存储和计划方案（如有）位于一个持久的私有 `workspace.yaml` 记录中。

原因：工作空间是通用的本地视图，不是计划方案拥有的目录。用户可能想要一个带有链接 repository 和文件夹但没有计划方案的自定义工作空间，或者针对同一计划方案有多个个人工作空间。按存储和计划方案键控存储会使文件系统布局过度适配到一种 workflow。

影响：

- 在 `workspace.yaml` 中保持计划方案引用为可选项。
- 使用显式的上下文存储绑定（而非扁平存储 id）存储计划方案上下文，因为工作空间状态可能需要记住注册表选择器或运行时本地路径选择器。
- 在管理工作空间根目录生成 `AGENTS.md`、开启器工作空间文件和特定于工具的 skill。
- 项目 10 仅使用 `workspace.yaml` 作为唯一的视图文件；不添加单独的机器可读视图文件。
- 项目 10 不引入单独的生成输出目录。
- 如果用户在没有工作空间名称的情况下打开计划方案，在计划方案 id 不模糊时从中派生出友好的默认工作空间名称。
- 在工作空间名称冲突或多个工作空间指向同一计划方案时，请人类选择或在非交互 schema 下要求显式的工作空间名称。

## 2026-05-26：项目 10 工作空间打开用户体验决策

决策：关闭项目 10 剩余的关于运行时身份、JSON 输出、Codex Desktop、编辑边界和实现范围的产品决策。

影响：

- 使用 `getGlobalDataDir()` 作为跨平台的运行时本地边界。项目 10 不添加路径转换或单独的运行时 id。
- 保留 `workspace open --json` 作为同一打开操作的机器可读回执。它应返回有用的生成路径、选定上下文、打开的根目录、跳过的根目录、开启器、启动状态和警告。
- 项目 10 不添加 `--prepare-only`。
- 对于 Codex Desktop，将生成的工作空间根目录作为项目打开，并通过生成的指南和 `workspace open --json` 输出暴露附加的计划方案和 repository/文件夹路径。
- 仅发出建议性编辑边界；不强制执行写入限制。
- 继续仅打开已知的现有本地路径。在项目 10 中不克隆、不分支、不创建工作树、不使用子模块、不推断本地 repository。
