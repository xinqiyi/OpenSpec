# 上下文存储与计划方案路线图

本路线图将 `direction.md` 中的方向转化为可交付的块。

每一步背后的产品决策是：

```text
Context stores sync truth.
Collections shape truth.
Initiatives coordinate work.
Workspaces open local views.
Changes implement repo-owned slices.
```

## 当前 Beta 优先级

手动 Beta 验证应将首次运行的摩擦点前置。在投资更深层次的模式或生命周期机制之前，按此顺序工作：

1. 完成手动 Beta 实际体验验证，足以让后续切片有据可依。
2. 项目 12，上下文存储首次运行和清理用户体验：交互式无参 setup、目标路径安全性，以及受支持的取消注册/移除路径。
3. 项目 13，代理交接输出和交付优化："你的代理的下一步"块、直接 JSON 路径，以及即使在命令导向的工作流入点时的基础 OpenSpec 指南。
4. 项目 14，工作空间 Beta 指南拆分：使面向用户的文档匹配交互式设置路径，并将精确标志保留在代理操作手册中。
5. 项目 15，上下文存储项目根目录和基于模式的计划方案：稀疏的计划方案创建和存储本地模式。

升级用户体验、团队共享强化和计划方案托管的目标绑定变更仍然重要，但它们应等待直到首次运行路径以好的方式变得平淡无奇。

在工作空间变为公开/稳定之前，运行项目 19 作为后期 Beta 清理，以便 Beta 兼容性代码得到有意义的审查，而不是被视为永久契约。

## 1. 锁定方向

目标：使工作空间到计划方案的转变明确化，使未来的工作空间工作不再继续实现旧的"工作空间拥有计划"模型。

交付：

- 记录工作空间是本地工作视图，而不是持久的共享规划对象。
- 记录计划方案是跨团队或跨仓库工作的持久协调对象。
- 将当前工作空间 apply、verify 和 archive 方向标记为推迟或被取代，直到计划方案链接的仓库变更存在。
- 保留已构建的工作空间 setup、link、open、update 和 doctor 行为作为有用的 Beta 基础设施。

完成标志：

- 新代理能够分辨哪些工作空间概念仍然适用，哪些不应指导实现。

锁定处理：

- 保留工作空间 setup、link、relink、list、open、update 和 doctor 作为 Beta 本地视图基础设施。
- 保留"工作空间可见性不是变更承诺"作为链接仓库和文件夹的安全规则。
- 用"计划方案是持久协调对象"取代"工作空间是持久规划中心"。
- 取代工作空间级别规划产物作为规范共享的跨仓库计划。
- 推迟工作空间 apply、verify 和 archive 作为一等生命周期命令，直到计划方案链接的仓库本地变更存在。
- 推迟分支/工作树编排、强跨仓库验证、依赖图强制执行和共享合约治理。

新代理规则：

- 以 `openspec/initiatives/context-store-and-initiatives/direction.md` 作为产品权威来源。
- 将 `openspec/changes/workspace-reimplementation-roadmap/HISTORICAL_DIRECTION.md` 和 `openspec/changes/workspace-reimplementation-roadmap/` 视为保留的本地视图行为的概念验证经验教训的历史参考材料。
- 不要将 `workspace-apply-repo-slice` 或 `workspace-verify-and-archive` 作为下一个实现切片，除非后续的计划方案链接的仓库变更设计明确重新激活它们。

## 2. 将工作空间稳定为本地视图

目标：使工作空间保持有用，而不是使其成为真相来源。

交付：

- 工作空间指南，将持久协调路由到计划方案，将实现规划路由到仓库本地变更，将链接的仓库或文件夹在选定编辑根目录之前作为本地上下文。
- 工作空间打开行为，以可见的链接文件夹启动本地规划视图。
- 工作空间 doctor/status 输出，解释本地路径映射、未解决的链接、已安装的代理技能和修复步骤。
- 清晰的文档说明 `workspace update` 刷新本地代理指南，不修改链接的仓库。

完成标志：

- 用户可以设置工作空间、链接仓库、打开代理，并理解工作空间是上下文的本地视图，而不是规范的共享计划。

## 3. 添加上下文存储基础

目标：创建通用的本地上下文存储基础，以后可以承载计划方案和其他共享上下文集合。同步/监视行为保留为未来的强化切片。

交付：

- 一个上下文存储抽象，具有通用的本地操作：read、write、delete 和 list。
- 第一个 Git 形状的后端模型，可以指向本地存储根目录。
- 一个测试/内存后端，用于快速测试和原型。
- 一个不包含计划方案特定逻辑的存储配置模型。

完成标志：

- OpenSpec 可以在本地上下文存储中创建和操作文件，而核心存储层不需要知道这些文件的含义。Pull、push、watch、远程创建和冲突处理被追踪为未来的同步工作。

## 4. 添加集合基础

目标：让产品特定的内容系统存在于上下文存储内部，而无需将每个未来概念硬编码到存储层中。

交付：

- 一个带有挂载文件夹命名空间的集合接口。
- 规则确保集合的写入在其挂载内。
- 基本的集合验证和模板钩子。
- 一种让集合以后暴露可选代理指南或 UI 元数据的方式。

完成标志：

- 上下文存储可以托管挂载的 `initiatives/` 集合，同时保持足够的通用性，以支持未来的集合如 decisions、API catalogs 或 playbooks。

## 5. 交付计划方案 MVP

目标：为协调的工作提供一个持久的、共享的、代理可消费的归属。

交付：

- 计划方案创建和列出。
- 默认的计划方案文件结构：

```text
initiatives/<id>/
  initiative.yaml
  requirements.md
  design.md
  decisions.md
  questions.md
  tasks.md
```

- 产品意图、已采纳需求、设计决策、开放问题和协调任务的模板。
- 必需的计划方案元数据的验证。
- 明确推迟完整的 read/show、update 和 delete 策略，直到代理优先发现和生命周期需求更清晰。

完成标志：

- 用户或代理可以在任何仓库承诺实现细节之前创建和列出计划方案作为共享规划对象。

## 6. 添加最小上下文存储用户体验

目标：使共享计划方案存储在仓库交接或工作空间打开依赖它之前可用。

交付：

- `context-store setup <id>` 用于创建本地 Git 后端存储文件夹，带有可移植的存储元数据和本地注册。
- `context-store register <path>` 用于注册现有克隆或文件夹，默认从仓库或文件夹名称推断存储 id。
- `context-store list` 和 `context-store doctor` 用于本地可见性和非变异诊断。
- `initiative list` 默认显示所有已注册存储，使用 `--store` 作为过滤器，`--store-path` 作为逃生口。
- 适用于代理的最小人类可读输出和 JSON 输出。

完成标志：

- 单个开发者或队友可以创建或注册共享上下文存储，列出跨已注册存储的计划方案，并诊断缺失或损坏的本地存储设置，而无需了解内部注册表布局。

## 7. 添加代理优先的计划方案发现

目标：让代理解析用户命名的计划方案，并从真相来源读取规范的计划方案上下文。

交付：

- `initiative show <id>` 默认搜索已注册存储。
- 当相同计划方案 id 存在于多个存储中时的模糊处理。
- JSON 输出，包含规范的计划方案元数据、存储身份、计划方案根路径和元数据路径。
- 面向人类用户的输出，聚焦于身份和可用文件，而非工作进度。

完成标志：

- 代理可以回答："用户指的是哪个计划方案，规范上下文在哪里，计划方案元数据在哪里？"

## 8. 将仓库本地变更连接到计划方案

目标：清晰地将共享协调与仓库拥有的实现计划分开。

实现前需确认的讨论点：

- 创建/链接流程是否应明确报告变更所在位置、引用的计划方案以及建议的下一条命令？
- `--initiative <id>` 是否应默认搜索已注册存储，还是当注册了多个存储时需要 `--store`？
- 当计划方案存在但当前仓库没有明显的所有权匹配时，命令应做什么？

交付：

- 仓库本地变更元数据，可以按存储 id 和计划方案 id 引用计划方案。
- 代理友好的创建或链接流程，如 `new change <id> --initiative <store>/<initiative>`。
- 指南说明仓库本地变更负责实现、验证和归档。
- 默认不检入 `initiative.md` 快照；代理实时从上下文存储读取规范的计划方案文件。

完成标志：

- 一个计划方案可以协调多个仓库本地变更，而无需将共享计划复制到每个仓库、在计划方案中存储机器本地链接、或让计划方案拥有实现产物。

## 9. 拒绝计划方案解析

决策：现在或将来都不添加 `openspec initiative resolve`。

理由：

- `initiative show` 已经解析规范共享计划方案上下文。
- 工作空间是覆盖仓库、文件夹、上下文存储和计划方案的本地视图。
- 仓库本地变更已经在其检入的 `.openspec.yaml` 元数据中携带持久的计划方案链接。
- 仓库本地状态已经报告工作进度。
- 独立的 resolve 命令要么重复工作空间本地视图状态，要么在没有工作空间时产生弱输出。

不交付：

- `openspec initiative resolve <id>`
- 扫描所有工作空间或所有仓库以查找计划方案可用性
- 显式路径扫描作为计划方案命令
- Git 远程匹配以确定计划方案参与
- 仓库所有权推断
- 克隆、分支创建或工作树创建作为计划方案解析的一部分
- 计划方案反向链接
- 计划方案命令下的本地可用性或进度仪表板

完成标志：

- 未来的代理可以看到"initiative resolve"被有意拒绝，并且不应以其他命令名称复活。

## 提议讨论点：添加计划方案下一步 / 代理交接用户体验

状态：候选工作项，尚未锁定到编号路线图中。

需确认的问题：

- 这是否应成为"让工作空间打开计划方案"之前的路线图项？

目标：在计划方案从当前仓库或工作空间发现后，给代理和用户一个小的"现在做什么？"命令，而不使其变成仪表板或进度/状态界面。

可能的形式：

```bash
openspec initiative next billing-launch --json
```

可能的 JSON 回答：

```json
{
  "initiative": "billing-launch",
  "next_action": "create_repo_change",
  "reason": "initiative found, no linked local change exists for this repo",
  "suggested_command": "openspec new change add-billing-api --initiative billing-launch"
}
```

实现前需确认的讨论点：

- `initiative next` 是正确的命令名称吗？还是此指南应属于工作空间计划方案打开或仓库本地状态？
- 它应返回恰好一个建议的下一步操作，还是一组排序的选项？
- 它是否应检查工作进度，还是仅限于交接/就绪状态？
- 当没有注册存储、计划方案模糊或本地仓库不相关时，它应如何表现？

完成标志（如果被接受）：

- 代理可以回答"从这个位置开始，针对这个计划方案，我下一步应该做什么？"而无需在 `show`、工作空间状态和仓库本地变更元数据之间猜测。

## 10. 让工作空间打开计划方案

目标：在计划方案 show 和仓库变更链接存在之后，将持久的计划方案上下文连接到本次运行时的本地工作视图。

锁定方向：

- 工作空间不包含工作。它记住本次运行时如何打开工作。
- 仅持久化微小的私有本地视图选择。
- 在打开时生成开启器特定的运行时文件。
- 附加计划方案上下文和选定的现有本地仓库或文件夹。
- 在此切片中不克隆、不分支、不创建工作树、不使用子模块、不推断本地仓库。
- 仅上下文打开是有效的。

产品决策状态：

- 项目 10 没有剩余的开放产品决策。实现仍可能发现机械细节，但预期的用户体验形状已锁定。

命令用户体验决策：

- 使用 `openspec workspace open --initiative <initiative>`。
- 支持 `<store>/<initiative>` 和 `<initiative> --store <store>`。
- 当用户想要显式选择本地工作空间身份时，支持 `openspec workspace open <workspace-name> --initiative <initiative>`。
- 如果仅提供 `<initiative>`，则在恰好一个已注册上下文存储具有该计划方案 id 时继续。
- 在模糊情况下，列出精确匹配并要求显式的存储选择器。
- 在没有精确匹配时，显示可能的匹配（若可用）并建议 `openspec initiative list`；不要静默打开模糊匹配。
- 如果用户省略工作空间名称，在计划方案 id 不模糊时从中派生出友好的默认值；否则要求用户选择显式的工作空间名称。

打开目标决策：

- 默认打开计划方案目录，而不是整个上下文存储。
- 生成的指南和 JSON 输出仍应报告上下文存储根目录以及更广泛的上下文可用。
- 以后的显式选项可以打开整个上下文存储，但广泛的存储范围不是项目 10 的默认设置。

本地视图记录决策：

- 为计划方案感知的本地视图使用一个私有本地视图记录。
- 将计划方案视图状态存储在根 `workspace.yaml` 文件中。
- 记录存储选定的上下文存储绑定、计划方案、本地链接、开启器和选定工具。绑定可以保留注册表选择器或运行时本地路径选择器。
- 上下文绑定是可选的，因此工作空间也可以是自定义本地视图，带链接文件夹而无需计划方案。

工作空间存储决策：

- 将每个私有工作空间视图存储在 `getGlobalDataDir()/workspaces/<workspace-name>/` 下。
- 工作空间名称是本地标识。选定的存储和计划方案（如有）是私有记录中的数据，而不是路径段。
- 在工作空间根目录使用一个持久化的 `workspace.yaml`。
- 在工作空间根目录生成 `AGENTS.md`、开启器工作空间文件和特定于工具的技能。
- 项目 10 不引入单独的生成输出目录。

运行时身份决策：

- 使用 `getGlobalDataDir()` 作为跨平台的运行时本地边界。
- 本地路径仅在写入私有 `workspace.yaml` 的运行时中有效。
- 项目 10 不添加路径转换或单独的 `<runtime-id>` 路径段。

Prepare/JSON 决策：

- 保留 `workspace open --json` 作为同一打开操作的机器可读回执。
- 项目 10 不添加 `--prepare-only`。
- JSON 应返回有用的生成路径、选定上下文、打开的根目录、跳过的根目录、开启器、启动状态和警告，而不仅仅是裸成功响应。

Codex Desktop 决策：

- 将生成的工作空间根目录作为 Codex Desktop 项目打开。
- 通过生成的指南和 `workspace open --json` 输出暴露附加的计划方案和链接的仓库/文件夹路径。
- 推迟 Desktop 多根自动化，直到有更清晰的 Desktop 契约。

编辑边界决策：

- 仅发出建议性边界。
- 将计划方案/上下文存储文件标记为共享协调上下文，将链接的仓库/文件夹标记为本地实现上下文（当选定时）。
- 项目 10 不强制执行写入限制。

交付：

- 私有本地视图状态，可以记住选定的上下文存储、选定的计划方案、选定的本地链接、开启器和选定工具。
- `workspace open` 支持生成开启器特定的运行时文件，并打开计划方案上下文加上本地解析的链接仓库/文件夹。
- 代理指南和机器可读的 `workspace open --json` 输出，解释当前计划方案、打开的根目录、跳过的根目录、本地路径和建议的编辑边界。
- 工作空间名称复用行为，避免静默地将现有工作空间重新指向不同的计划方案。
- 打开时警告，跳过缺失的链接仓库/文件夹，同时在选定的计划方案或上下文存储无法解析时失败。
- 继续支持自定义非计划方案工作空间作为一等本地视图。
- 缺失上下文存储、缺失链接仓库/文件夹和过期本地视图记录的 doctor 指南。

完成标志：

- 队友可以在他们的运行时中打开相同的计划方案，同时使用他们自己的本地路径和选定的仓库子集。
- 生成的运行时文件明确是派生的，可以在不丢失用户本地视图选择的情况下重新生成。

## 11. 手动 Beta 实际体验验证

状态：提议的即时 Beta 学习项。

目标：手动运行现有功能，并利用摩擦来更新计划方案记录，然后再设计更多的表面积。

交付：

- 新用户逐步体验上下文存储设置、计划方案创建、工作空间打开、仓库链接、doctor 输出和仓库本地链接变更创建。
- 记录哪些部分感觉清晰，哪些感觉奇怪，哪些提示缺失，哪些文档向用户推送了太多标志。

完成标志：

- 计划方案包含通过手动尝试当前 Beta 流程获得的具体记录。
- 下一个实现或文档切片基于观察到的摩擦点，而非猜测的工作流形状。

## 12. 上下文存储首次运行和清理用户体验

目标：使上下文存储设置和清理感觉像正常的本地工作流程，而不添加同步、远程或治理自动化。

工作项：
`work-items/12-context-store-first-run-and-cleanup-ux/`

交付：

- 为终端用户提供交互式无参 `context-store setup`。
- 当必需的设置选择缺失时，提供确定性的非交互和 JSON 行为。
- 管理默认值、显式路径、现有 Git 仓库和非空目录的目标路径安全输出。
- 受支持的本地清理路径，用于注销或移除上下文存储，无需手动编辑注册表。
- 设置输出解释本地注册表状态和 Git 状态，包括 `--init-git` 后的未提交共享存储文件。

完成标志：

- 新用户可以在不知道隐藏的注册表路径、环境变量或手动文件编辑的情况下设置或清理本地上下文存储。

## 13. 代理交接输出和交付优化

目标：使现有命令输出和交付选择足以让新代理安全地继续，在添加任何更广泛的 `initiative next` 命令之前。

工作项：
`work-items/13-agent-handoff-output-and-delivery-polish/`

交付：

- 在首次运行流程否则依赖于粘贴的 Beta 知识的命令输出中，添加"你的代理的下一步"交接指南。
- 在代理需要写入文件的地方，在 JSON 输出中添加直接的创建产物路径，同时保留现有相对字段以保持兼容性。
- 清晰的交付措辞，将基础 OpenSpec 指南与工作流入点（如技能或斜杠命令）分开。
- 当选定的工具无法接收工作流斜杠命令时发出警告。

完成标志：

- 编码代理可以从设置或计划方案创建输出继续，而无需猜测命令名称、重建可写路径、或因为用户选择了命令导向的交付而丢失基础 OpenSpec 指南。

完成标志：

## 15. 上下文存储项目根目录和基于模式的计划方案

目标：让上下文存储的行为类似于 OpenSpec 根目录，用于共享规划配置和模式，同时默认保持实现变更为仓库拥有。

工作项：
`work-items/15-context-store-project-roots-and-schema-led-initiatives/`

需确认的产品决策：

- 上下文存储可以在 `openspec init` 后拥有 `openspec/config.yaml` 和 `openspec/schemas/`，就像仓库一样。
- 这种类似项目的结构用于共享上下文配置和计划方案模式。它绝不能静默地使上下文存储成为实现仓库。
- `initiative create` 应创建稀疏外壳，并通过基于模式的状态/说明让经过审查的计划方案产物逐步增长。

交付：

- 上下文存储设置，创建或支持存储本地的 OpenSpec 配置。
- 用于高级需求和设计产物的默认计划方案模式。
- 稀疏的计划方案创建：`initiative.yaml` 加上简短的 `brief.md`，没有 `TBD` 占位符，没有默认的 `tasks.md`。
- 基于计划方案目录根部的计划方案产物状态和说明输出。
- 防护措施，使 `openspec new change` 不会仅因为存储有 `openspec/` 目录而意外在上下文存储内部创建可执行的仓库本地变更。
- 对现有六文件 MVP 计划方案的兼容性。

完成标志：

- 上下文存储可以解析存储本地的计划方案模式。
- 代理可以从 CLI 说明迭代地创建计划方案需求和设计产物。
- 现有的 MVP 计划方案继续列出和显示。
- 文档不再将计划方案创建描述为"立即填充每个 markdown 文件"。

## 18. 探索计划方案托管的目标绑定变更产物

目标：决定共享的计划方案产物是否只有在绑定到目标仓库或规范根目录后才能升级为可执行的 OpenSpec 变更，且不模糊计划方案协调、仓库所有权和工作空间本地视图的边界。

工作项：
`work-items/18-explore-initiative-hosted-target-bound-change-artifacts/`

探索前需确认的讨论点：

- "变更归属"是否应保持为内部解析器语言，面向用户的措辞如"这个计划应该放在哪里？"和"可编辑目标"？
- 计划方案工作项、brief、目标绑定变更和仓库本地变更之间的区别是什么？
- 在计划方案托管的产物可以被视为实现就绪之前，需要哪些可移植的目标元数据？
- 共享目标绑定变更是否需要显式选择加入，还是计划方案/存储策略可以选择它们？
- 什么样的用户/团队场景会证明计划方案托管的目标绑定变更比仓库本地链接变更更合理？

交付：

- 审计仓库本地 `openspec/changes/` 假设的命令、模板、验证、归档、apply、完成和文档。
- 定义产物归属、实现目标、允许的编辑根目录和操作上下文的概念。
- 决定计划方案托管的目标绑定变更如何绑定到仓库规范、实现根目录、分支、验证、归档和同步/冲突行为。
- 定义代理可读的 JSON 输出，包含工作目标、产物归属、实现目标、计划方案链接、编辑边界、不支持的生命周期命令和下一步命令。
- 记录现有仓库本地和工作空间本地变更的兼容性行为。
- 推荐这应成为实现切片、保持推迟、仅作为计划方案工作项开始，还是首先限于特定模式或工作流。

完成标志：

- 计划方案具有具体的推荐、选择加入/配置示例、受影响的命令列表以及实现的可行/不可行标准。

## 19. 在公开发布前审查工作空间 Beta 兼容性

目标：决定哪些工作空间 Beta 兼容性行为应保留到公开工作空间契约中，并在工作空间仍处于未发布状态时移除或迁移其余部分。

工作项：
`work-items/19-review-workspace-beta-compatibility-before-public-release/`

为什么这是后期工作：

- 工作空间仍处于 Beta 状态，尚未公开/稳定。
- 我们不需要永远保留每个中间 Beta 文件形状。
- 在首次运行用户体验和计划方案行为仍在变化时，早期清理有造成变动的风险。
- 在手动 Beta 使用显示真实用户实际创建了哪些本地工作空间产物之后，更容易定义正确的兼容性契约。

交付：

- 盘点工作空间兼容性代码，包括遗留的拆分状态读取器、注册表回退、`codex` 到 `codex-cli` 别名、生成的 `.gitignore` 清理和空的兼容性 shim。
- 将每个路径分类为公共契约、Beta 迁移、仅测试 shim 或可移除的死代码。
- 移除仅支持未发布中间工作空间形状的仅 Beta shim。
- 定义任何值得为尝试过 Beta 的用户保留的迁移行为。
- 更新文档、测试、生成的指南和发布说明，使公开工作空间兼容性承诺明确。

完成标志：

- 工作空间兼容性表面积有意地小。
- 公开文档不暗示支持仅 Beta 的工作空间内部。
- 任何剩余的迁移代码都有明确的所有者、原因和移除策略。
