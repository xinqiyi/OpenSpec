# 手动 Beta 真实体验检查笔记

在尝试 beta 流程时使用此笔记作为草稿本。

## 做得好的方面

- 手动 beta 检查在构建更多功能之前发现了一个不良默认值。
- 更改默认值后，从 OpenSpec 仓库内部重新运行 `openspec context-store setup team-context --init-git`，将存储创建在 `~/.local/share/openspec/context-stores/team-context`，而不是嵌套在仓库中。
- 最小化的新代理交接方式在倡议创建方面效果良好。仅给子代理一个存储 ID 和一个宽松的主题，它在正确的上下文存储位置创建了 `agent-trace-hooks`：`~/.local/share/openspec/context-stores/team-context/initiatives/agent-trace-hooks`。

## 感觉别扭的方面

- 新用户指导立刻漂移到沙箱/环境设置（`XDG_CONFIG_HOME`、`XDG_DATA_HOME`），而不是让用户直接在本地运行 beta。强烈反应：这应该作为正常的本地工作流工作。
- `openspec context-store setup` 不带参数感觉应该启动交互式设置，但实际上并没有。命令名称本身就创造了这种期望。
- `openspec context-store setup team-context --init-git` 在当前 OpenSpec 仓库内部创建了 `team-context/`，因为默认路径是 `./<id>`。用户期望默认位置在当前仓库之外，而不是在他们碰巧运行命令的目录中嵌套一个新的 Git 仓库。
- 清理意外创建的存储没有明显的 CLI 路径。`context-store` 提供了 setup/register/list/doctor，但没有 unregister/remove 命令，因此清理需要手动删除文件夹和编辑注册表。
- `context-store setup --init-git` 初始化了 Git，但将 `.openspec-store/` 和新的倡议留在了未跟踪状态。这可能没问题，但 beta 流程没有告诉用户或代理是否要暂存/提交共享上下文存储。
- `openspec workspace open` 没有参数时仅提示已知的本地工作区视图。它不会显示已注册的上下文存储或倡议，因此即使下一步指南是从该存储打开一个倡议，`team-context` 也不在显示列表中。这在技术上与当前实现一致，但在 beta 流程中令人困惑，因为命令名称读起来像是一个广泛的"打开某个 OpenSpec 相关内容"的入口点。
- 倡议创建后的步骤使用了错误的首次运行动词。在创建上下文存储和倡议后，用户概念上是在为该倡议创建一个本地工作区视图。"Open"意味着工作区已经存在，因此 beta 指南和 CLI 让用户推断出一个隐藏的创建或打开行为。

## 缺失的提示或过多的标志

- 需要更清晰的指导，说明 beta 检查是否应该使用现有的本地 OpenSpec 状态，还是创建一个正常的本地测试上下文存储。避免将环境变量作为默认手动路径的要求。
- 缺失提示：当未提供上下文存储 ID 时，询问存储 ID、路径和 Git 初始化选择，而不是要求用户知道位置参数/标志。
- 缺失提示/安全检查：在当前目录下创建默认上下文存储之前，显示目标路径并要求确认，或提供一个托管默认位置。
- 缺失交接指导：上下文存储设置后，指南告诉用户让代理创建一个倡议，但新代理可能不知道 beta 倡议 CLI 或在哪里找到代理手册。
- 缺失提示：当已注册的倡议存在时，`workspace open` 应该提供一个"从上下文存储打开倡议"的路径，或者使无参数提示文本明确说明它仅选择现有的本地工作区视图。如果它提供倡议，应该显示类似 `team-context/agent-trace-hooks` 的引用，而不仅仅是存储 ID。
- 缺失首次运行工作区创建流程：在倡议存在后，应引导用户创建本地工作区视图。一个简单的交互式路径可以询问要设置什么，列出已注册的倡议如 `team-context/agent-trace-hooks`，从倡议 ID 建议工作区名称，可选地链接现有的仓库/文件夹路径，选择一个打开器，然后创建工作区视图。
- 更好的最小 beta 路径：保留延迟工作区创建，但让裸交互式 `openspec workspace open` 能感知倡议。选择器应显示现有的本地工作区视图和可以创建本地视图的已注册倡议，并带有保持"工作区"和"倡议"之间区别的标签。
- 生成的倡议文件合约解释不足。CLI 确切创建 `initiative.yaml`、`requirements.md`、`design.md`、`decisions.md`、`questions.md` 和 `tasks.md`，但文档将 Markdown 文件描述为"典型的"或"然后编辑"，而不是清晰地命名合约。
- 查看生成的倡议树的用户可能会合理地问这些结构来自何处。确切的六个文件合约在代码和内部 MVP 工作项中是清晰的，但公开 beta 文档没有明确说明，更广泛的方向文档仍然提到了未来的 `contracts/` 内容。

## 代理交接笔记

- 第一个代理步骤存在引导问题。`context-store setup` 不会创建仓库本地指导，而 `workspace open --initiative` 在倡议存在之前无法运行。新代理需要显式粘贴的迷你手册、已安装的 OpenSpec 技能，或者打印确切的下一个代理提示/命令的 CLI 输出。
- 在手动子代理测试中，代理运行了 `initiative create --help`，然后用 `--store team-context --title ... --summary ... --json` 创建了倡议。它正确地解析了存储，没有在 OpenSpec 仓库中创建文件。
- 子代理将生成的 `TBD` 占位符替换为有用的简短内容，这表明模板提供了足够的结构但不够的指导。没有 CLI 选项可以播种比标题和摘要更丰富的内容。
- `initiative create --json` 将 `created_files` 报告为相对名称。代理必须将这些与返回的根路径结合才能获得绝对路径。
- 对于此 beta，"仅命令"在产品含义上存在歧义。实现将其视为"移除所有技能并仅安装斜杠命令文件"，但用户可能将其理解为"我更喜欢将斜杠命令作为工作流入口点"。他们仍然可能期望他们的编码代理理解 OpenSpec 概念、上下文存储、倡议和工作区交接。

## 交付 UX 模型

- 将概念分为两层：
  - 基础 OpenSpec 素养："代理是否理解 OpenSpec 概念，并知道如何检查上下文存储、倡议、工作区和仓库本地变更？"
  - 工作流入口点："用户如何调用工作流操作，如 propose/apply/archive？"
- 当前的 `delivery` 表现得像一个生成-构件清理开关。这对于面向用户的选择来说太底层了。
- 更好的含义：
  - `skills`：安装基础指导技能加工作流技能。
  - `commands`：安装基础指导技能加工作流斜杠命令。
  - `both`：安装基础指导技能加工作流技能和工作流斜杠命令。
- 在 UI 文案中，如果"仅命令"暗示完全没有技能，则避免使用。偏好使用如"将斜杠命令作为工作流入口点"或"仅工作流命令"这样的标签，并附上辅助文字说明当所选代理支持技能时，基础 OpenSpec 指导仍然会安装。
- 对于没有命令适配器的工具，面向命令的交付应清晰警告该工具不支持工作流斜杠命令。如果工具支持技能，它仍应收到基础指导技能，这样所选代理就不会一无所获。

## 倡议放置 UX

- 新代理还需要知道新的规划对象属于上下文存储还是当前仓库。这不应该仅凭感觉决定。
- 产品区分：
  - 上下文存储中的倡议是有意存在于实施仓库之外的持久规划和协调上下文：产品意图、决策、问题、路线图笔记以及不一定需要检入代码仓库的任务。
  - 仓库本地 OpenSpec 变更是仓库拥有的实施计划，将发生变化：提案/设计/规范差异/任务/验证。
  - 工作区是连接共享上下文与本地仓库的本地视图；它们不应成为第三个持久的规划家园。
- 代理指导不应仅因为工作涉及一个仓库就假定仓库本地是首选。当用户希望 OpenSpec 构件在仓库之外、当 monorepo 有多个团队各自拥有独立的规划上下文、当仓库策略不鼓励规划构件、当工作是跨仓库/跨团队协调的、长期存在的、实施前的探索，或已经与现有上下文存储关联时，应使用或创建上下文存储倡议。
- 如果请求不明确，代理应首先检查：`openspec initiative list --json`、`openspec list --json` 和工作区状态（如果有）。如果仍然不明确，应询问："这些 OpenSpec 构件应该位于仓库之外的上下文存储中，还是作为仓库本地实施变更位于此仓库内部？"
- CLI/技能文案应使连接的流程显式化：在上下文存储中创建/读取倡议，然后从拥有的仓库中使用 `--initiative <store>/<initiative>` 创建仓库本地变更。

## 倡议创建反思

- `openspec initiative create` 目前创建一个完整的六文件规划包，带有 `TBD` 占位符。这对于目标受众（PM、设计师、架构师和促进早期产品/架构思考的代理）来说过于急切。
- 初始创建应注册倡议外壳，而不是凭空创造计划。最保守的第一个切片是 `initiative.yaml` 加上：
  - 一个从标题/摘要/当前理解播种的简短 `brief.md`；或
  - 一个轻量级的 `requirements.md`，没有 `TBD` 占位符，在内容经过审查之前不声称有已接受的需求。
- 后续构件应在它们变得真实时迭代创建：
  - `requirements.md`：已接受的高级需求、目标、非目标、未解决的产品问题。
  - `design.md`：已审查的产品/UX/架构方向和权衡。
  - `questions.md`：可选的疑问日志，当问题需要跟踪时使用。
  - `decisions.md`：可选的决策日志，仅在决策发生后追加。
  - 避免默认的 `tasks.md`；实施任务属于仓库本地变更。如果以后需要倡议级别的协调，使用更清晰的语言如 `workstreams.md`、`milestones.md` 或 `coordination.md`。
- 这理想情况下应由架构驱动。重用构件图概念（构件 ID、生成路径、模板、依赖、状态/指令），但将其根植于倡议目录而不是仓库本地变更。
- 一个最小的倡议架构可以只从 `requirements` 和 `design` 开始，其中 design 依赖 requirements。`decisions` 和 `questions` 是活动日志，因此文件存在完成语义可能不适合它们。
- 为了下一个版本的安全性，在 `initiative.yaml` 中避免严格的顶层 `schema:` 字段，直到元数据兼容性经过设计。如果架构提示需要持久化，将其存储在 `metadata` 下或保持默认隐式。

## 文档修复

- beta 指南说"这将创建一个本地上下文存储"，但没有解释默认位置是相对于当前工作目录的 `./<id>`。如果默认值保持不变，这需要明确说明。
- 即时文档/代码修复将默认值从 `./<id>` 更改，并记录了托管的本地数据位置。
- 步骤 2 不应假设代理已经知道 beta 倡议命令。包含一个可复制粘贴的引导提示，或代理 CLI 手册的链接/内联摘录。
- 步骤 3 说"打开你的本地工作台"，但当传递 `--initiative` 时，该命令实际上是创建或打开。指南应明确说明："为倡议创建或打开本地工作区视图。"还应警告裸 `openspec workspace open` 仅选择现有的工作区视图，不会列出像 `team-context` 这样的上下文存储。
- 更好的做法：更改面向用户的流程，使首次使用路径明确是创建/设置。指南应将用户引导到倡议的交互式工作区设置路径，然后将 `workspace open` 保留为重新打开现有工作区视图的用途。
- 子代理 UX/模型测试建议了一个更精简的 beta 更改：保留 `workspace open --initiative <store>/<initiative>` 作为显式的创建或重用路径，但使裸交互式 `workspace open` 显示倡议作为可选择的选项。选择倡议时应说明它正在创建/打开本地工作区视图。

## 可能的实施切片

- 使 `openspec context-store setup` 在未提供 ID 时变为交互式：提示输入存储 ID、默认路径和 Git 初始化；保持 `--json` / 非交互式行为是确定性的，并附带有用的修复消息。
- 重新考虑默认的上下文存储设置路径。选项：默认使用托管的 OpenSpec 数据目录，或在交互式确认命名完整目标路径后才使用 `./<id>`。
  - 在体验检查期间已实施：默认使用托管的 OpenSpec 数据目录，保留 `--path` 用于显式位置。
- 添加 `openspec context-store unregister <id>` 或 `remove <id>` 用于本地注册表清理，带有明确的选项来决定是否删除文件或仅忘记本地注册。
- 添加上下文存储设置后的首次运行交接辅助功能，例如打印"为你的代理的下一步"指导，或添加一个命令来发出适用于共享上下文/倡议设置的代理手册。
- 为倡议视图添加交互式工作区创建。候选接口：扩展 `openspec workspace setup` 以包含倡议选择，添加 `openspec workspace setup --initiative <store>/<initiative>`，或引入更清晰的 `workspace create` 命令。关键的 UX 要求是，新用户可以在倡议创建后运行一个交互式命令，并被引导到"为此倡议创建本地工作区视图"，而无需知道 `--initiative` 或派生的工作区名称约定。
- 添加一个能感知倡议的 `workspace open` 选择器作为最小的产品修复：在裸交互式打开时，列出本地工作区加上已注册的倡议。如果用户选择了一个倡议，通过现有的 `--initiative` 创建/重用路径进行处理。不要在上下文存储设置或倡议创建时自动创建工作区，也不要使工作区与倡议一一对应。
  - 在体验检查期间已实施：裸交互式 `workspace open` 现在显示尚未有已知本地视图的已注册倡议，选择一个就会创建/重用绑定到该倡议的工作区视图。
  - 后续修复：当该延迟倡议视图是新的时，`workspace open` 现在在创建工作区视图之前运行与 `workspace setup` 相同的仓库/文件夹链接提示。这避免了打开空工作区，并在用户期望的时刻收集实施根目录。
- 考虑将基础 OpenSpec 素养与工作流交付分开。一个小的默认 `use-openspec` 技能可以在所选代理支持技能时安装，即使工作流交付设置为仅命令，这样"仅命令"意味着"工作流操作是斜杠命令"，而不是"代理得不到任何 OpenSpec 上下文"。
- 更简单的可能切片：将 `use-openspec` 视为一个与配置器捆绑并按默认安装的正常托管技能。即使它作为默认配置文件的一部分呈现，也保持其为仅技能，这样它不会创建斜杠命令、工作流构件或面向用户的工作流操作。
- 重新思考 `openspec initiative create` 作为一个稀疏的、架构驱动的容器，而不是一个完全脚手架化的规划包。初始创建可能只写 `initiative.yaml` 加上一个从标题和摘要播种的简短 `brief.md`。后续的代理/CLI 操作可以在有审查内容需要捕获时添加 `requirements.md`、`design.md`、`questions.md`、`decisions.md` 或协调构件。避免默认的 `TBD` 章节、虚假决策和可能与仓库本地实施任务混淆的默认倡议级别 `tasks.md`。
- 手动后续将测试倡议 `agent-trace-hooks` 转换为建议的稀疏形状：保留 `initiative.yaml`，添加 `brief.md`，移除了过早生成的规划文件。`initiative show` 仍然可以解析，因为当前倡议身份取决于 `initiative.yaml`。
- 将更广泛的修复提升到 `work-items/15-context-store-project-roots-and-schema-led-initiatives/`：上下文存储应作为共享上下文的 OpenSpec 根目录，具有存储本地配置、架构和稀疏的架构驱动倡议构件。
- 工作区形状修正：托管工作区视图不应看起来像仓库。新的工作区视图应包含生成的根文件（`AGENTS.md`、`workspace.yaml` 和 `<workspace>.code-workspace`），没有默认的 `changes/` 目录或生成的 `.gitignore`；VS Code 多根视图应首先显示链接的仓库，然后是倡议上下文，最后是小的 OpenSpec 工作区文件夹。
- 指南修正：打开工作区后，用户应让代理使用倡议进行探索或起草。代理应解析工作区状态、倡议上下文和链接仓库所有权，然后从拥有仓库运行仓库本地的 OpenSpec 命令。面向用户的流程不应让人类输入 `openspec new change` 或 `cd` 进入实施仓库。
