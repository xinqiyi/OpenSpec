# artifact-graph 规范

## 目的
定义 schema 驱动工作流使用的工件图模型、依赖验证和完成状态逻辑。

## 需求
### 需求：Schema 加载
系统应从 schema 目录中的 YAML schema 文件加载工件图定义。

#### 场景：加载有效 schema
- **当** schema 目录包含有效的 `schema.yaml` 文件
- **则** 系统返回包含所有工件和依赖关系的 ArtifactGraph

#### 场景：拒绝无效 schema
- **当** schema YAML 文件缺少必需字段
- **则** 系统抛出带有描述性消息的错误

#### 场景：检测到循环依赖
- **当** schema 包含循环的工件依赖关系
- **则** 系统抛出错误，列出循环中的工件 ID

#### 场景：无效的依赖引用
- **当** 工件的 `requires` 数组引用了不存在的工件 ID
- **则** 系统抛出错误，指出无效的引用

#### 场景：拒绝重复的工件 ID
- **当** schema 包含多个具有相同 ID 的工件
- **则** 系统抛出错误，指出重复项

#### 场景：未找到 schema 目录
- **当** 解析的 schema 名称没有对应的目录
- **则** 系统抛出错误，列出可用的 schema

### 需求：构建顺序计算
系统应计算工件的有效拓扑构建顺序。

#### 场景：线性依赖链
- **当** 工件形成线性链（A → B → C）
- **则** getBuildOrder() 返回 [A, B, C]

#### 场景：菱形依赖
- **当** 工件形成菱形（A → B, A → C, B → D, C → D）
- **则** getBuildOrder() 返回 A 在 B 和 C 之前，D 最后

#### 场景：独立工件
- **当** 工件没有依赖关系
- **则** getBuildOrder() 以稳定的顺序返回它们

### 需求：状态检测
系统应通过扫描文件系统检测工件的完成状态。

#### 场景：简单文件存在
- **当** 工件生成 "proposal.md" 且文件存在
- **则** 工件标记为已完成

#### 场景：简单文件缺失
- **当** 工件生成 "proposal.md" 且文件不存在
- **则** 工件未标记为已完成

#### 场景：包含文件的 Glob 模式
- **当** 工件生成 "specs/*.md" 且 specs/ 目录包含 .md 文件
- **则** 工件标记为已完成

#### 场景：Glob 模式为空
- **当** 工件生成 "specs/*.md" 且 specs/ 目录为空或不存在
- **则** 工件未标记为已完成

#### 场景：缺少变更目录
- **当** 变更目录不存在
- **则** 所有工件标记为未完成（空状态）

### 需求：就绪工件查询
系统应根据依赖完成情况识别哪些工件可以创建。

#### 场景：根工件初始就绪
- **当** 没有工件已完成
- **则** getNextArtifacts() 返回没有依赖关系的工件

#### 场景：依赖工件变为就绪
- **当** 工件的所有依赖项都已完成
- **则** getNextArtifacts() 包含该工件

#### 场景：排除阻塞工件
- **当** 工件有未完成的依赖项
- **则** getNextArtifacts() 不包含该工件

### 需求：完成检查
系统应确定图中的所有工件是否都已完成。

#### 场景：全部完成
- **当** 图中的所有工件都在已完成集合中
- **则** isComplete() 返回 true

#### 场景：部分完成
- **当** 图中的某些工件未完成
- **则** isComplete() 返回 false

### 需求：阻塞查询
系统应识别哪些工件被阻塞，并返回它们所有未满足的依赖项。

#### 场景：工件被单个依赖阻塞
- **当** 工件 B 需要工件 A 且 A 未完成
- **则** getBlocked() 返回 `{ B: ['A'] }`

#### 场景：工件被多个依赖阻塞
- **当** 工件 C 需要 A 和 B，且只有 A 完成
- **则** getBlocked() 返回 `{ C: ['B'] }`

#### 场景：工件被所有依赖阻塞
- **当** 工件 C 需要 A 和 B，且两者都未完成
- **则** getBlocked() 返回 `{ C: ['A', 'B'] }`

### 需求：Schema 目录结构
系统应支持带有同位置模板的自包含 schema 目录。

#### 场景：带模板的 Schema
- **当** schema 目录包含 `schema.yaml` 和 `templates/` 子目录
- **则** 工件可以引用相对于 schema 模板目录的模板

#### 场景：用户 Schema 覆盖
- **当** `${XDG_DATA_HOME}/openspec/schemas/<name>/` 存在 schema 目录
- **则** 系统使用该目录替代内置目录

#### 场景：内置 Schema 回退
- **当** schema 不存在用户覆盖
- **则** 系统使用包内置的 schema 目录

#### 场景：列出可用 Schema
- **当** 列出 schema
- **则** 系统返回用户目录和包目录中的 schema 名称

### 需求：工作区规划 schema
工件图应提供用于工作区范围变更的内置工作区规划 schema。

#### 场景：内置工作区规划 schema 可用
- **当** 从包内置项解析 schema
- **则** 应提供一个名为 `workspace-planning` 的 schema
- **且** 它应描述工作区范围规划的工件结构

#### 场景：工作区规划 schema 工件
- **当** 加载 `workspace-planning` schema
- **则** 它应包含用于共享提案、工作区范围规范、跨区域设计和协调任务的正常规划工件
- **且** 它不应要求在这些正常规划工件之外再提供额外的区域清单

#### 场景：工作区规划 schema 支持嵌套规范
- **当** `workspace-planning` schema 定义其规范工件
- **则** 规范工件应在 `specs/**/*.md` 下解析工作区范围的规范文件
- **且** schema 指导应将 `specs/<area-or-repo>/<capability>/spec.md` 描述为按区域划分需求的默认约定

#### 场景：工作区规划 schema 模板
- **当** 请求 `workspace-planning` schema 的工件指令
- **则** schema 应提供指导代理编写工作区级别规划内容的模板
- **且** 这些模板应避免指示代理创建仓库本地的实现工件
- **且** 规范指令应支持在工作区范围的 `specs/` 路径下组织按区域划分的需求

#### 场景：工作区嵌套规范路径保持工作区范围
- **给定** 工作区变更在 `specs/<area-or-repo>/<capability>/spec.md` 下有规范文件
- **当** OpenSpec 报告工作区变更的状态或工件指令
- **则** 它应保留具体的嵌套工作区规范路径
- **且** 它不应将这些文件视为仓库本地规范进行同步或归档，除非有明确的影响区域实现上下文

#### 场景：工作区规划 apply 就绪
- **当** `workspace-planning` schema 定义 apply 就绪条件
- **则** 它应在实现开始之前要求完成协调任务
- **且** apply 指导应引导代理在选择影响区域后再进行实现编辑
