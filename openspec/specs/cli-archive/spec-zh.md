# CLI Archive 命令规范

## 目的
archive 命令将已完成的变更从活动变更目录移动到归档文件夹，采用基于日期的命名，遵循 OpenSpec 约定。

## 命令语法
```bash
openspec archive [change-name] [--yes|-y]
```

选项：
- `--yes`、`-y`：跳过确认提示（用于自动化）
## 需求
### 需求：变更选择

该命令应支持交互式和直接变更选择方法。

#### 场景：交互式选择

- **当**未提供 change-name 时
- **那么**显示可用变更的交互式列表（排除 archive/）
- **并且**允许用户选择一个

#### 场景：直接选择

- **当**提供了 change-name 时
- **那么**直接使用该变更
- **并且**验证其是否存在

### 需求：任务完成检查

该命令应在归档前验证任务完成状态，以防止过早归档。

#### 场景：发现未完成任务

- **当**发现未完成任务时（标记为 `- [ ]`）
- **那么**向用户显示所有未完成任务
- **并且**提示确认是否继续
- **并且**为安全起见默认"否"

#### 场景：所有任务完成

- **当**所有任务都完成或没有 tasks.md 时
- **那么**无需提示直接进行归档

### 需求：归档过程

归档操作应遵循结构化的过程，以安全地将变更移动到归档。

#### 场景：执行归档

- **当**归档一个变更时
- **那么**执行以下步骤：
  1. 如果 archive/ 目录不存在则创建
  2. 使用当前日期生成目标名称 `YYYY-MM-DD-[change-name]`
  3. 检查目标目录是否已存在
  4. 从变更的未来状态规范更新主规范（参见下面的规范更新过程）
  5. 将整个变更目录移动到归档位置

#### 场景：归档已存在

- **当**目标归档已存在时
- **那么**失败并显示错误消息
- **并且**不覆盖现有归档

#### 场景：成功归档

- **当**移动成功时
- **那么**显示成功消息，包含归档名称和已更新的规范列表

### 需求：规范更新过程

在将变更移动到归档之前，该命令应将 delta 更改应用于主规范，以反映部署后的实际情况。

#### 场景：应用 delta 更改

- **当**归档具有基于 delta 的规范的变更时
- **那么**按照 openspec-conventions 中的定义解析并应用 delta 更改
- **并且**在应用前验证所有操作

#### 场景：验证 delta 更改

- **当**处理 delta 更改时
- **那么**按照 openspec-conventions 中的规定执行验证
- **并且**如果验证失败，显示具体错误并中止

#### 场景：冲突检测

- **当**应用 delta 会创建重复的需求标题时
- **那么**中止并显示显示冲突的错误消息
- **并且**建议手动解决

### 需求：确认行为

规范更新确认应在更改应用前提供清晰的可见性。

#### 场景：显示确认

- **当**提示确认时
- **那么**显示清晰的摘要，显示：
  - 将创建哪些规范（新能力）
  - 将更新哪些规范（现有能力）
  - 每个规范的来源路径
- **并且**将确认提示格式化为：
  ```
  将更新以下规范：
  
  将创建的新规范：
    - cli-archive（来自 changes/add-archive-command/specs/cli-archive/spec.md）
  
  将更新的现有规范：
    - cli-init（来自 changes/update-init-command/specs/cli-init/spec.md）
  
  更新 2 个规范并归档 'add-archive-command'？[y/N]：
  ```
#### 场景：处理确认响应

- **当**等待用户确认时
- **那么**为安全起见默认"否"（需要显式的"y"或"yes"）
- **并且**当提供了 `--yes` 或 `-y` 标志时跳过确认

#### 场景：用户拒绝确认

- **当**用户拒绝确认时
- **那么**中止整个归档操作
- **并且**显示消息："归档已取消。未进行任何更改。"
- **并且**以非零状态码退出

### 需求：错误条件

该命令应优雅地处理各种错误条件。

#### 场景：处理错误

- **当**发生错误时
- **那么**处理以下情况：
  - 缺少 openspec/changes/ 目录
  - 未找到变更
  - 归档目标已存在
  - 文件系统权限问题

### 需求：跳过规范选项

archive 命令应支持 `--skip-specs` 标志，该标志跳过所有规范更新操作并直接进行归档。

#### 场景：使用标志跳过规范更新

- **当**执行 `openspec archive <change> --skip-specs` 时
- **那么**跳过规范发现和更新确认
- **并且**直接进行将变更移动到归档
- **并且**显示指示规范已被跳过的消息

### 需求：非阻塞确认

当用户拒绝规范更新时，归档操作应继续进行，而不是取消整个操作。

#### 场景：用户拒绝规范更新确认

- **当**用户拒绝规范更新确认时
- **那么**跳过规范更新
- **并且**继续进行归档操作
- **并且**显示指示规范未更新的成功消息

### 需求：显示输出

该命令应提供关于 delta 操作的清晰反馈。

#### 场景：显示 delta 应用

- **当**应用 delta 更改时
- **那么**为每个规范显示：
  - 添加的需求数量
  - 修改的需求数量
  - 移除的需求数量
  - 重命名的需求数量
- **并且**使用 openspec-conventions 中定义的标准输出符号（+ ~ - →）：
  ```
  正在将更改应用到 specs/user-auth/spec.md：
    + 2 个已添加
    ~ 3 个已修改
    - 1 个已移除
    → 1 个已重命名
  ```

### 需求：归档验证

archive 命令应在应用更改前验证变更，以确保数据完整性。

#### 场景：归档前验证

- **当**执行 `openspec archive change-name` 时
- **那么**首先验证变更结构
- **并且**仅当验证通过时才继续
- **并且**如果验证失败，显示验证错误

#### 场景：不带验证的强制归档

- **当**执行 `openspec archive change-name --no-validate` 时
- **那么**跳过验证（不安全模式）
- **并且**显示关于跳过验证的警告

## 为何做出这些决策

**交互式选择**：减少输入并帮助用户查看可用的变更
**任务检查**：防止意外归档未完成的工作
**日期前缀**：维护时间顺序并防止命名冲突
**不覆盖**：保留历史归档并防止数据丢失
**归档前规范更新**：主目录中的规范代表当前实际情况；当变更被部署和归档时，其未来状态规范成为新的实际情况，必须替换主规范
**规范更新确认**：提供将要更改的内容的可见性，防止意外覆盖，并确保用户在规范被修改前了解影响
**用于自动化的 --yes 标志**：允许 CI/CD 管道在无需交互式提示的情况下归档，同时默认为手动使用保持安全性
