# cli-artifact-workflow 规范

## 目的
定义脚手架化和活跃变更的构件工作流 CLI 行为（`status`、`instructions`、`templates` 和设置流程）。

## 需求
### 需求：状态命令

系统应当显示变更的构件完成状态，包括脚手架化（空）变更。

> **修复了 Bug**：之前通过 `getActiveChangeIds()` 要求 `proposal.md` 必须存在。

#### 场景：显示包含所有状态

- **当** 用户运行 `openspec status --change <id>`
- **那么** 系统显示每个构件及其状态指示：
  - `[x]` 表示已完成的构件
  - `[ ]` 表示就绪的构件
  - `[-]` 表示被阻塞的构件（列出缺失的依赖）

#### 场景：状态显示完成摘要

- **当** 用户运行 `openspec status --change <id>`
- **那么** 输出包括完成百分比和计数（例如，"2/4 构件已完成"）

#### 场景：状态 JSON 输出

- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 系统输出 JSON，包含 changeName、schemaName、isComplete 和 artifacts 数组

#### 场景：状态 JSON 包含应用阶段要求

- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 系统输出 JSON，包含：
  - `changeName`、`schemaName`、`isComplete`、`artifacts` 数组
  - `applyRequires`：应用阶段所需的构件 ID 数组

#### 场景：脚手架化变更的状态

- **当** 用户对没有构件的变更运行 `openspec status --change <id>`
- **那么** 系统显示所有构件及其状态
- **且** 根构件（无依赖）显示为就绪 `[ ]`
- **且** 依赖构件显示为被阻塞 `[-]`

#### 场景：缺少 change 参数

- **当** 用户运行 `openspec status` 而不带 `--change`
- **那么** 系统显示错误，并列出现有的可用变更
- **且** 包括脚手架化变更（没有 proposal.md 的目录）

#### 场景：未知变更

- **当** 用户运行 `openspec status --change unknown-id`
- **且** 目录 `openspec/changes/unknown-id/` 不存在
- **那么** 系统显示错误，列出所有可用的变更目录

### 需求：下一个构件发现

工作流应当使用 `openspec status` 输出来确定下一步可以创建什么，而不是使用独立的 next-command 接口。

#### 场景：从状态输出中发现下一个构件

- **当** 用户需要知道接下来要创建哪个构件
- **那么** `openspec status --change <id>` 标识出 `[ ]` 状态的就绪构件
- **且** 不需要专门的"next command"来继续工作流

### 需求：指令命令

系统应当输出用于创建构件的增强指令，包括针对脚手架化变更的指令。

#### 场景：显示增强指令

- **当** 用户运行 `openspec instructions <artifact> --change <id>`
- **那么** 系统输出：
  - 构件元数据（ID、输出路径、描述）
  - 模板内容
  - 依赖状态（已完成/缺失）
  - 解锁的构件（完成后可用的内容）

#### 场景：指令 JSON 输出

- **当** 用户运行 `openspec instructions <artifact> --change <id> --json`
- **那么** 系统输出符合 ArtifactInstructions 接口的 JSON

#### 场景：未知构件

- **当** 用户运行 `openspec instructions unknown-artifact --change <id>`
- **那么** 系统显示错误，列出该架构的有效构件 ID

#### 场景：依赖未满足的构件

- **当** 用户请求被阻塞构件的指令
- **那么** 系统显示指令并附带缺失依赖的警告

#### 场景：脚手架化变更的指令

- **当** 用户对脚手架化变更运行 `openspec instructions proposal --change <id>`
- **那么** 系统输出用于创建 proposal 的模板和元数据
- **且** 不要求已有任何构件存在

### 需求：模板命令
系统应当显示架构中所有构件的已解析模板路径。

#### 场景：使用默认架构列出模板路径
- **当** 用户运行 `openspec templates`
- **那么** 系统使用默认架构显示每个构件及其已解析的模板路径

#### 场景：使用自定义架构列出模板路径
- **当** 用户运行 `openspec templates --schema tdd`
- **那么** 系统显示指定架构的模板路径

#### 场景：模板 JSON 输出
- **当** 用户运行 `openspec templates --json`
- **那么** 系统输出将构件 ID 映射到模板路径的 JSON

#### 场景：模板解析来源
- **当** 显示模板路径时
- **那么** 系统指示每个模板是来自用户覆盖还是包内置

### 需求：新建变更命令
系统应当创建带有验证的新变更目录。

#### 场景：创建有效变更
- **当** 用户运行 `openspec new change add-feature`
- **那么** 系统创建 `openspec/changes/add-feature/` 目录

#### 场景：无效变更名称
- **当** 用户使用无效名称运行 `openspec new change "Add Feature"`
- **那么** 系统显示带有指导的验证错误

#### 场景：重复变更名称
- **当** 用户对已存在的变更运行 `openspec new change existing-change`
- **那么** 系统显示错误，指示该变更已存在

#### 场景：附带描述创建
- **当** 用户运行 `openspec new change add-feature --description "Add new feature"`
- **那么** 系统创建变更目录，并在 README.md 中包含描述

### 需求：工作区设置命令
CLI 构件工作流应当在创建变更之前公开工作区设置命令。

#### 场景：在变更前准备工作区规划
- **当** 用户需要跨仓库或文件夹准备工作区规划
- **那么** CLI 应当提供设置、列出、链接、重新链接和诊断工作区的命令
- **且** 这些命令不应要求存在活跃的工作区变更

#### 场景：使用简短命令列出工作区
- **当** 用户需要简洁的工作区列表命令
- **那么** CLI 应当支持 `openspec workspace ls`
- **且** 其行为应与 `openspec workspace list` 相同

#### 场景：将设置与代理启动分开
- **当** 用户完成工作区设置
- **那么** 设置工作流应将代理启动和工作区打开行为留给后面的工作流
- **且** 设置不应要求首选代理选择

#### 场景：避免公开直接创建
- **当** 用户在首次工作区设置流程中创建工作区
- **那么** CLI 应使用 `openspec workspace setup`
- **且** 不应将 `openspec workspace create` 公开为公共创建路径

### 需求：架构选择
系统应当支持工作流命令的自定义架构选择。

#### 场景：默认架构
- **当** 用户运行不带 `--schema` 的工作流命令
- **那么** 系统使用 "spec-driven" 架构

#### 场景：自定义架构
- **当** 用户运行 `openspec status --change <id> --schema tdd`
- **那么** 系统对构件图使用指定的架构

#### 场景：未知架构
- **当** 用户指定未知架构
- **那么** 系统显示错误列出现有可用架构

### 需求：输出格式
系统应当提供一致的输出格式。

#### 场景：彩色输出
- **当** 终端支持颜色
- **那么** 状态指示器使用颜色：绿色（已完成）、黄色（就绪）、红色（被阻塞）

#### 场景：无颜色输出
- **当** 使用 `--no-color` 标志或设置了 `NO_COLOR` 环境变量
- **那么** 输出仅使用文本指示器，不带 ANSI 颜色

#### 场景：进度指示
- **当** 加载变更状态需要时间
- **那么** 系统在加载期间显示旋转指示器

### 需求：实验性隔离
系统应当以隔离方式实现构件工作流命令，以便于移除。

#### 场景：单文件实现
- **当** 实现构件工作流功能时
- **那么** 所有命令位于 `src/commands/artifact-workflow.ts`

#### 场景：帮助文本标记
- **当** 用户在任何构件工作流命令上运行 `--help`
- **那么** 帮助文本指示该命令是实验性的

### 需求：架构应用阶段块

系统应当支持架构定义中的 `apply` 块，用于控制何时以及如何开始实现。

#### 场景：带 apply 块的架构

- **当** 架构定义了 `apply` 块
- **那么** 系统使用 `apply.requires` 确定在应用阶段之前必须存在哪些构件
- **且** 使用 `apply.tracks` 标识进度跟踪文件（如果没有则为 null）
- **且** 使用 `apply.instruction` 作为向代理显示的指导

#### 场景：不带 apply 块的架构

- **当** 架构没有 `apply` 块
- **那么** 系统要求所有构件都存在后才可以进行应用阶段
- **且** 使用默认指令："所有构件已完成。开始实施。"

### 需求：应用阶段指令命令

系统应当通过 `openspec instructions apply` 生成感知架构的应用阶段指令。

#### 场景：生成应用阶段指令

- **当** 用户运行 `openspec instructions apply --change <id>`
- **且** 所有必需的构件（根据架构的 `apply.requires`）都存在
- **那么** 系统输出：
  - `contextFiles`：将构件 ID 映射到所有现有构件的具体路径数组
  - 架构特定的指令文本
  - 进度跟踪文件路径（如果设置了 `apply.tracks`）

#### 场景：因缺少构件而阻塞应用阶段

- **当** 用户运行 `openspec instructions apply --change <id>`
- **且** 必需的构件缺失
- **那么** 系统指示应用阶段被阻塞
- **且** 列出必须先创建的构件

#### 场景：应用阶段指令 JSON 输出

- **当** 用户运行 `openspec instructions apply --change <id> --json`
- **那么** 系统输出 JSON，包含：
  - `contextFiles`：将构件 ID 映射到现有构件的具体路径数组的对象
  - `instruction`：应用阶段指令文本
  - `tracks`：进度文件路径或 null
  - `applyRequires`：必需的构件 ID 列表

### 需求：工具选择标志

`artifact-experimental-setup` 命令应当接受 `--tool <tool-id>` 标志来指定目标 AI 工具。

#### 场景：通过标志指定工具

- **当** 用户运行 `openspec artifact-experimental-setup --tool cursor`
- **那么** 技能文件生成在 `.cursor/skills/` 目录下
- **且** 命令文件使用 Cursor 的 frontmatter 格式生成

#### 场景：缺少工具标志

- **当** 用户运行 `openspec artifact-experimental-setup` 而不带 `--tool`
- **那么** 系统显示错误，要求提供 `--tool` 标志
- **且** 在错误消息中列出有效的工具 ID

#### 场景：未知工具 ID

- **当** 用户运行 `openspec artifact-experimental-setup --tool unknown-tool`
- **且** 该工具 ID 不在 `AI_TOOLS` 中
- **那么** 系统显示错误列出现有有效的工具 ID

#### 场景：没有 skillsDir 的工具

- **当** 用户指定了一个没有配置 `skillsDir` 的工具
- **那么** 系统显示错误，指示该工具不支持技能生成

#### 场景：没有命令适配器的工具

- **当** 用户指定了一个有 `skillsDir` 但没有注册命令适配器的工具
- **那么** 技能文件生成成功
- **且** 命令生成被跳过，并显示信息性消息

### 需求：输出消息

设置命令应当显示关于生成了什么的清晰输出。

#### 场景：在输出中显示目标工具

- **当** 设置命令成功运行
- **那么** 输出包括目标工具名称（例如，"正在为 Cursor 设置..."）

#### 场景：显示生成的路径

- **当** 设置命令完成
- **那么** 输出列出所有生成的技能文件路径
- **且** 列出所有生成的命令文件路径（如果适用）

#### 场景：显示跳过的命令消息

- **当** 命令生成因缺少适配器而被跳过
- **那么** 输出包括消息："命令生成已跳过 - 没有适用于 <tool> 的适配器"

### 需求：状态 JSON 提供规划上下文
状态命令应当为仓库本地和工作区变更提供机器可读的规划上下文。

#### 场景：报告规划根目录
- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 输出应当标识变更是仓库本地还是工作区范围
- **且** 应包括规划根目录和变更根目录

#### 场景：报告具体构件路径
- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 输出应当包含现有构件的具体路径
- **且** 代理应当能够读取这些路径，而不假设为 `openspec/changes/<id>/`
- **且** 工作区范围的嵌套规范路径应当在不展平区域或能力路径的情况下报告

#### 场景：报告工作区受影响区域
- **给定** 变更是工作区范围的
- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 输出应当包含已知的受影响区域
- **且** 应在受影响区域仍未解决时进行指示，而无需额外的区域清单构件

#### 场景：报告下一步
- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 输出应当包含给代理的下一步指导
- **且** 指导应使用简洁的操作语言

### 需求：状态 JSON 操作上下文
状态命令应当公开操作上下文，使代理无需硬编码的文件系统假设即可行动。

#### 场景：规划操作上下文
- **当** 工作区变更仍在规划中
- **那么** 状态 JSON 应当标识代理可以读取或更新的规划构件
- **且** 应指示链接的仓库和文件夹是用于探索的上下文

#### 场景：实施操作上下文
- **当** 工作区变更有选定的受影响区域用于实施
- **那么** 状态 JSON 应当包括该区域的允许编辑根目录
- **且** 应避免授权对该选定区域之外的编辑

#### 场景：仓库本地操作上下文
- **给定** 变更是仓库本地的
- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 状态 JSON 应当保留现有的构件状态行为
- **且** 应为使用操作上下文的代理报告仓库本地规划根目录

### 需求：指令使用已解析的规划路径
构件和应用阶段指令应使用已解析的规划路径，而不是硬编码的仓库本地变更路径。

#### 场景：工作区构件指令
- **给定** 变更是工作区范围的
- **当** 用户运行 `openspec instructions <artifact> --change <id> --json`
- **那么** 指令输出应指向工作区变更根目录下的构件路径
- **且** 除非有明确的实施上下文允许，否则不应指示代理在链接的仓库下写入

#### 场景：仓库本地构件指令
- **给定** 变更是仓库本地的
- **当** 用户运行 `openspec instructions <artifact> --change <id> --json`
- **那么** 指令输出应保留现有的仓库本地路径

### 需求：工作流技能使用 CLI 构件上下文
生成的工作流技能应使用 OpenSpec CLI 输出作为构件位置的唯一真实来源。

#### 场景：技能在构件工作前检查状态
- **当** 生成的工作流技能需要检查或创建变更的构件时
- **那么** 它应指示代理运行 `openspec status --change <id> --json`
- **且** 应使用返回的规划上下文和构件路径，而不是假设仓库本地变更路径

#### 场景：技能在写入构件前使用指令
- **当** 生成的工作流技能即将创建或更新构件时
- **那么** 它应指示代理运行 `openspec instructions <artifact> --change <id> --json`
- **且** 应写入命令返回的已解析构件路径

#### 场景：技能避免硬编码的仓库本地路径
- **当** 生成的工作流技能描述构件位置时
- **那么** 它们应避免要求变更位于 `openspec/changes/<id>/` 下的硬编码示例
- **且** 任何示例都应引用 CLI 报告的路径，适用于仓库本地和工作区范围的变更

#### 场景：技能保护不支持的工作区工作流
- **给定** 生成的工作流技能被全局配置文件选中
- **且** 该工作流在此切片中尚未具有完整的工作区范围行为
- **当** 该技能用于工作区范围的变更时
- **那么** 它应告知代理该工作区操作尚不支持
- **且** 不应指示代理回退到仓库本地路径或在没有明确允许编辑根目录的情况下编辑链接的仓库

### 需求：工作区架构指令
工作流命令应对使用工作区规划架构的工作区范围变更使用工作区规划架构指令。

#### 场景：工作区规划构件顺序
- **给定** 工作区范围变更使用架构 `workspace-planning`
- **当** 用户运行 `openspec status --change <id> --json`
- **那么** 构件列表应反映工作区规划架构
- **且** 应包括正常的 proposal、specs、design 和 tasks 构件

#### 场景：工作区规范指令
- **给定** 工作区范围变更使用架构 `workspace-planning`
- **当** 用户请求 specs 构件的指令时
- **那么** 指令输出应指导代理在工作区范围的 `specs/` 路径下组织特定区域的需求
- **且** 不应要求所有受影响区域在规划继续之前都最终确定
- **且** 不应指示代理在变更仍在工作区规划中时创建仓库本地规范文件
