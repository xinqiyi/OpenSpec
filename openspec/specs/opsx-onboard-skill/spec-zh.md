# opsx-onboard-skill 规范

## 目的
定义 `/opsx:onboard` 的行为，用于引导用户在其真实代码库中完成端到端的 OpenSpec 工作流。

## 需求
### 需求：OPSX Onboard 技能

系统应提供一个 `/opsx:onboard` 技能，通过解说和真实代码库工作，引导用户完成他们的第一个完整 OpenSpec 工作流周期。

#### 场景：技能调用

- **当** 用户调用 `/opsx:onboard`
- **则** 代理检查 OpenSpec 是否已初始化
- **且** 如果未初始化，提示用户先运行 `openspec init`
- **且** 如果已初始化，继续执行入门流程

#### 场景：欢迎和预期

- **当** 入门开始时
- **则** 代理显示欢迎消息，解释将要发生什么
- **且** 设置约 15 分钟的时长预期
- **且** 解释工作流阶段：探索 → 新建 → 工件 → 应用 → 归档

### 需求：用于任务建议的代码分析

技能应分析用户的代码库，以建议范围适中的入门级任务。

#### 场景：代码扫描

- **当** 入门到达任务选择阶段
- **则** 代理扫描代码库寻找小的改进机会
- **且** 查找：TODO/FIXME 注释、缺失的错误处理、缺少测试的函数、过时的依赖、TypeScript 中的 type: any、生产代码中的 console.log、缺失的输入验证
- **且** 检查最近的 git 提交以了解当前工作的上下文

#### 场景：任务建议展示

- **当** 代理已分析代码库
- **则** 代理展示 3-4 个具体的任务建议，附带范围估算
- **且** 每个建议包括：任务描述、估算范围（文件/行数）、为何是好的入门任务
- **且** 提供让用户自行指定任务的选项

#### 场景：范围防护

- **当** 用户选择或描述的任务过大
- **则** 代理温和地引导其转向较小的范围
- **且** 建议拆分或推迟大任务
- **且** 提供大小合适的替代方案

### 需求：探索阶段演示

技能应在创建变更前简要演示探索模式。

#### 场景：简要探索演示

- **当** 任务已选择
- **则** 代理通过调查相关代码简要演示 `/opsx:explore`
- **且** 解释探索模式是在行动之前的思考
- **且** 保持此阶段简短（不是完整的探索会议）
- **且** 过渡到变更创建

### 需求：引导式工件创建

技能应通过解说引导用户创建每个工件，解释其用途。

#### 场景：带解说的变更创建

- **当** 创建变更目录时
- **则** 代理运行 `openspec new change "<name>"`，使用推导的 kebab-case 名称
- **且** 解释什么是"变更"（思考和规划的容器）
- **且** 显示已创建的文件夹结构
- **且** 在继续前暂停等待用户确认

#### 场景：带解说的提案创建

- **当** 创建 proposal.md 时
- **则** 代理解释提案记录我们为什么要做这个变更
- **且** 基于选定的任务起草提案
- **且** 在保存前向用户展示草稿以获批准
- **且** 解释各部分（Why, What Changes, Capabilities, Impact）

#### 场景：带解说的规范创建

- **当** 创建规范文件时
- **则** 代理解释规范详细定义我们要构建什么
- **且** 解释需求/场景格式
- **且** 基于提案的能力创建规范文件
- **且** 说明规范会成为保持同步的文档

#### 场景：带解说的设计创建

- **当** 创建 design.md 时
- **则** 代理解释设计记录我们将如何构建
- **且** 说明这是技术决策和权衡所在的地方
- **且** 对于小的变更，承认设计可能很简短
- **且** 基于提案和规范创建设计

#### 场景：带解说的任务创建

- **当** 创建 tasks.md 时
- **则** 代理解释任务将工作拆分为复选框
- **且** 解释这些驱动 apply 阶段
- **且** 从设计和规范生成任务列表
- **且** 显示任务并询问是否准备好实现

### 需求：引导式实现

技能应在实现任务时添加解说，将工作连接回工件。

#### 场景：带解说的实现

- **当** 实现任务时
- **则** 代理在开始处理每个任务前宣布它
- **且** 在代码库中实现变更
- **且** 偶尔提及规范/设计如何影响决策
- **且** 完成每个任务时标记为完成
- **且** 保持解说轻量（不过度解释）

#### 场景：实现完成

- **当** 所有任务完成时
- **则** 代理宣布完成
- **且** 总结完成了什么
- **且** 过渡到归档阶段

### 需求：带解释的归档

技能应归档完成的变更并解释发生了什么。

#### 场景：带解说的归档

- **当** 归档变更时
- **则** 代理解释归档将变更移动到带日期的文件夹
- **且** 运行归档过程
- **且** 显示归档变更存放的位置
- **且** 解释长期价值（以后查找决策）

### 需求：回顾和后续步骤

技能应以回顾和命令参考结束。

#### 场景：最终回顾

- **当** 入门完成时
- **则** 代理总结已完成的工作流阶段
- **且** 强调这个节奏适用于任何规模的变更
- **且** 提供命令参考表（/opsx:explore, /opsx:new, /opsx:ff, /opsx:continue, /opsx:apply, /opsx:verify, /opsx:archive）
- **且** 建议下一步操作（尝试 /opsx:new 或 /opsx:ff）

### 需求：优雅退出处理

技能应处理中途想要停止的用户。

#### 场景：用户想停止

- **当** 用户在入门过程中表示想停止
- **则** 代理优雅地确认
- **且** 说明进行中的变更已保存
- **且** 解释以后如何通过 `/opsx:continue <name>` 继续
- **且** 无压力退出

#### 场景：用户只想要快速参考

- **当** 用户说只想查看命令
- **则** 代理提供命令速查表
- **且** 优雅退出，鼓励尝试 `/opsx:new`
