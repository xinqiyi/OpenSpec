# workspace-links 规范

## 目的
定义管理跨仓库和文件夹的 OpenSpec 工作区时，直接工作区设置、发现、链接、重新链接、健康检查和 JSON 输出行为。

## 要求
### 要求：引导式工作区设置
OpenSpec 应为开始工作区规划的用户提供引导式设置流程。

#### 场景：通过设置创建工作区
- **当** 用户运行 `openspec workspace setup`
- **则** OpenSpec 应引导用户创建 OpenSpec 工作区
- **且** 工作区应使用工作区基础所规定的标准工作区位置

#### 场景：先询问工作区名称
- **当** 交互式设置开始时
- **则** OpenSpec 应在询问仓库或文件夹之前先询问工作区名称
- **且** 工作区名称应使用 kebab-case 格式，包含小写字母、数字和连字符

#### 场景：设置过程中重试无效的工作区名称
- **当** 交互式用户输入无效的工作区名称时
- **则** OpenSpec 应解释工作区名称必须为 kebab-case 格式
- **且** 应在继续设置之前让用户输入另一个工作区名称

#### 场景：链接所需的第一个仓库或文件夹
- **当** 设置询问仓库或文件夹时
- **则** 用户应提供至少一个现有的仓库或文件夹路径
- **且** 在链接至少一个路径之前，设置不应成功完成

#### 场景：设置过程中推断链接名称
- **当** 用户在设置过程中提供仓库或文件夹路径时
- **则** OpenSpec 应从文件夹的基本名称推断链接名称
- **且** 仅当推断的名称冲突时才询问不同的名称

#### 场景：处理设置过程中推断的链接名称冲突
- **给定** 设置推断的链接名称已存在于工作区中
- **当** 设置是交互式时
- **则** OpenSpec 应显示冲突的链接名称和该链接的现有路径
- **且** 应在继续之前要求用户提供不同的链接名称

#### 场景：保留文件夹风格的链接名称
- **当** OpenSpec 接受工作区链接名称时
- **则** 应允许在工作区基础链接名称规则下有效的文件夹风格名称
- **且** 不应要求链接名称使用更严格的工作区名称 kebab-case 规则

#### 场景：设置过程中添加多个仓库或文件夹
- **当** 设置链接一个仓库或文件夹时
- **则** OpenSpec 应让用户通过简单的重复提示添加另一个仓库或文件夹
- **且** 每个链接的路径应被记录而不编辑目标仓库或文件夹

#### 场景：设置过程中存储已验证的绝对路径
- **当** 设置链接一个仓库或文件夹路径时
- **则** OpenSpec 应验证该路径解析到现有文件夹
- **且** 应在机器本地状态中存储绝对运行时本地路径，而非原始用户输入
- **且** 相对输入应相对于命令的当前工作目录进行解析

#### 场景：保留设置链接路径中的等号
- **当** 非交互式设置收到一个 `--link` 值，该值解析到现有文件夹且包含 `=`
- **则** OpenSpec 应将完整值视为路径
- **且** 应从文件夹基本名称推断链接名称
- **且** 显式的 `--link <name>=<path>` 输入应保留 `<path>` 中的 `=` 字符

#### 场景：使用非交互式输入运行设置
- **当** `openspec workspace setup --no-interactive` 收到一个工作区名称和至少一个有效链接
- **则** OpenSpec 应创建工作区，无需提示
- **且** 应支持重复的 `--link` 值

#### 场景：非交互式设置重复的链接名称
- **当** `openspec workspace setup --no-interactive` 收到两个具有相同推断或显式名称的链接
- **则** OpenSpec 应失败并显示清晰的重复杂链接名称错误
- **且** 错误应显示冲突的链接名称和第一个使用该名称的路径
- **且** 应建议使用不同名称的显式 `--link <name>=<path>` 值

#### 场景：非交互式设置缺失输入
- **当** `openspec workspace setup --no-interactive` 缺少工作区名称或链接
- **则** OpenSpec 应失败并显示清晰的消息
- **且** 应解释哪些标志是必需的

#### 场景：完成设置
- **当** 设置完成时
- **则** OpenSpec 应显示工作区位置、规划路径和链接的仓库或文件夹
- **且** 应检查当前机器可以解析的内容

#### 场景：本地记录已创建的工作区
- **当** 设置创建工作区时
- **则** OpenSpec 应在本地工作区注册表中记录该工作区
- **且** 工作区文件夹应保持为工作区状态的真实依据

#### 场景：设置过程中重用已有的工作区名称
- **给定** 具有请求名称的受管理工作区已存在
- **当** 用户使用该工作区名称运行设置时
- **则** OpenSpec 应解释该工作区已存在
- **且** 不应覆盖现有工作区

### 要求：工作区发现
OpenSpec 应让用户查看当前机器上可用的 OpenSpec 受管理工作区。

#### 场景：列出售工作区
- **当** 用户运行 `openspec workspace list`
- **则** OpenSpec 应列出已知的受管理工作区
- **且** 每个工作区应包含工作区名称、工作区位置和链接的仓库或文件夹

#### 场景：使用简短列出命令
- **当** 用户运行 `openspec workspace ls`
- **则** OpenSpec 的行为应与 `openspec workspace list` 相同

#### 场景：没有工作区时列出
- **当** 用户运行 `openspec workspace list`
- **且** 没有受管理工作区存在
- **则** OpenSpec 应说明未找到工作区
- **且** 应向用户展示如何创建一个

#### 场景：列出过期的注册表条目
- **当** 本地注册表包含一个不再存在的工作区位置
- **则** `workspace list` 应报告过期的工作区条目
- **且** 应避免静默删除注册表状态
- **且** 应避免自动重写或修复注册表状态

#### 场景：避免注册表清理命令
- **当** 用户在此切片中检查过期的工作区注册表条目时
- **则** OpenSpec 应将过期条目视为仅报告的诊断信息
- **且** 不应暴露诸如 `workspace forget` 之类的注册表清理命令

### 要求：全局工作区命令
OpenSpec 应允许工作区命令从工作区目录之外运行。

#### 场景：通过标志选择工作区
- **当** 需要某个工作区的命令收到 `--workspace <name>`
- **则** OpenSpec 应从本地注册表中使用该工作区
- **且** 如果工作区名称未知，应清晰失败

#### 场景：使用当前工作区
- **给定** 命令从工作区文件夹或子目录运行
- **当** 命令需要一个工作区且未提供 `--workspace` 标志时
- **则** OpenSpec 应使用当前工作区

#### 场景：使用未注册的当前工作区
- **给定** 命令从有效的工作区文件夹或子目录运行
- **且** 该工作区未在本地工作区注册表中记录
- **当** 命令需要一个工作区且未提供 `--workspace <name>` 标志时
- **则** OpenSpec 应使用当前工作区
- **且** 应包含一个非致命警告状态，代码为 `workspace_not_in_local_registry`
- **且** 警告应解释用户如何让该工作区在本地注册

#### 场景：变更操作后注册未注册的当前工作区
- **给定** 一个变更型工作区命令使用一个不在本地工作区注册表中记录的有效当前工作区
- **当** `workspace link` 或 `workspace relink` 成功时
- **则** OpenSpec 应将工作区名称和位置记录在本地工作区注册表中

#### 场景：Doctor 不注册当前工作区
- **给定** `workspace doctor` 使用一个不在本地工作区注册表中记录的有效当前工作区
- **当** doctor 完成时
- **则** OpenSpec 应报告非致命的注册表警告
- **且** 不应写入注册表状态

#### 场景：从多个工作区中选择
- **给定** 存在多个已知工作区
- **当** 交互式命令需要一个工作区且未指定时
- **则** OpenSpec 应显示工作区选择器
- **且** 选择器应包含工作区名称和路径

#### 场景：模糊的非交互式工作区选择
- **给定** 存在多个已知工作区
- **当** 非交互式命令需要一个工作区且未指定时
- **则** OpenSpec 应失败并显示清晰的消息
- **且** 应建议传递 `--workspace <name>`

#### 场景：模糊的 JSON 工作区选择
- **给定** 存在多个已知工作区
- **当** 使用 `--json` 运行的命令需要一个工作区且未指定时
- **则** OpenSpec 应失败而不显示选择器
- **且** 应输出结构化的状态错误
- **且** 应建议传递 `--workspace <name>`

#### 场景：需要工作区的命令没有已知工作区
- **给定** 本地注册表中没有已知工作区
- **且** 命令不是从工作区文件夹或子目录运行
- **当** `workspace link`、`workspace relink`、`workspace doctor` 或其他需要一个工作区的命令在没有 `--workspace <name>` 的情况下运行时
- **则** OpenSpec 应失败而不显示选择器，无论交互模式如何
- **且** 应输出 `未找到已知的 OpenSpec 工作区。请先运行 'openspec workspace setup'。`
- **且** 应解释在至少一个工作区本地已知后可以使用 `--workspace <name>`

### 要求：工作区链接
OpenSpec 应让用户在创建变更之前将现有仓库或文件夹链接到工作区。

#### 场景：使用推断名称链接
- **当** 用户运行 `openspec workspace link <path>`
- **则** OpenSpec 应从文件夹基本名称推断链接名称
- **且** 应将已验证的绝对本地路径存储为机器本地状态

#### 场景：使用显式名称链接
- **当** 用户运行 `openspec workspace link <name> <path>`
- **则** OpenSpec 应使用显式链接名称进行规划
- **且** 应将已验证的绝对本地路径存储为机器本地状态

#### 场景：要求路径存在
- **当** 用户链接仓库或文件夹路径时
- **则** 该路径应在当前机器上存在
- **且** OpenSpec 应拒绝缺失的路径并给出清晰的消息

#### 场景：存储前解析链接路径
- **当** 用户链接仓库或文件夹路径时
- **则** OpenSpec 应存储当前运行时的已验证绝对路径
- **且** 相对输入应相对于命令的当前工作目录进行解析
- **且** OpenSpec 不应在原生 Windows、WSL2 和 Unix 运行时之间转换路径

#### 场景：链接单体仓库文件夹
- **当** 用户链接单体仓库内的包、服务、应用或目录时
- **则** OpenSpec 应将其存储为工作区链接
- **且** 不应要求该文件夹拥有自己的仓库本地 `openspec/` 目录

#### 场景：链接没有仓库本地 OpenSpec 的路径
- **当** 用户链接不包含仓库本地 OpenSpec 状态的路径时
- **则** OpenSpec 应保持该仓库或文件夹可用于工作区规划
- **且** 不应将缺少仓库本地 OpenSpec 状态视为链接失败

#### 场景：仅记录链接
- **当** 用户链接仓库或文件夹时
- **则** OpenSpec 应记录工作区状态和本地路径状态
- **且** 不应在链接的仓库或文件夹中创建、复制、移动、初始化或编辑文件

#### 场景：本地状态无效时阻止链接
- **给定** 工作区机器本地状态文件存在但无法解析或验证
- **当** 用户运行 `openspec workspace link`
- **则** OpenSpec 应失败，状态代码为 `workspace_local_state_invalid`
- **且** 不应重写共享工作区状态或机器本地路径状态

#### 场景：重复使用链接名称
- **给定** 工作区已有一个具有给定名称的链接
- **当** 用户尝试以相同名称链接另一个路径时
- **则** OpenSpec 应解释该链接名称已被另一个链接使用
- **且** 应显示现有的链接名称和现有路径
- **且** 应建议选择不同的链接名称
- **且** 当用户意图更改现有链接路径时，应建议 `workspace relink <name> <path>`
- **且** 应保留现有链接，除非用户显式重新链接它

### 要求：工作区重新链接
OpenSpec 应让用户更新现有链接路径，而无需重新创建工作区。

#### 场景：更新本地路径
- **给定** 工作区有一个链接
- **当** 用户运行 `openspec workspace relink <name> <path>`
- **则** OpenSpec 应保持稳定的链接名称
- **且** 应将当前机器的机器本地路径更新为已验证的绝对路径

#### 场景：要求重新链接路径存在
- **当** 用户重新链接到新路径时
- **则** 新路径应在当前机器上存在
- **且** OpenSpec 应拒绝缺失的路径并给出清晰的消息

#### 场景：存储前解析重新链接路径
- **当** 用户重新链接到新路径时
- **则** OpenSpec 应存储当前运行时的已验证绝对路径
- **且** 相对输入应相对于命令的当前工作目录进行解析

#### 场景：本地状态无效时阻止重新链接
- **给定** 工作区机器本地状态文件存在但无法解析或验证
- **当** 用户运行 `openspec workspace relink`
- **则** OpenSpec 应失败，状态代码为 `workspace_local_state_invalid`
- **且** 不应重写机器本地路径状态

#### 场景：更新未知链接
- **当** 用户尝试重新链接一个不存在的链接时
- **则** OpenSpec 应解释该链接名称未知
- **且** 应保留现有工作区状态

#### 场景：避免所有者与交接字段
- **当** 用户在此切片中链接或重新链接仓库或文件夹时
- **则** OpenSpec 不应询问所有者或交接元数据
- **且** 链接维护应聚焦于名称和本地路径

### 要求：工作区健康检查
OpenSpec 应解释当前机器可以对工作区解析哪些内容。

#### 场景：Doctor 检查一个选定的工作区
- **当** 用户运行 `openspec workspace doctor`
- **则** OpenSpec 应检查一个选定的工作区
- **且** 默认不应扫描本地注册表中的每个已知工作区

#### 场景：Doctor 推断当前工作区
- **给定** 命令从工作区文件夹或子目录运行
- **当** 用户运行不带 `--workspace <name>` 的 `openspec workspace doctor`
- **则** OpenSpec 应检查当前工作区

#### 场景：检查健康工作区
- **当** 用户运行 `openspec workspace doctor`
- **则** OpenSpec 应显示工作区位置和工作区规划路径
- **且** 应显示链接的仓库或文件夹以及哪些路径在当前机器上可解析

#### 场景：选定的工作区位置缺失
- **给定** 选定的工作区来自本地注册表
- **且** 已注册的工作区位置缺失或无效
- **当** 用户运行 `openspec workspace doctor`
- **则** OpenSpec 应报告选定工作区的状态错误
- **且** 不应尝试检查该工作区的链接

#### 场景：报告仓库本地 specs 路径
- **当** 链接的仓库或文件夹可解析时
- **则** doctor 应在仓库本地 `openspec/specs` 存在时报告 `repo_specs_path`
- **且** 当仓库本地 specs 不存在时报告 `repo_specs_path: null`

#### 场景：检查缺失路径
- **当** 链接指向当前机器上缺失的路径时
- **则** doctor 应标识受影响的链接名称
- **且** 应包含建议的 `workspace relink` 修复

#### 场景：检查共享状态与本地状态的漂移
- **当** 共享工作区状态与机器本地路径状态不一致时
- **则** doctor 应解释哪些链接名称受影响
- **且** 应区分共享工作区链接和仅本地路径

#### 场景：报告无效的本地状态
- **当** list 或 doctor 读取一个机器本地状态文件无法解析或验证的工作区时
- **则** OpenSpec 应报告状态代码 `workspace_local_state_invalid`
- **且** 应避免将无效的本地状态视为空路径映射用于变更或修复建议
- **且** 不应重写工作区注册表状态或机器本地路径状态

#### 场景：报告而不自动修复
- **当** doctor 发现问题时
- **则** 应报告它能找到的所有问题
- **且** 不应自动修复工作区状态

#### 场景：使用可读的人类输出
- **当** doctor 输出人类可读内容时
- **则** 应显示可读的工作区摘要、链接的仓库或文件夹以及存在的问题（如有）
- **且** 应避免将原始 JSON 或依赖严格 YAML 转储作为默认的人类体验

### 要求：可脚本化的工作区设置命令
OpenSpec 应为直接工作区设置命令提供 JSON 输出。

#### 场景：请求 JSON 输出
- **当** 用户向直接工作区设置命令传递 `--json`
- **则** OpenSpec 应输出机器可读的内容
- **且** 输出应避免多余的人类可读文本
- **且** 输出应将主要对象与结构化的 `status` 条目分开

#### 场景：设置 JSON 需要非交互式设置
- **当** 用户运行 `openspec workspace setup --json` 但不加 `--no-interactive`
- **则** OpenSpec 应清晰失败
- **且** 应解释 `workspace setup --json` 需要 `--no-interactive`

#### 场景：JSON 输出禁用提示
- **当** 直接工作区设置命令以 `--json` 运行时
- **则** OpenSpec 应避免交互式提示
- **且** 当所需选择不明确时，应以结构化状态输出失败

#### 场景：JSON 状态条目形态
- **当** 直接工作区设置命令在 JSON 输出中报告警告、错误或建议修复时
- **则** 每个状态条目应包含稳定的 `code`、`severity` 和人类可读的 `message`
- **且** 当特定对象字段或建议命令有用时，状态条目可以包含 `target` 和 `fix` 字段

#### 场景：JSON 对象状态形态
- **当** 直接工作区设置命令为工作区、链接或列表对象输出 JSON 时
- **则** 每个对象可以包含一个 `status` 数组，用于对象特定的警告或错误
- **且** 顶级响应应包含一个 `status` 数组，用于命令级别的警告或错误
- **且** 健康对象和健康响应应使用空的 `status` 数组

#### 场景：带 JSON 输出的命令
- **当** 用户运行 `workspace setup --no-interactive`、`workspace list`、`workspace link`、`workspace relink` 或 `workspace doctor`
- **则** 每个命令应支持 JSON 输出

### 要求：工作区设置安装代理技能
OpenSpec 应让用户在工作区设置期间将 OpenSpec 代理技能安装到工作区。

#### 场景：提示选择工作区代理技能
- **当** 交互式工作区设置到达代理技能安装步骤时
- **则** OpenSpec 应询问哪些代理应在该工作区中获得 OpenSpec 技能
- **且** 提示应使用"代理技能"语言而非"AI 工具"语言

#### 场景：预选首选开启器
- **给定** 用户选择了支持 OpenSpec 技能生成的首选开启器
- **当** 交互式工作区设置询问哪些代理应获得技能时
- **则** OpenSpec 应预选中匹配的代理
- **且** 用户应能够选择额外代理或取消预选已选代理

#### 场景：安装选定的工作区技能
- **当** 工作区设置完成时选择了至少一个代理
- **则** OpenSpec 应在工作区根目录下为每个选定的代理生成或刷新 OpenSpec 技能文件
- **且** 应报告哪些代理获得了技能
- **且** 应将选定的代理存储在工作区本地机器状态中

#### 场景：安装配置文件选定的工作流
- **给定** 全局配置解析为某个工作流配置文件
- **当** 工作区设置安装代理技能时
- **则** OpenSpec 应为该配置文件选定的工作流安装工作区本地技能
- **且** 应将 `--tools` 视为代理选择，而非工作流选择
- **且** 应记录上次应用的工作流 ID 以用于漂移检测

#### 场景：仅在设置期间安装技能
- **当** 工作区设置安装代理技能时
- **则** OpenSpec 应仅生成技能文件
- **且** 不应生成斜杠命令文件或全局命令文件作为工作区设置的一部分

#### 场景：工作区设置忽略命令交付方式
- **给定** 全局配置交付方式为 `commands` 或 `both`
- **当** 工作区设置安装代理技能时
- **则** OpenSpec 仍应仅生成工作区本地技能
- **且** 应报告工作区命令生成不属于此切片

#### 场景：技能安装期间保留已链接的仓库
- **当** 工作区设置安装代理技能时
- **则** OpenSpec 应保持已链接的仓库和文件夹不变
- **且** 生成的技能应限定在工作区规划家园范围内

#### 场景：非交互式设置工具选择
- **当** 非交互式工作区设置收到 `--tools all`、`--tools none` 或 `--tools <ids>`
- **则** OpenSpec 应使用选定的工具集进行工作区代理技能安装
- **且** 应使用与仓库初始化技能生成相同的受支持工具 ID 来验证工具 ID

#### 场景：非交互式设置未选择工具
- **当** 非交互式工作区设置省略 `--tools`
- **则** OpenSpec 应创建工作区而不安装代理技能
- **且** 应报告未安装工作区技能
- **且** 应告知用户稍后运行 `openspec workspace update --tools <ids>` 安装技能

#### 场景：在 JSON 输出中报告设置技能
- **当** 非交互式工作区设置安装代理技能且启用 JSON 输出时
- **则** OpenSpec 应在机器可读输出中包含已生成、刷新、跳过或失败的技能安装结果

### 要求：工作区更新管理代理技能
OpenSpec 应提供工作区更新流程，用于在设置后刷新代理技能。

#### 场景：更新当前工作区
- **给定** 命令从 OpenSpec 工作区内部运行
- **当** 用户运行 `openspec workspace update`
- **则** OpenSpec 应更新该当前工作区

#### 场景：更新命名工作区
- **给定** 名为 `platform` 的工作区在本地已知
- **当** 用户运行 `openspec workspace update platform`
- **则** OpenSpec 应更新 `platform` 工作区

#### 场景：通过标志更新选定的工作区
- **给定** 名为 `platform` 的工作区在本地已知
- **当** 用户运行 `openspec workspace update --workspace platform`
- **则** OpenSpec 应更新 `platform` 工作区

#### 场景：更新选定的工作区技能
- **当** 工作区更新完成且选定了代理
- **则** OpenSpec 应为选定的代理刷新 OpenSpec 技能
- **且** 应为新选定的代理添加技能
- **且** 应移除不再选定的代理的 OpenSpec 管理工作流技能目录
- **且** 应更新存储的工作区本地选定代理列表

#### 场景：识别管理工作流技能目录
- **当** 工作区更新评估要移除的工作流技能目录时
- **则** OpenSpec 仅当目录名称与已知的生成工作流技能目录匹配且其 `SKILL.md` 包含 OpenSpec 生成的元数据时，才将其视为 OpenSpec 管理的目录
- **且** 生成的元数据应包含 OpenSpec 技能生成写入的 `generatedBy` 标记
- **且** OpenSpec 不应移除缺少生成元数据的目录，即使其名称与已知工作流技能目录名称匹配

#### 场景：更新配置文件选定的工作流
- **给定** 全局配置解析为某个工作流配置文件
- **当** 工作区更新刷新工作区本地技能时
- **则** OpenSpec 应将工作区本地技能工作流集同步到该配置文件选定的工作流
- **且** 取消选定的工作流技能目录仅在其为已知的 OpenSpec 管理工作流技能目录时才被移除
- **且** 应更新上次用于漂移检测的应用工作流 ID

#### 场景：工作区更新忽略命令交付方式
- **给定** 全局配置交付方式为 `commands` 或 `both`
- **当** 工作区更新刷新工作区本地技能时
- **则** OpenSpec 仍应仅更新工作区本地技能
- **且** 不应生成斜杠命令文件或全局命令文件

#### 场景：仅移除受管理的技能目录
- **当** 工作区更新为未选定的代理移除技能时
- **则** OpenSpec 应仅移除已知的 OpenSpec 管理工作流技能目录
- **且** 应保留代理目录中的不相关文件

#### 场景：通过标志更新存储的代理选择
- **当** 工作区更新收到 `--tools <ids>` 或 `--tools none`
- **则** OpenSpec 应将存储的工作区本地选定代理列表替换为该选择
- **且** 未来不带 `--tools` 的工作区更新应使用存储的选择

#### 场景：非交互式更新工具选择
- **当** 工作区更新收到 `--tools all`、`--tools none` 或 `--tools <ids>`
- **则** OpenSpec 应使用该选定工具集更新工作区代理技能
- **且** 应避免提示选择代理

#### 场景：非交互式更新未选择工具
- **给定** 工作区本地选定的代理已存储
- **当** 非交互式工作区更新省略 `--tools`
- **则** OpenSpec 应使用活跃的全局配置文件刷新已存储的选定代理
- **且** 应避免提示选择代理

#### 场景：非交互式更新没有存储的选择
- **给定** 未存储工作区本地选定的代理
- **当** 非交互式工作区更新省略 `--tools`
- **则** OpenSpec 应完成而不安装代理技能
- **且** 应报告无操作并提供传递 `--tools` 的指导

#### 场景：报告工作区技能漂移
- **给定** 工作区本地技能状态记录了上次应用的工作流 ID
- **且** 活跃的全局配置文件解析为不同的工作流集
- **当** OpenSpec 报告工作区技能状态时
- **则** 应报告工作区本地技能与全局配置文件不同步
- **且** 应建议 `openspec workspace update`

#### 场景：报告干净的工作区技能同步
- **给定** 工作区本地技能状态与活跃的全局配置文件和选定的代理匹配
- **当** OpenSpec 报告工作区技能状态时
- **则** 不应报告配置文件漂移

#### 场景：报告工作区技能更新结果
- **当** 工作区更新更改代理技能状态时
- **则** OpenSpec 应报告哪些代理被刷新、添加、移除、跳过或失败

#### 场景：在 JSON 输出中报告工作区更新结果
- **当** 工作区更新启用 JSON 输出运行时
- **则** OpenSpec 应在机器可读输出中包含已刷新、添加、移除、跳过或失败的技能结果

### 要求：工作区技能更新界面已文档化
OpenSpec 应在面向用户的命令界面中暴露工作区技能设置/更新行为。

#### 场景：工作区更新出现在帮助中
- **当** 用户运行 `openspec workspace --help`
- **则** OpenSpec 应列出 `workspace update`
- **且** 应将其描述为刷新工作区本地代理技能

#### 场景：工作区更新选项出现在帮助中
- **当** 用户运行 `openspec workspace update --help`
- **则** OpenSpec 应文档化工作区选择选项
- **且** 应文档化 `--tools all|none|<ids>`
- **且** 应说明全局配置文件选择工作流，`--tools` 选择代理

#### 场景：工作区更新出现在自动补全中
- **当** 生成 shell 自动补全时
- **则** 工作区命令注册表应包含 `workspace update`
- **且** 应包含相关选项，如 `--workspace`、`--tools`、`--json` 和 `--no-interactive`
